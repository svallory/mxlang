# Upstream provenance

`packages/editors/zed` ships four languages for Zed (AngularMX shares
Solid's grammar; AstroMX has `packages/editors/tree-sitter-astromx` and
injects `MX` into its template body):

- `MX` (`.mx`), backed by this monorepo's own
  `packages/editors/tree-sitter-mx`: a vendored `marko-js/tree-sitter` plus
  the name-sugar shorthands. That package's own `UPSTREAM.md` owns its pin
  and patches; this file only records how it is wired into the extension.
- `Solid`, backed by this monorepo's own `packages/editors/tree-sitter-solid` — a
  patched `tree-sitter-typescript` (tsx dialect) with an `mx_element`
  external token in expression position. That package's own `UPSTREAM.md`
  owns its `tree-sitter-typescript` pin and patch; this file only records how
  its output is wired into the extension.

### When Zed calls the TypeScript hooks

Read in `zed-industries/zed` at `48741fd17d0dec28be6ad664b0a06dc7202086be`,
`crates/project/src/lsp_store.rs`:

- `workspace_configuration_for_adapter` and
  `initialization_options_for_adapter` (~4393-4462) start from the target
  server's own settings, then loop over `delegate.registered_lsp_adapters()`
  and merge every *other* adapter's `additional_workspace_configuration` /
  `additional_initialization_options` for that target. That list is
  `language_registry.all_lsp_adapters()` (~17173): every adapter an installed
  extension registered, whether or not its server runs. So this extension's
  hooks run for a TypeScript server because it declares
  `[language_servers.mxlang]`; no MX file has to have started the `mxlang`
  server in that worktree. The `worktree` the hooks receive is the target
  server's.
- Initialization options are computed once, when the target server starts
  (~662). Workspace configuration is computed at start (~653), on every
  `workspace/configuration` request from the server (~1037), and when
  settings change for a running server (~9873). A plugin installed into an
  open project therefore reaches `vtsls` on its next configuration request,
  and `typescript-language-server` only on a restart.
- `crates/language_extension/src/extension_lsp_adapter.rs` (~399-450) passes
  the target's `LanguageServerName` to the extension and parses the returned
  JSON; an error is logged, not fatal.

The LSP language ids in `languages` are the languages' `config.toml` names
lowercased (`LanguageName::lsp_id`): `mx`, `solid`, `reactmx`, `preactmx`,
`honomx`, `angularmx`. AstroMX is left out, as in
`[language_servers.mxlang]`. VS Code's id for `.ng.mx` is `ngmx`; Zed's is
`angularmx`.

`scripts/vendor.sh` generates `languages/mx/*.scm` the same way as
`languages/solid/*.scm`, and `.github/workflows/upstream-check.yml`'s
`vendored-files-match` job regenerates and diffs all three languages. MX's
drift check against `marko-js/tree-sitter` itself is the grammar package's
`scripts/vendor-check.sh` (job `mx-vendor-matches`).

## MX owns its grammar (2026-10-05)

This extension rides `marko-js/tree-sitter` and `marko-js/zed`'s queries as
its base. The name sugar (`apps/docs/docs/design-notes/adr-name-sugar.md`) is
MX syntax that Marko's grammar misparses: the `:name` sugar (`<input:email>`,
`<:email>`) and `#id`/`.class`/`:name` in attribute position (`<input
type="email" :email #main .big>`): Marko's grammar reads `a:b` as one tag name
and `"email" :email` as one attribute value. So MX owns its grammar:
`packages/editors/tree-sitter-mx`, a snapshot of Marko's grammar plus patches,
named `mx` so it coexists with the official Marko extension's `marko` grammar.
Everything else about `.mx` (its identity, Marko as the reference for every construct
MX shares with it) still holds; the grammar follows Marko upstream through its
pin and `patches/`.

Solid has no equivalent of `marko-js/zed` to source `injections.scm`,
`brackets.scm` and `outline.scm` from — no reference Zed extension for this
grammar exists. Those three query names' base content is hand-authored in
`base/solid/*.scm` (see "Local modifications" below).

## Local modifications

`languages/solid/highlights.scm` is
`packages/editors/tree-sitter-solid/queries/highlights.scm` (that package's own,
already-final query — see its `UPSTREAM.md`) plus
`overlay/solid/highlights.scm` concatenated on. `injections.scm`,
`brackets.scm` and `outline.scm` have no upstream source at all, so their
base content lives in this package's own `base/solid/*.scm` (hand-authored,
reviewed like any other source file) with `overlay/solid/*.scm`
concatenated the same way. All four Solid overlay files are currently
empty: the base content already covers every node the grammar emits.

`base/solid/injections.scm` injects this extension's own `MX` language into
`mx_element` so the otherwise-opaque region highlights instead of remaining
plain text.

### Solid injection

`base/{solid,ngmx,reactmx,preactmx,honomx}/injections.scm` set
`injection.language "MX"`. Zed resolves an injected language by matching
that string against an **installed language's own `name`**
(case-insensitively), not against a grammar key. `languages/mx/config.toml`
declares `name = "MX"`, so the injection resolves to this extension's own
`MX` language and the region is parsed with the `[grammars.mx]` grammar
(tree-sitter-mx), name sugars included; `languages/astromx/injections.scm`
already injects `MX` for its template body the same way. No other extension
is needed. Before this, the hosts injected `"marko"`, which only the official
`marko-js/zed` extension's `Marko` language satisfied, through Marko's
grammar, which misparses the name sugars.
`packages/editors/tree-sitter-mx/test/regions.bun-test.mts` proves an
`mx_element` region parses on its own with the MX grammar and that no
`languages/*/injections.scm` injects `marko`.

`extension.toml` deliberately omits `[language_servers.marko]`, `src/lib.rs`
and `Cargo.toml` — a grammar-only extension needs no Rust build (Zed's
`extension_builder.rs` only runs the Rust build when `Cargo.toml` exists).

## Bump procedure — Solid

Solid has two independent "bumps": the grammar itself (owned by
`packages/editors/tree-sitter-solid`) and this extension's wiring to it.

**Grammar change** (new scanner fix, new upstream `tree-sitter-typescript`
pin, etc.) — see `packages/editors/tree-sitter-solid/UPSTREAM.md`'s own bump
procedure. That package's changes must land as **committed** commits before
they can reach Zed at all (see "A note on the `file://` dev loop" below).

**Extension wiring change** (this package):

1. If `packages/editors/tree-sitter-solid/queries/highlights.scm` changed, or
   `base/solid/*.scm` needs updating for a new node the grammar now emits:
   edit the source (the grammar package's file, or this package's
   `base/solid/*.scm` — never `languages/solid/*.scm` directly).
2. Regenerate: `./scripts/vendor.sh` (no args). This rewrites
   `languages/solid/*.scm` from `packages/editors/tree-sitter-solid`'s highlights
   query, `base/solid/*.scm`, and `overlay/solid/*.scm`.
3. If the grammar itself changed (new commit under
   `packages/editors/tree-sitter-solid`): `git rev-parse HEAD` and update
   `extension.toml`'s `[grammars.solid]` `rev` to the new sha
   (`scripts/check-grammar-revs.sh`, run by `scripts/zed-compile-check.sh`
   and CI, fails while any `file://` grammar's `rev` lacks its
   `path/src/parser.c` or differs from HEAD's `src/`) — see
   `README.md`'s "Dev install (Zed) — Solid" for the full commit-then-bump
   loop.
4. Reinstall the dev extension in Zed and spot-check highlighting, bracket
   matching, outline, and the `MX` injection on a `.solid.mx` file (see
   "Solid injection" above).
5. Commit `languages/solid/*.scm`, any changed `base/solid/*.scm`,
   `extension.toml` (if `rev` moved), and this file together.

### A note on the `file://` dev loop

Because `[grammars.solid]`'s `rev` must be a real commit sha, **there is no
way to iterate on the grammar and see the result in Zed without committing
first.** Expect to commit more often than feels natural while iterating on
`packages/editors/tree-sitter-solid` under active Zed testing — that is the cost of
a `file://` dev dependency, not a workflow mistake.

## No `vendor.sh --check`

This script has no `--check` mode (the retired MX language's version did —
it compared `marko-js/tree-sitter`/`marko-js/zed` pins against upstream
HEAD). Solid's `highlights.scm` source is `packages/editors/tree-sitter-solid`, a
local sibling package with no networked upstream HEAD to drift against, so a
"check" mode here could only ever report success, and a gate that
cannot fail is not a gate. `moon.yml`'s `vendor-check` task and
`package.json`'s `vendor:check` script were removed along with it.
`.github/workflows/upstream-check.yml`'s `vendored-files-match` job is the
real check: it regenerates and diffs against committed output.

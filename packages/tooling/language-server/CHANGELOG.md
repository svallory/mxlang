# @mxlang/language-server

## 0.1.0-alpha.33 — 2026-10-18

- **Added (ls-angular-host-wiring):** Angular-host documents get real compile/translate diagnostics. A whole-file `.mx` under the `angular-template` target compiles through `@mxlang/angular`'s `compile`; a `.ng.mx` compiles whole-file through `compileNgMx`, routed by suffix (never as html, whatever `mx.host` derived), so errors and warnings inside an MX region land at their authored position. Warnings (e.g. a `<for>` with no `by=`) are published too. `@angular/compiler-cli` is never loaded — not a dependency of anything the server imports, and proven absent by `dist-build.test.ts` (resolution fails and the module cache stays clean after both compiles). Angular *template* diagnostics stay with the TypeScript plugin (separate item). A `.ng.mx` reports no callee-dependency list yet, so a watcher edge for an imported tag module is a follow-up. `.ng.mx` region errors carry no code-frame `data` yet (Angular page errors do); also a follow-up with the dependencies work.

- **Changed:** one diagnostic per error of the file (core's `TranslateError.errors`).

- **Changed (third-party-data-host):** a third-party host on the data target (`.mesh.mx`) resolves with no diagnostics and compiles whole-file through the host's descriptor; data's errors are positioned in the file. `tsconfig.json` roots at the repo for the shared fixtures; the build config keeps `src`.

- **Changed (bridge-host):** a region file is routed by suffix through the document's own lookup (`lookupFor(policy)`) to the host whose file kind has a region entry; the file is printed with `mx: true`. `REGION_LANGUAGE_IDS` added; `SOLID_MX_LANGUAGE_IDS` kept as its alias. An unregistered `.<word>.mx` and a third-party host's file (`.mesh.mx`) compile whole-file under the page policy, as before.

- **Changed (solid-rename):** the Solid file kind accepts the language ids `solidmx` and `solid`; `SolidMX` is no longer recognised. Zed now sends `solid` because its LSP id is the lowercased language name, and the Zed language is renamed from `SolidMX` to `Solid`. Settings keyed by `"SolidMX"` must use `"Solid"`.

- **Tests (name-sugar-tooling r2):** the mid-edit buffers pin an exact diagnostic count each; `input :` is 1 (the bare `:` is now an error).

- **Tests/Docs (name-sugar-tooling):** the sugar sigils right after whitespace inside a tag (`<input :`, `<input #`, `<input .`) never crash the server or report more than one error; the server page says it offers no completion or hover of its own, so there is no sugar hover.

- **Added (default-tag-ladder):** a package's `mx.<target>.defaultTag` reaches the page compile and each `.solid.mx` region; an invalid one is the one error the policy diagnostics report, positioned at the `package.json` value, and the built-in answers meanwhile.

- **Fix (translate-error-callee-file):** callee syntax errors are published on the callee URI at its real range. Caller pointers include the file and 1-based line/column and link to that range. An aggregate callee (several Marko parser errors in one file) says how many further errors its code frame holds, on the callee diagnostic and the caller's pointer alike.

### Fixed: no page compile after a target load failure (registration PR 7 round 2)

When the policy carries `target-not-found`, `target-load-failed`, `target-invalid-descriptor` or `host-invalid-descriptor`, the server reports the policy and scan diagnostics only. The fallback target's verdict on a page written for the missing one no longer buries the real error.

### Added: third-party targets (registration PR 7)

`diagnoseDocument` compiles through the descriptor a package specifier under `mx.target` / `mx.host` loaded (`policy.descriptor`), with that project's lookup. The new `target-not-found`, `target-load-failed`, `target-invalid-descriptor` and `host-invalid-descriptor` errors reach the document, linked to the key in `package.json`, through the existing policy-diagnostics path. The language server finds a target the project installed even when it runs as the VSIX-bundled copy: the specifier is resolved from the project, never from the bundle.

### Fixed (mx.contracts PR 2)

- Scanned contracts modules, sidecars and tag files are now caller dependencies.
  A watched-file edit re-diagnoses open callers without a page edit, including
  after a failed compile. Bun reloads edited declarations; Node ESM/TS reload
  still requires restart (`sync-esm-reload-node`).

### Added: target selection errors (target-select)

`mx.target` selects its target's host behaviour. Invalid targets and
host/target mismatches are errors on the document and `package.json`, with
full value ranges; mismatches link back to `mx.host`. Existing host warnings
are unchanged. Explicit `data` reports the registry's
error naming `parseData` and `TODO data-target-tooling-dispatch`.

### Changed (refactor/target-open-set)

The server resolves host policy and scans through `@mxlang/target-registry`'s wrappers over the built-in lookup, so it no longer depends on core's deleted closed lists; `diagnoseDocument` takes a policy whose `target` names the target and whose `host` is set only for a target that has one, and matches `mx.tags[].hosts` on `hostFilterKey(policy.target)` — the same string as before for every built-in. Compiles carry the built-in lookup, so a callee importing `AttrTag` from any registered target's package still reads. `isTranslateError` replaces `instanceof TranslateError`, so a positioned error from another copy of core keeps its position and dependencies. No change in the diagnostics published for any document.

### Changed

- **`x.astro.mx` is routed by kind** (amx-to-astro-mx): the server watches `**/*.astro.mx` (it watched `**/*.amx`), and an `.astro.mx` document no longer reaches the `.mx` compile; it is silent, like `.ng.mx`, since Astro-template diagnostics come from `mx-tsc --astro` and the TS plugin.

### Fixed

- **A compile error no longer ends in Babel's 0-based ` (L:C)`** (ts-plugin-ts80001-babel-suffix): `… opening "span" tag at 1:23 (1:32)` is now `… opening "span" tag at 1:23`, matching `mx-tsc` and the TypeScript plugin.

### Added

- **`data.codeFrame` on compile-error diagnostics**: the compiler's code frame (ANSI-free, dedented to its `> 1 |` marker) moves out of `message`, which now holds only the error text (about 38 tokens down to 6 on a simple case). Messages with no frame are unchanged. A callee-template parse error keeps its "custom tag threw" header, names the callee as `(in <path>:L:C)` and gets `relatedInformation` there.
- **A VSIX-only self-contained build** (relocatable: `import.meta.url` resolves from the bundle at run time) (`build/bundled.ts`, `bun build/bundled.ts`): `src/bin.ts` bundled to `bundle/bin.cjs` (gitignored, outside `files`) with `@mxlang/*` and `vscode-languageserver` inlined and `@marko/compiler` external, from one list (`build/bundled-config.ts`). The `@mxlang/vscode` VSIX ships it. The npm tarball, `files`, `package.json` and the public exports are unchanged.

- **Host-policy warnings** (host-policy-walk-edge-cases): a malformed `package.json` (the document is compiled as `html`, and the warning names the ancestor whose host it used to take) or an unknown `mx.host` is published as a warning on the open document, worded like the scan's (`<package.json>: message`). `diagnoseDocument` takes an optional trailing `hostPolicyDiagnostics` argument; omitting it leaves the output exactly as before. (`mx-tsc` and the editor's TypeScript plugin do not surface these warnings.)

### Fixed

- **Fixing a `package.json` clears its diagnostics** (review of the host-policy location fix): the server now watches `**/package.json` and records the nearest `package.json` (plus any a diagnostic names) as a dependency of each document, so a fix re-diagnoses every open document that read it and clears the `package.json` copy and both `.mx` copies without editing them. The `.mx` message names the `package.json` once (core's own leading path is dropped), and the `.solid.mx` branch compiles under the file path, not the URI.
- **Host-policy diagnostics are located where they can be acted on** (audit item 8; h23, h24, a24): they were published on the `.mx` URI at *package.json's* line:column, a coordinate that means nothing there. The `.mx` now gets the warning at 1:1 with the message `<package.json>:<line>:<col>: <message>` (1-based, like `mx-tsc`) and `relatedInformation` pointing at the real range; the same problem is also published on the `package.json` URI at that range, and cleared when the last open document reporting it recovers or closes. The `mx.tags` scan warnings follow the same rule. Both, because the VS Code client's `documentSelector` covers only `mx`/`solidmx`: an agent or editor that reads only the `.mx`'s diagnostics still gets an exact `package.json:line:col`.
- **`diagnoseDocument` passes a file path, not the URI, to the compiles** (ls-uri-path-in-messages): the react, preact, hono, html and solid-unit compiles were handed a `file://` URI, so their messages named `<cwd>/file:/...`.
- **No false "angular host is not wired" Error** (ls-angular-not-wired): `diagnoseDocument` no longer throws a severity-1 error at 1:1 on every Angular-host document, clean ones included (25 of 26 audit angular cases). Angular-host documents now get no diagnostics from the server; `mx-tsc` and the TypeScript plugin own them (host-policy warnings are still published). Wiring `@mxlang/angular` into the server is tracked as `ls-angular-host-wiring`.
- **A `.ng.mx` never reaches the html compile** (audit a24: an `.ng.mx` under a typo'd `mx.host`, resolved to the html default, got html's `@tags must be nested within another element`). Routed by file kind first (`hostModuleSegment`), as `mx-tsc` does. An unknown `mx.host` on an `.mx` page compiles under the host the resolver returns plus the warning, matching `mx-tsc` and vite (parity test in `@mxlang/tsc`).

- **The tarball ships only `dist/` and the README** (pkg-types-g10): `tsconfig.build.json` excludes `src/**/fixtures/**` (`dist/fixtures/…/stamp.tag.d.ts.map` is gone) and turns `declarationMap` off.

- **Added (mx-config):** MX's settings now load from a config file found with cosmiconfig under the name `mx`: `mx.config.ts`, `.js`, `.cjs`, `.mjs`, `.mts`, `.cts`, `.json`, `.yaml` or `.yml`, `.mxrc` and `.mxrc.*`, the same names under `.config/`, or the `mx` key of `package.json`, which stays valid with the same positioned errors. One file serves the whole project: MX reads it from the directory of the compiled file's nearest `package.json` only, never from a subdirectory or from above, so every tool resolves the same config for a file. In that directory `package.json#mx` wins, and every other config file there gets a `shadowed-config` warning naming the one in force. Configs are never merged. A config that is not an object (an array, a scalar, a module exporting a function or a promise) is a `malformed-config` error. The config is optional: with none, the target still comes from the `@mxlang/*` dependency or defaults to `html`. `mx.host` and `mx.target` are read the same way in every format. Relative paths (`tags`, `contracts`, a target package) resolve from the config's directory. Settings for a dialect live under the dialect's id, and MX passes them through without reading them. `extensions`, which maps a file extension to a dialect, is read from the config in every format. `mx.dialect`, a dialect package's identity block, is never read as MX's config. `provideMxConfig(root, config, { file })` lets a dialect or tool hand MX a config it built itself, without a file search. `findMxConfig(dir)` returns the config that applies to a directory and where it came from, and `isMxConfigFile(path)` tells a watcher whether a changed file is a config file. The language server, the Vite plugin and the Angular watcher pick up an edit to the config, or a config file created or deleted, without a restart. While an edit leaves the config unreadable, the last revision that loaded stays in force, and the problem is reported as a `malformed-config` error at its position in the file. Configs load synchronously, so a module config cannot use top-level `await`. An ES module config needs Node 22.12 or later (22.18 for TypeScript) or Bun; on an older Node, MX's error says so instead of the runtime's. On Node, an edited ES module config needs a restart to apply, and MX says so; reverting it to the text that last loaded clears the error. The Angular watcher now also rebuilds on an edit under `.config/`.

- **Changed (core-cold-start):** `@mxlang/core` loads its heavy dependencies lazily: importing the package no longer loads `@babel/parser` (it now loads on the first parse), `@babel/plugin-transform-typescript` (on the first strip, which every lowering with an expression payload runs) or `cosmiconfig` (on the first MX config read; `MX_CONFIG_SEARCH_PLACES` now spells out cosmiconfig 10.0.1's defaults, pinned by a test). Importing `@mxlang/core` in a fresh process is ~10 ms faster on Node and Bun. A dialect's first `lowerSource` no longer loads `dist/marko-frontend.cjs`: validating a dialect's syntax table uses the template parser the dist already inlines (`@mxlang/parser` under its `./lexer` export, so core's type program still sees only the curated `public.d.ts`), which cut ~50 ms (forge, Bun) off a dialect's first call — the bulk of the regression Mesh reported. `@mxlang/typescript-plugin` and `@mxlang/language-server` declare `cosmiconfig` and list it (with `@babel/parser`) in `BUNDLED_INSTALLED`, so the VSIX bundles ship the requires the bundler cannot follow.

- **Added (dialect-1c):** The tools check a dialect's files. `mx-tsc`, the language server and the TypeScript plugin route a file to the dialect that claims its extension (`mx.extensions` can route more, and `.probe.mx`-style extensions count), run `lowerSource` on it under the dialect's own syntax and tag rules, and report its diagnostics. A diagnostic's `source` is the dialect's `name` (`mxlang` when a project hands the extension to dialects but routing cannot settle which, say two dialects claim it) and its `code` is the dialect's own code; `mx-tsc` prints that code where `tsc` prints `TS<number>`, as in `page.probe(1,4): error PROBE_BAD: bad probe`. No JavaScript is generated for these files, and a file that is not a dialect's is checked exactly as before. The Vite plugin refuses to import a dialect's file: building a file calls its dialect's emit, and the error is positioned at the import, `<dialect name> files cannot be imported: the dialect registers no emit`, with the same text whether or not the file checks clean. For an entry or a hand-built id, it is positioned at the head of the dialect file. A dialect's file is checked against the project's contracts (`mx.contracts`) and local `tags/` like an MX file, so a contract violation shows in every tool. A dialect declared in a package below the project's root (a workspace package, or a `-b` reference of `mx-tsc`) counts for the files in that package, and a sibling package that declares no dialect keeps its own files. A dialect's file gets no `mx.target` problems from the language server: it has no target. `mx.target: "tree"` is now the ordinary unknown-target error in every tool, listing the valid targets. The `mx-tsc` data-package check and the registry's data-target mask are gone with the target they served.

- **Removed (core-drops-name-sugars):** **Breaking:** core has no name sugars. Every form reads as stock Marko reads it, with Marko's errors; a dialect that wants a name sugar claims it through its syntax table. The tag-adjacent shorthand (`<div#a.b>`, `<#a>`, `<.b>`) is unchanged. Readings that change, all visible to a dialect such as Mesh: a `:` in a tag head is part of the name (`<input:email>`, `<uuid:id>`, `<:x>` and concise `entity:Todo` are one tag name each, so on web an unknown custom tag; Angular's `<svg:rect>` passes through as written), and part of a shorthand part (`<div.c:b>` is the class `c:b`, `<div#d:b>` the id `d:b`); an attribute named `:x` is Marko's `value:x` and a bare `:` is `value:`, `:x(…)` is Marko's "Unsupported arguments on the `value:x` attribute."; a spaced `#x` or `.x` in attribute position is `Invalid attribute name` (a host with `acceptsForeignAttrNames`, Angular, keeps `#ref`); a spaced ` :x` or ` .x` after any value, a default value or a single atom included, continues the value as in stock, so `<div x=a :b/>` and `<if=:a :b>` are Marko's "Expected a single expression, but found `:` after it." and `x=a .b` is member access. Removed exports: `sugarTagName` (`@mxlang/core`), `HostDeclarations.claimsAttributeHash` (Angular no longer sets it), and the `":"` value of `MxShorthand.sigil` (`@mxlang/babel`). Removed codes: `MX_SUGAR_ARGUMENTS`, `MX_SUGAR_BOUND`, `MX_SUGAR_DYNAMIC`, `MX_SUGAR_NAME_INVALID`, `MX_SUGAR_NAME_MISSING`, `MX_SUGAR_ON_STATEMENT`, `MX_SECOND_NAME`, `MX_COLON_BEFORE_DYNAMIC` and `MX_SHORTHAND_INVALID`; the "`:x` right after a default value is not supported" error is gone with them. The `Attr.sugar` and `Attr.sugarValueOf` IR fields stay, set by the tag-adjacent shorthand and by a dialect's triggers.

- **Fixed (dialect-file-invalid-manifest):** A dialect file in a project whose dialect manifest is invalid (a bad `tagDirs`, say) is still taken for a dialect file, and shows the manifest's error. `dialectExtensions` lists the extensions a manifest that is invalid in another field names (when core would accept them), so `checkDialectFile` no longer returns nothing for the file: the error is reported at the head of the file with the manifest's real place in `origin`, and the language server also publishes it on the `package.json` at the offending field, as it already did when the error was reached through an `.mx` file. `emitOf` reports such a file as unsettled instead of throwing the manifest error.

- **Added (dialect-tag-discovery-tooling):** The tools show a dialect file's tag-discovery diagnostics with their severity, code and file. `checkDialectFile` keeps a scan diagnostic's `severity` and `code` (`MX_MISPLACED_TAG_FILE` was always a warning with no code, a scan error always an error with no code), and a diagnostic measured in another file (a tag file's own error, `MX_TAG_FILE_CYCLE` found in a second tag file, a manifest or contracts module) carries `origin: { file, line, column }`, the real place, while it stays at the head of the checked file so no tool paints it at the wrong offsets. The language server publishes such a diagnostic on its own file at its real range and leaves a pointer with `relatedInformation` at the head of the dialect file, and sets `code` on the scan warnings it shows for an MX file (`MX_MISPLACED_TAG_FILE`).

- **Fixed (dialect-tag-extensions-watch):** A dialect's `tagExtensions` entry that no claimed extension ends (`.concept` beside a dialect that claims `.probe`) is now a dialect file the tools list: `dialectExtensions` and `dialectExtensionsUnder` include `tagExtensions`. The language server watches such a tag file, so a change to it re-checks the dialect files that call it; the TypeScript plugin hosts it; and `mx-tsc` checks it and prints its errors, as it already did for a tag file named `.thing.probe`.

- **Fixed (ls-diagnostics-union-publish):** The language server publishes the union of the diagnostics against one URI instead of letting the last publish win. A tag file open in the editor keeps the diagnostics the documents that call it raise on it (and the other way round), and two callers raising the same diagnostic show it once. The union shrinks as it should: a caller that is fixed, edited or closed removes only its own part, and the file's own diagnostics changing leave the callers' parts alone.

- **Fixed (dialect-dependson-dependencies):** Editing a file a dialect's `tagFile` hook names with `ctx.dependsOn` re-checks the dialect files that call that tag file. `checkDialectFile` now adds those files, and the files of the tag files they called, to the dependencies it reports, counting only the tag files this check's lowering read (new `collectTagFileDependencies` export of `@mxlang/core`, `@unstable`). The language server asks the client to watch a dependency no watcher glob names (a `.json` data file) by its own path, and stops watching it once no open document names it. Before, only the tag files, contracts modules, sidecars and configs the scan read were dependencies, so the file changed on disk and the dialect file kept its old diagnostics until it was edited.

- **Fixed (tag-file-unsaved-read):** A dialect tag file an editor has open is read as the editor has it, so an unsaved fix to it clears the errors it caused on the files that call it (and an unsaved break raises them) before anything is saved. Core read the tag file from disk, so the caller's `` `<money>`'s definition has errors `` stayed until save, though an unsaved `.mx` template already reached it through `withCalleeInputSources`; the dialect's `tagFile` hook now gets that same text, and a contract derived from unsaved text is kept only while that text is in force, and one derived from the disk only while no unsaved text is. The language server re-checks the callers when such a document is closed, so an unsaved change that is discarded stops counting.

- **Changed (unknown-tag-wording):** `MX_UNKNOWN_TAG` no longer claims the contract was missing from `customTags`, which was false for a dialect file whose tags come from the dialect's `contracts`, its tag directories or the project's scan. A file of a dialect now names the dialect by its id: `` `<widget>` is not a known tag: it has no contract in `customTags` `` is now `` `<widget>` is not a known tag in the `mesh` dialect ``. Any other file now reads `` `<widget>` is not a known tag: no contract for it was given ``, because a lowering is handed its contracts and cannot tell where the caller found them. The `; did you mean `<x>`?` hint and the `(inside the unknown tag `<parent>`; may resolve once it is declared)` and `; inside `<parent>`: …` suffixes are unchanged, and so are the code and the position. Consumers that match on the code `MX_UNKNOWN_TAG` are unaffected; a golden file or a test that pins the old text needs to be regenerated. A dialect's `tagFile` hook whose contract carries a key no contract has now gets the wording every other contract source gives. `` `bogus` is not a contract key: a tag file's contract holds attributes, attributeTags, children, parents, defaultTag, or a key the dialect claims (`contractFields.tag`) `` is now `` Unknown key "bogus" in the declaration of tag "money"; allowed: attributes, attributeTags, children, parents, defaultTag `` (plus any key the dialect claims through `contractFields`), with the same code (`MX_TAG_FILE_ERROR`) and position. A `declares` key in that contract now reads `` `declares` is not allowed: no syntax module claims it (`contractFields`) ``.

- **Added (ir-diagnostic-codes):** Every error `lowerSource` and the template compilers report now carries a stable code, and so does every core warning: `IrDiagnostic.code` on the IR entry, `TranslateError.diagnosticCode` on a template compile, `MxWarning.code` on a warning. Match on the code; the wording may change, the code does not. Messages, severities and where a diagnostic starts are unchanged. Codes come from one catalogue, by family: - **Lowering**, the language's own rules: `MX_INVALID_IF`, `MX_INVALID_FOR`, `MX_UNKNOWN_ATTRIBUTE_TAG` and the rest. - **Contract**, a call checked against its tag's contract: `MX_UNKNOWN_TAG`, `MX_TAG_NOT_ALLOWED`, `MX_TEXT_NOT_ALLOWED`, `MX_MISSING_ATTRIBUTE`, `MX_UNKNOWN_ATTRIBUTE`, `MX_RESERVED_TAG`, `MX_INVALID_DEFAULT_TAG` and the rest. - **Data file**, what a static data tree cannot hold: `MX_STRUCTURAL_CONSTRUCT`, `MX_NOT_IN_DATA_FILE`. - **Registration**: contracts, configuration, dialects and tag files (`MX_INVALID_CONTRACT`, `MX_TAG_FILE_ERROR`, `MX_TAG_FILE_CYCLE`, `MX_INVALID_DIALECT_CONTRACT`). - **Hook defaults**: `MX_DIALECT_ERROR` and `MX_TAG_ERROR` for a hook's error that gave no code, `MX_DIALECT_WARNING` for its warning, `MX_DIALECT_HOOK_ERROR` and `MX_TAG_HOOK_ERROR` for a hook that broke its contract or threw. - **Warnings**: every core warning, among them `MX_DUPLICATE_ATTRIBUTE`, `MX_IGNORED_CONFIG` and `MX_SHADOWED_CONTRACT`. - **Parse**: the front end's own errors reach `code` too, `MX_PARSE_EXPRESSION` for a Babel error in an expression, `MX_EXPECTED_SINGLE_EXPRESSION` for a second expression where one is expected, the front end's own rules (`MX_TAG_NAME_MISSING`, `MX_ATTRIBUTE_TAG_AT_ROOT`, ...) and one `MX_PARSE_*` code per template-parser error (`MX_PARSE_MISSING_END_TAG`, `MX_PARSE_MALFORMED_OPEN_TAG`, ...). - **Internal**: `MX_INTERNAL_ERROR` for an error that reaches the entry without a code, which is a bug in MX. The specification lists every code (§13.7.5 Diagnostic codes). The tools that already showed a dialect's code now show core's too: on a dialect file `mx-tsc` prints `error MX_PARSE_MISSING_END_TAG:` where it printed `error TS80001:`, the TypeScript plugin gives the code in place of `80001`, the language server sets `code`, and a `@mxlang/vite-plugin` scan warning reads `MX_IGNORED_CONFIG: …`. The codes a dialect that restricts its tags relies on (`MX_UNKNOWN_TAG`, `MX_TAG_NOT_ALLOWED`, `MX_TEXT_NOT_ALLOWED`, `MX_EXPECTED_SINGLE_EXPRESSION`, `MX_DUPLICATE_ATTRIBUTE`) and `MX_TAG_FILE_ERROR` keep their meanings and their sites. Hooks may pass `at` as a span (`{ sourceStart, sourceEnd }`) as well as a position: `unit.fail(message, { at })` in `afterLower` and a contract hook's `ctx.fail(message, { at })` keep the span. `unit.warn(message, { at, code })` places and codes a dialect's warning. The `MX_` prefix is reserved for MX's own codes. A hook that passes a code starting with `MX_` gets `MX_DIALECT_HOOK_ERROR` (`MX_TAG_HOOK_ERROR` from a contract hook) in place of its diagnostic; a `tagFile` hook may still forward the diagnostics `ctx.lower()` gave it, codes included. Give your dialect's codes your own prefix. More diagnostics now say where they end (`end`, exclusive): a contract error ends at the end of `<name` when it is about the whole tag, after the value of the attribute it names, or at the end of the text it refuses; a `ctx.fail` given a span ends at the span's end; a contract key a dialect module or `mx.contracts` module writes ends at the end of the key; core's lowering warnings (`MX_DUPLICATE_ATTRIBUTE`, `MX_NOT_A_DOM_EVENT`, `MX_DEFINE_EXTRA_PARAMS`, `MX_BODY_DROPPED`, ...) end with the attribute or tag name they blame; a statement that does not parse is a point. Changed: the IR entry's `invalid-default-tag` code is now `MX_INVALID_DEFAULT_TAG`. The target-policy diagnostic keeps `invalid-default-tag`. No other code is renamed. An `afterLower` that throws is now `MX_DIALECT_HOOK_ERROR` (`the dialect's \`afterLower\` threw: …`), where it was reported as an internal error.

- **Changed (ir-diagnostic-tools):** Errors and warnings in `.mx` files now show MX's own code where they showed `TS80001` (for a `.solid.mx` region error or an `.astro.mx` lowering error, which carry no code, `TS80001` remains): `mx-tsc` prints `page.mx(1,6): error MX_PARSE_MISMATCHED_CLOSING_TAG: …` where it printed `page.mx(1,6): error TS80001: …`, the TypeScript plugin gives the code in place of `80001`, and the language server sets `code`. `TS80001` and `TS80002` remain for an error or warning that has no code. If a script matches `error TS80001` in `mx-tsc` output, match `error MX_` as well. The tools also paint the range a diagnostic covers, not one character. The editor (the language server and the TypeScript plugin) underlines the whole `<name` of a tag, the whole attribute, or the whole expression a diagnostic blames, in `.mx` and dialect files alike (except the region errors named above, which still underline one character). A diagnostic without a range, and a parse error at a single point, still underline one character. The Vite plugin's error overlay and build log draw a run of carets under that range in the code frame, to the end of the line when the range runs on.

- **Fixed (hosts-colon-astro-rethrow):** An undeclared colon tag in an `.astro.mx` file (`<ns:tag/>`, `<Ns:Tag/>`) is now a compile error at the tag, as in the JSX hosts: Astro used to emit it silently as a namespace element. The fix the error names is now true for every name. It suggests an `mx.tags` `prefix` only when some prefix can produce the name (the name ends in a file stem: `<a:-x/>` takes `prefix: "a:-"`), and for a name no tag file can end (`<uuid:/>`, `<a:b$/>`) it says only to write the name without the colon. The error now carries the end of the name, so an editor underlines all of it. A lowering error inside a region of a `.solid.mx`, `.preact.mx`, `.react.mx` or `.hono.mx` file, and in an `.astro.mx` file, now reaches `mx-tsc` and the TypeScript plugin with its `MX_*` code and its whole range, where it showed `TS80001` and one character. The language server shows the same code and underlines the whole range for such an error, where it showed one character.

- **Added (diagnostic-fix-its):** A diagnostic can now say how to fix itself. `IrDiagnostic.fixes` (`@unstable`) is a list of fixes, each `{ title, edits }` where an edit is `{ offset, end, newText }`: UTF-16 offsets into the same text the diagnostic's `offset` indexes (the file named by `file` when the diagnostic is positioned in another file), `end` exclusive, edits within one fix never overlapping, so applying all the edits of one fix to the original source gives the fixed source. The types are exported as `IrDiagnosticFix` and `IrDiagnosticEdit`, and a compile error carries the same list as `TranslateError.fixes`. The `<effect>` error (`MX_RESERVED_EFFECT_TAG`) now offers one fix, "Rename to `<script>`", that renames the open tag and, when there is one, the close tag; a self-closing tag, a concise tag and a `</>` close have only the open name. A host's "not supported" error for `<effect>` and the strict html policy's own row offer no fix. `fixes` travels wherever a diagnostic's `code` and `end` already do: the tag-file and tag-template errors, a JSX-region error re-raised by `@mxlang/tsx-bridge` (a non-enumerable `fixes`, offsets in the whole file), `AstroTemplateError`, `DialectDiagnostic` from `@mxlang/targets/dialect-check`, and the TypeScript plugin's `MxCompileDiagnostic`. The language server puts a diagnostic's fixes in its `data.fixes` and offers each one as a quick fix (code action) that edits the document, only while the text is the one the diagnostic was computed from. A fix for a diagnostic raised inside another file (a tag template) is not offered across files. The TypeScript plugin's tsserver diagnostics and `mx-tsc` do not show fixes.

- **Fixed (block-import-export-crash):** An `import` or an `export` written inside a `static`, `server` or `client` block no longer fails to compile. `static { import x from "./x" }` used to be refused with `'import' and 'export' may only appear at the top level.` (the block's braces reached the statement check), and `server { export default foo }` crashed the compiler with an internal `undefined is not an object` error. The block's statements are now module-level statements, as in Marko: `static { import x from "./x"; export const z = 1 }` hoists both to the module, exactly as `static import x from "./x"` and `static export const z = 1` do, and in a `client` block the names they bind are declared as `var name;`. An `import` or `export` below the block's own statements (inside a nested block, an `if` or a function body, or in a second block) is still refused at the position of the declaration, with a message that says where an `import` or `export` may go (it used to be Babel's "'import' and 'export' may only appear at the top level."), and a real syntax error, decorator or JSX beside an import in a block is reported at its own position instead of as the import's placement error. Blocks without an `import` or `export` compile as before.

- **Fixed (parse-error-cascade-after-expression-error):** An expression error in an open tag is now listed before the tag-level error it causes. `<for of=[1]|x|>` reads `|>` as the pipeline operator, which swallows the tag's `>`: the file has a missing end tag, and the cause is the expression error at the `|>`. `lowerSource` listed the "missing end tag" error first because it sorted by position; it now lists the expression error first, as Marko does (`compileSource` and `parseFragment` already did). Only an expression error (or a second expression, "Expected a single expression") inside the open tag of the tag reported as never closed moves; every other order is by position. Two parse errors that used to be zero-width now cover what they point at, so an editor underlines it and a build error frame marks it: an expression error spans the offending token (`|>` both characters, an identifier or string whole), and a trigger line that ends after its text ("ends after its text") spans the stray text, trailing whitespace left out. An expression that stops at its delimiter (the `}` of `${1+}`, the `>` of `<div x=a.>`) spans that character; only an error at the very end of the file has nothing to cover and stays a point.

- **Fixed (tag-var-error-position-siblings):** Two more `MX_INVALID_TAG_VAR` errors now point at the tag variable with its end, as the "declares no `<return>`" error beside them already does: a `/var` on a tag with no template (an L2 sidecar: "it has no template, so it has no `<return>` to bind") and a `/var` on an imported `.mx` unit that cannot be read ("`/n` on `<B>` can't bind: … does not exist / does not compile"). `<box/x/>` underlines `x`, where both used to point at the start of the tag and carry no end, so an editor or `mx-tsc` showed the squiggle on the tag name instead of on the variable to remove. A multi-line destructuring pattern is covered whole, and a region of a `.preact.mx` file reports the same file-absolute position.

- **Fixed (block-export-default-refused):** A default export in a `static`, `server` or `client` statement (`export default <value>`, `export default function`, `export default class`, `export { x as default }`, `export { default } from "…"`, `export { a as default } from "…"`, `export * as default from "…"`, in a block or without one) is a compile error at the export, `MX_INVALID_STATEMENT`, with a message that says a template is already its own default export and to use a named export instead. It used to compile to a module with two default exports that does not load, and `mx-tsc` reported TS2528 at 1:1. A type-only default (`export default interface I {}`) is erased and still compiles. Also, an `export { q }` or `export { q as other }` in its own `static`, `server` or `client` statement may name a binding an earlier statement or import declares (`static const q = 1;` then `static export { q };`, or a plain top-level `export { q }` after an `import`); it was refused with "Export 'q' is not defined." and printed a Babel warning, and stock Marko compiles it.

- **Changed (script-body-syntax-check):** A `<script>` body that does not parse is now a compile error, `MX_INVALID_STATEMENT`, positioned at the syntax error, as in Marko. Before, the html target emitted none of the body and so accepted any text (`<script>@d class C {}</script>` and `<script>const = 1;</script>` compiled), and the check for a stale `<const>` read in a `<script>` body was switched off for such a body without a word. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (tsc-watch-misses-mx-errors):** `mx-tsc --watch` reports MX compile errors on every rebuild. It used to print them once, after the first build (and under the first build's "Found 0 errors"), so an MX error introduced while the watcher ran, such as `<effect>` or an unclosed tag, produced "Found 0 errors" and no MX line at all. Each rebuild now prints the MX errors that hold after it, with their fix lines, before tsc's summary, and the summary's count includes them; a fixed error is gone from the next rebuild. A one-shot run with an MX error ends with `mx-tsc: Found N MX error(s) (tsc's own error count does not include MX errors).` when tsc printed its own count line, since tsc counts only its own diagnostics. The language server's quick-fix code actions skip a malformed fix (a `null` entry, a `null` edit, a missing `edits` array) instead of throwing on it.

- **Fixed (language-server-multi-parse-error-no-diagnostic):** A file with two or more parse errors now shows every one of them. Before, the editor showed none (the language server published an empty list and handed the error to its unexpected-error hook), the TypeScript plugin and `mx-tsc` showed one diagnostic at the start of the file with no code and the whole error text as its message, and a Vite build failed with no file position in its header. Each parse error is now its own diagnostic with its own code and range, the cause before what it leaves behind (`mx-tsc` prints `page.mx(1,11): error MX_PARSE_EXPRESSION` and `page.mx(2,12): ...`), and a Vite build locates the first and lists the others in its message, as it does for a compile error. An error that holds no errors still reports once.

# @mxlang/tsc

## Unreleased

- **Added (third-party-target, registration PR 7):** `mx-tsc` compiles through a target loaded from `package.json#mx.target` / `mx.host` and reports a failed load as `TS80003` at the key's value, with a failing exit code. Dispatch goldens gain the `third-party-*` rows; the `target-package` row now pins `target-not-found` where it pinned the staging error.

- **Angular template diagnostics now run on every `mx-tsc -w` rebuild** (mx-tsc-watch-templates, tsc-watch-ngmx-rebuild-test): the pass used to run once after the initial build, so a `.ng.mx` broken while the watcher runs was never checked again and the rebuild that saw the change reported `Found 0 errors`. Each rebuild now re-runs the pass over the compiles of the programs of that run, prints its diagnostics before tsc's own summary, and counts them in it (`Found 1 error.` where it used to say `Found 0 errors`). `-b -w` checks each project's `.ng.mx` under that project's own tsconfig, matched by the program's own root files, newest program per project, so a referenced project's template is checked as the last program compiled it. A watch run that never prints a summary still falls back to the single pass of a non-watch run, and a rebuild whose summary this pass does not recognize (a localized `tsc --locale`) says the templates went unchecked rather than passing over it.
- **Test fix (tsc-host-policy-test-macos-tmp round 2):** before normalising a printed TS80003 manifest location, tests assert that its filename resolves from the actual run cwd to the expected `package.json`. A missing-parent-traversal negative control prevents a wrong path from being hidden by normalisation; spawned runs use their project cwd, in-process runs use the runner cwd.

- **Test fix (tsc-host-policy-test-macos-tmp):** host-policy diagnostic tests normalise the unique temporary directory name rather than requiring its absolute spelling to survive TypeScript's cwd-relative formatting. This also works for macOS review checkouts under `/private/tmp`, where the shared `/private` prefix cancels. Production code is unchanged.

- **Test fix (vite-plugin-colored-marko-header):** "catches what plain tsc cannot even see" asserts on `stripVTControlCharacters(output)`: TypeScript colourises its pretty diagnostics when `FORCE_COLOR` reaches the spawned `tsc` (TypeScript ≥ 5.9), so the plain-text `error TS2307` substring no longer matched.

### Fixed: calling Angular tags preserves template diagnostics (ng-mx-tags-call-ts991010)

A `.ng.mx` component calling a `tags/` component now reports its real template errors at authored positions, without `TS-991010` at `(1,1)` or the tag's phase-2 `TS80001`. The shared plugin and Angular checker resolve the tag's generated component module in memory; no prior `mx-angular build` is required. Page dispatch and dispatch goldens are unchanged.

### Added: target selection errors (target-select, decisions 129/132)

Invalid `mx.target` values and host/target mismatches print positioned
`error TS80003` diagnostics and fail the run. TS80001 points from the MX
file to its manifest; existing warnings do not change exit status. Added
four-tool dispatch golden rows without regenerating existing rows, including
the explicit `data` tooling restriction (decision 131 addendum).

### Added: `mx-tsc` reports mistyped event handlers on preact, react and hono (jsx-handler-typing, decision 140)

Through `@mxlang/typescript-plugin`: `<button onClick=((a: string) => a.length)>` is now `TS2345` at the authored handler (it was silent), the body of a shorthand handler is type-checked, and valid handlers no longer report `TS7006`. See `@mxlang/typescript-plugin` for the user-visible new errors.

### Fixed

- **`mx-tsc -w` no longer loses a template's errors on the rebuild that touches it** (tsc-watch-rebuild-misses-error): appending a newline to a `.solid.mx` (or `.mx`) with a real `TS2345` made the rebuild print `Found 0 errors`, and every rebuild after that kept printing it — a silent pass, the one failure an agent cannot recover from by reading the output. `tsc -w` installs `getSourceFileByPath` on its watch host and `createProgram` prefers it over `getSourceFile` (`tryReuseStructureFromOldProgram`), while Volar's program proxy patches only `getSourceFile`, on its own copy of the host; so every *changed* file in a rebuild skipped the language plugins and was checked as its own MX source (a `.solid.mx` region then parses as plain TSX and nothing is wrong with it), while unchanged files kept reporting their errors from the cached first-program projection. `mx-tsc` removes the host's `getSourceFileByPath`, which puts a rebuild back on the `getSourceFile` path a non-watch run already takes; the watch host's own `getSourceFile` is that same versioned function called with `toPath(fileName)`, so its source-file cache, change detection and failed-lookup watching are unchanged. Upstream defect in `@volar/typescript@2.4.28` (`proxyCreateProgram.js:98`), worked around here; pin with `watch-rebuild-diagnostics.test.ts` (plain `tsc`, `.ts`, `.mx` and `.solid.mx`, four no-op rebuilds each, then a real fix and a real break again).

- **`TS80001` repeats neither the file nor the position (translate-error-no-repeated-path, audit item 17):** the message no longer opens with `<abs path>: ` (core) or an `    at <path>:L:C` line (typescript-plugin) after `file(L,C)`. The host-dispatch goldens drop exactly those repeats.

### Changed

- **`.amx` is now `.astro.mx`** (amx-to-astro-mx, decision 134): `mx-tsc --astro` checks `.astro.mx` files; `.amx` is no longer recognised. The `host-dispatch` fixtures and goldens `amx`, `amx-html-host` are renamed `astro-mx`, `astro-mx-html-host`, and the typecheck fixtures `amx-*` become `astro-mx-*`. The only golden change is the file name and extension strings.

- Dispatch golden `solid-file.json` (leg `solid-file`: the TS80001 diagnostic, its message, and the printed line) now carries the opener position, ` at 1:23`, on the mismatched-closing-tag error. No other golden moves.

### Added

- **`mx-tsc` prints host-policy diagnostics** (host-policy-diagnostics-tsc-tsserver): an unknown `mx.host` and a malformed `package.json` (audit cases h23, h24, a24) were silent in `mx-tsc`, and the malformed one exited 0 with nothing printed. They are now printed as `package.json(line,col): warning TS80003: …`, once per run. Warnings only: no exit code changes. They come from the language plugins' per-instance record of `resolveTargetPolicyDetailed` (no process-global listener), for `.mx`, `.solid.mx`, `.ng.mx` and `.amx` files alike.

- **NG8103 is configurable through `extendedDiagnostics`, with tests** (ng8103-extended-diagnostics, audit cases a21, a25): `*ngIf`/`*ngFor` used without `NgIf`/`NgFor`/`CommonModule` imported stays a warning, printed at the directive's `.ng.mx` line and column, exit code unchanged. A project promotes it as it would for `ng build`: `angularCompilerOptions.extendedDiagnostics.checks.missingControlFlowDirective: "error"` (printed as an error, non-zero exit), or `defaultCategory: "error"` (a per-check value wins); `"suppress"` hides it. Angular's own checker applies the category and `mx-tsc` passes the tsconfig through, so no code changed: the behaviour is now pinned by `ng-extended-diagnostics.test.ts` and documented in the README.

### Fixed

- **Compact output when stdout is not a TTY, even under `FORCE_COLOR`** (agent-output-positions, audit item 20): `tsc` switches its `pretty` mode on for any non-empty `FORCE_COLOR`, which CI sets, so `mx-tsc` printed a code frame, ANSI and declaration sites under every error (about 1.7x the text; 525 characters with ANSI (394 stripped) instead of 84 for audit case h01). `mx-tsc` now hides `FORCE_COLOR` from `tsc` when stdout is not a TTY and restores it after the run. `--pretty` on the command line or `pretty` in the tsconfig still wins; a TTY is unchanged. Pinned by `pretty.test.ts`; documented in the README.

- **A `TS80001` line carries one location** (agent-output-positions, audit item 13): `file(5,28): error TS80001: … (5:27)` ended with a second, 0-based `(line:column)` that Babel appends to a syntax error's message, so one line spelled the same position twice with two different columns. `mx-tsc` now strips that trailing suffix (the vite plugin already did). Pinned by `position-output.test.ts`.

- **`mx-tsc -b` resolves `.mx` modules like `-p`** (mx-tsc-build-extensionless-resolve): `import "./x"` and `"./x.ng"` found `x.ng.mx` under `-p` but gave a false `TS2307` under `-b`, as did the same forms through a `paths` alias, across a project reference, and through a package `exports` entry pointing at a `.ng.mx`. Volar's `proxyCreateProgram` keeps the host's own `resolveModuleNameLiterals` / `resolveModuleNames` for any batch of imports none of which ends in a plugin extension; `-p`'s plain host has none (so it always took Volar's patched resolver), while `-b`'s solution builder installs its own on the one `compilerHost` it shares across every project. `mx-tsc` now wraps the host's resolver: it answers first, and Volar's resolver is consulted only for imports it left unresolved. So the builder's cross-project resolution cache and, in `-w` / `-b -w`, tsc's failed-lookup watching (a module installed after the first error clears its `TS2307`) are kept. Where Volar's resolver also fails, the host's own result is kept (tsc's resolution cache keeps its failed lookups), and a host answer that is an `x.d.ts` beside an `x.ng.mx` is overruled by Volar's, which is what `-p` picks. A package's own `.d.ts` beside its `.ng.mx` is not overruled (what a package publishes as its types wins), so under `-b` and `-w` that one case still differs from `-p` alone. The cache holds resolved answers only and re-checks that the target still exists, so it can only be stale when the old target remains and a better candidate appears (`x.solid.mx` added beside a cached `x.ng.mx`; a package `exports` retargeted); it is rebuilt whenever a program's root names or options change. The wrapper is installed on the shared host once; Volar's resolved answers are cached, failures never. A module that really is missing still gives `TS2307` under both. Known limitation: on Linux `mx-tsc -w -p` does not recover from a module installed after watch started; plain `tsc -w -p` (TypeScript 6.0.3) behaves the same there, and `-b -w` recovers. The watch test asserts parity with plain tsc, not recovery.

- **`dist/*.cjs` no longer bakes the build machine's path**: Bun inlines `import.meta.url` in CJS output, so every `createRequire(import.meta.url)` (the plugin, `@mxlang/angular-checker`, `typescript`) resolved from the tree that built the package, not from the installed one. `build` now defines `import.meta.url`, `__filename` and `__dirname` from the bundle's own location and fails if a `file:///` literal or the build root remains. `scripts/pack-probe.ts` also typechecks a `.mx` fixture with the packed `mx-tsc`.

- **`mx-tsc -b` checks Angular templates of up-to-date projects** (mx-tsc-build-uptodate-templates): `tsc -b` skips a project whose build info says it is up to date, so no program was created and its `.ng.mx` templates were never checked: a template error exited 1 on the first run and **0 on the second** with no file changed. The template pass now runs for every project of the build graph (the named projects and, transitively, their `references`) whether or not tsc rebuilt it, over each project's `.ng.mx` files as the program tsc builds for that project holds them (`mx-tsc` creates it as in non-build mode, with `--listFilesOnly`: same plugins, resolver, `paths` and `moduleResolution`; a referenced project's `.ng.mx` is its own, checked under its tsconfig; the Angular CLI's default solution tsconfig, where no glob matches a `.ng.mx`, is covered), each under its own tsconfig and each file once; a file is checked once, under the first project in build order (dependencies first) whose program holds it, which the ownership relies on because a program can hold a referenced lib's `.ng.mx` as a source file, and compile diagnostics of the extra programs are de-duplicated against the main run's, so nothing is reported twice. Positions and messages are those of a non-build run. `--clean` checks nothing; `--dry` builds nothing and prints, per project, that a build would check its `.ng.mx` files, instead of passing silently. `-b --help` and a rejected `-b` command line run no pass; `--watch` runs the pass once, after the initial build, as before. Cost: every `-b` run, up to date or not, now pays for one program creation and one Angular checker per project with `.ng.mx` files; caching is a follow-up.

- **Angular template diagnostics pick the same tsconfig as the TypeScript pass** (mx-tsc-tsconfig-resolution): `resolveProjectTsconfig` no longer re-implements `tsc`'s choice by hand; it runs TypeScript's own `parseCommandLine`/`findConfigFile`. So `-P`, `--PROJECT`, `@args.txt` response files and `-p` with a directory lacking `tsconfig.json` (no pick, as `tsc` fails with TS5057) agree; input files without `-p` use no tsconfig (was: the nearest one); `--project=<path>`, which `tsc` rejects (TS5023), is no longer honoured. `-b` resolves its projects (default `.`, no walk up) and the template pass runs once per project, in the order given, each over the `.ng.mx` files under that project's directory; before, `mx-tsc -b a b` only ever checked the templates of the last project.

- **The tarball ships only `dist/` and the README** (pkg-types-g10): `files` is now `["dist", "README.md"]`, so `src/`, the test fixtures and `moon.yml` (115 files) no longer ship. `types` is dropped: it pointed at `src/index.ts`, and `bun build` emits no declarations. Nothing imports `@mxlang/tsc` as a TypeScript module; the package is used through its `mx-tsc` bin. `scripts/pack-probe.ts` installs the packed tarball and runs `mx-tsc --version`.

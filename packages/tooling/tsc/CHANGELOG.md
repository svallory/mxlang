# @mxlang/tsc

## Unreleased

- **Fixed (data-check-keys-on-base-target):** `mx-tsc` runs data's check on a project whose resolved base target is data (a host declaring `builtOn: "data"`), not only on `mx.target: "data"`: strict `structural`/`unknownTags` defaults and the `mx.data.*` keys, with the host's own compile still running beside `parseData` and the host's `defaultTag` ladder intact.

- **Changed (decision 162):** prints every error of an `.mx` file in one run; host-dispatch goldens gain the errors core used to stop before.

- **Fix (unmapped-diagnostics-region-enclosing-spans, decision 161):** `mx-tsc` places an unmappable diagnostic in a region file (`.solid.mx`, `.preact.mx`, `.react.mx`, `.hono.mx`), `.astro.mx` or `.ng.mx` on its enclosing tag or attribute with `(position approximate: …)`, as it already did for whole-file `.mx`, instead of at 1:1 as `(position unknown in this file kind: …)`.

- **Fix (unmapped-diagnostics-never-dropped, decision 161):** a TypeScript diagnostic whose generated position has no source mapping is no longer dropped by Volar: `mx-tsc` reports it on the nearest enclosing tag or attribute (else 1:1) with `(position approximate: generated <line>:<col>)`, `(position unknown in this file kind: generated <line>:<col>)` (a kind with no authored spans: region, `.astro.mx`, `.ng.mx`) or, only when the author spelled none of it, `(in MX-generated code, not yours: an MX bug; generated <line>:<col>)` appended, per diagnostic range, independent of the order diagnostics arrive in; related locations and `program.emit` diagnostics too, so a page whose errors sit in unmapped generated code (a whole-file Solid unit's expression values) fails the run instead of exiting 0. Exactly mapped diagnostics are byte-identical. Wraps Volar's `decorateProgram` export once per process.

- **Fix (mx-tsc-astro-ambient-types):** `mx-tsc` adds the hosts' ambient declaration files (`TargetHost.ambientTypes`) to every program, as the framework's own tooling does; a host adds them only to a program holding its files. Under `--astro` that is Astro's `env.d.ts` and `astro-jsx.d.ts` (the language server's fallback copies without an astro install) for a program holding an `.astro.mx` or a plain `.astro` file: an authored `<Fragment>` in a plain `.astro` page and the `Fragment` an `.astro.mx` projection writes resolve under Astro's tsconfig preset, without `types: ["astro/env"]`. Before, `Fragment` was TS2304, and `astro/jsx-runtime` TS2875 without astro installed.

Host-dispatch goldens: only the `export default` lines moved.

- **Added (data-cli, decision 131 addendum 4):** `mx-tsc` checks a data package. Run in a package whose own `package.json` says `mx.target: "data"` (rule-5 inference from an `@mxlang/data` dependency, and a monorepo root, keep their normal `tsc` run), `mx-tsc` / `mx-tsc -p <dir>` parses every `.mx` file the policy assigns to `data` with `@mxlang/data` and the package's tag map (`tags/` sidecars and `mx.contracts`), prints `file(line,col): error TS80001` (warnings `TS80002`; `package.json` problems `TS80003`) in full-path order, and exits 1 on any error. No tsconfig and no `-w`. `package.json#mx.data.{structural, unknownTags}` default to `"reject"` here. - **Added (third-party-target, registration PR 7):** `mx-tsc` compiles through a target loaded from `package.json#mx.target` / `mx.host` and reports a failed load as `TS80003` at the key's value, with a failing exit code. - **Angular template diagnostics now run on every `mx-tsc -w` rebuild** (mx-tsc-watch-templates, tsc-watch-ngmx-rebuild-test): the pass used to run once after the initial build, so a `.ng.mx` broken while the watcher runs was never checked again and the rebuild that saw the change reported `Found 0 errors`. A watch run that never prints a summary still falls back to the single pass of a non-watch run, and a rebuild whose summary this pass does not recognize (a localized `tsc --locale`) says the templates went unchecked rather than passing over it.
- **Test fix (tsc-host-policy-test-macos-tmp round 2):** before normalising a printed TS80003 manifest location, tests assert that its filename resolves from the actual run cwd to the expected `package.json`. A missing-parent-traversal negative control prevents a wrong path from being hidden by normalisation; spawned runs use their project cwd, in-process runs use the runner cwd.

### Fixed

- **`mx-tsc -w` no longer loses a template's errors on the rebuild that touches it** (tsc-watch-rebuild-misses-error): appending a newline to a `.solid.mx` (or `.mx`) with a real `TS2345` made the rebuild print `Found 0 errors`, and every rebuild after that kept printing it — a silent pass, the one failure an agent cannot recover from by reading the output. `tsc -w` installs `getSourceFileByPath` on its watch host and `createProgram` prefers it over `getSourceFile` (`tryReuseStructureFromOldProgram`), while Volar's program proxy patches only `getSourceFile`, on its own copy of the host; so every *changed* file in a rebuild skipped the language plugins and was checked as its own MX source (a `.solid.mx` region then parses as plain TSX and nothing is wrong with it), while unchanged files kept reporting their errors from the cached first-program projection. `mx-tsc` removes the host's `getSourceFileByPath`, which puts a rebuild back on the `getSourceFile` path a non-watch run already takes; the watch host's own `getSourceFile` is that same versioned function called with `toPath(fileName)`, so its source-file cache, change detection and failed-lookup watching are unchanged. Upstream defect in `@volar/typescript@2.4.28` (`proxyCreateProgram.js:98`), worked around here; pin with `watch-rebuild-diagnostics.test.ts` (plain `tsc`, `.ts`, `.mx` and `.solid.mx`, four no-op rebuilds each, then a real fix and a real break again).

- **`TS80001` repeats neither the file nor the position (translate-error-no-repeated-path, audit item 17):** the message no longer opens with `<abs path>: ` (core) or an `    at <path>:L:C` line (typescript-plugin) after `file(L,C)`. The host-dispatch goldens drop exactly those repeats.

### Fixed

- **Compact output when stdout is not a TTY, even under `FORCE_COLOR`** (agent-output-positions, audit item 20): `tsc` switches its `pretty` mode on for any non-empty `FORCE_COLOR`, which CI sets, so `mx-tsc` printed a code frame, ANSI and declaration sites under every error (about 1.7x the text; 525 characters with ANSI (394 stripped) instead of 84 for audit case h01). `mx-tsc` now hides `FORCE_COLOR` from `tsc` when stdout is not a TTY and restores it after the run. `--pretty` on the command line or `pretty` in the tsconfig still wins; a TTY is unchanged. Pinned by `pretty.test.ts`; documented in the README.

- **A `TS80001` line carries one location** (agent-output-positions, audit item 13): `file(5,28): error TS80001: … (5:27)` ended with a second, 0-based `(line:column)` that Babel appends to a syntax error's message, so one line spelled the same position twice with two different columns. `mx-tsc` now strips that trailing suffix (the vite plugin already did). Pinned by `position-output.test.ts`.

- **`mx-tsc -b` resolves `.mx` modules like `-p`** (mx-tsc-build-extensionless-resolve): `import "./x"` and `"./x.ng"` found `x.ng.mx` under `-p` but gave a false `TS2307` under `-b`, as did the same forms through a `paths` alias, across a project reference, and through a package `exports` entry pointing at a `.ng.mx`. Volar's `proxyCreateProgram` keeps the host's own `resolveModuleNameLiterals` / `resolveModuleNames` for any batch of imports none of which ends in a plugin extension; `-p`'s plain host has none (so it always took Volar's patched resolver), while `-b`'s solution builder installs its own on the one `compilerHost` it shares across every project. `mx-tsc` now wraps the host's resolver: it answers first, and Volar's resolver is consulted only for imports it left unresolved. So the builder's cross-project resolution cache and, in `-w` / `-b -w`, tsc's failed-lookup watching (a module installed after the first error clears its `TS2307`) are kept. Where Volar's resolver also fails, the host's own result is kept (tsc's resolution cache keeps its failed lookups), and a host answer that is an `x.d.ts` beside an `x.ng.mx` is overruled by Volar's, which is what `-p` picks. A package's own `.d.ts` beside its `.ng.mx` is not overruled (what a package publishes as its types wins), so under `-b` and `-w` that one case still differs from `-p` alone. The cache holds resolved answers only and re-checks that the target still exists, so it can only be stale when the old target remains and a better candidate appears (`x.solid.mx` added beside a cached `x.ng.mx`; a package `exports` retargeted); it is rebuilt whenever a program's root names or options change. The wrapper is installed on the shared host once; Volar's resolved answers are cached, failures never. A module that really is missing still gives `TS2307` under both. Known limitation: on Linux `mx-tsc -w -p` does not recover from a module installed after watch started; plain `tsc -w -p` (TypeScript 6.0.3) behaves the same there, and `-b -w` recovers. The watch test asserts parity with plain tsc, not recovery.

- **`dist/*.cjs` no longer bakes the build machine's path**: Bun inlines `import.meta.url` in CJS output, so every `createRequire(import.meta.url)` (the plugin, `@mxlang/angular-checker`, `typescript`) resolved from the tree that built the package, not from the installed one. `build` now defines `import.meta.url`, `__filename` and `__dirname` from the bundle's own location and fails if a `file:///` literal or the build root remains. `scripts/pack-probe.ts` also typechecks a `.mx` fixture with the packed `mx-tsc`.

- **`mx-tsc -b` checks Angular templates of up-to-date projects** (mx-tsc-build-uptodate-templates): `tsc -b` skips a project whose build info says it is up to date, so no program was created and its `.ng.mx` templates were never checked: a template error exited 1 on the first run and **0 on the second** with no file changed. The template pass now runs for every project of the build graph (the named projects and, transitively, their `references`) whether or not tsc rebuilt it, over each project's `.ng.mx` files as the program tsc builds for that project holds them (`mx-tsc` creates it as in non-build mode, with `--listFilesOnly`: same plugins, resolver, `paths` and `moduleResolution`; a referenced project's `.ng.mx` is its own, checked under its tsconfig; the Angular CLI's default solution tsconfig, where no glob matches a `.ng.mx`, is covered), each under its own tsconfig and each file once; a file is checked once, under the first project in build order (dependencies first) whose program holds it, which the ownership relies on because a program can hold a referenced lib's `.ng.mx` as a source file, and compile diagnostics of the extra programs are de-duplicated against the main run's, so nothing is reported twice. Positions and messages are those of a non-build run. `--clean` checks nothing; `--dry` builds nothing and prints, per project, that a build would check its `.ng.mx` files, instead of passing silently. `-b --help` and a rejected `-b` command line run no pass; `--watch` runs the pass once, after the initial build, as before. Cost: every `-b` run, up to date or not, now pays for one program creation and one Angular checker per project with `.ng.mx` files; caching is a follow-up.

- **Angular template diagnostics pick the same tsconfig as the TypeScript pass** (mx-tsc-tsconfig-resolution): `resolveProjectTsconfig` no longer re-implements `tsc`'s choice by hand; it runs TypeScript's own `parseCommandLine`/`findConfigFile`. So `-P`, `--PROJECT`, `@args.txt` response files and `-p` with a directory lacking `tsconfig.json` (no pick, as `tsc` fails with TS5057) agree; input files without `-p` use no tsconfig (was: the nearest one); `--project=<path>`, which `tsc` rejects (TS5023), is no longer honoured. `-b` resolves its projects (default `.`, no walk up) and the template pass runs once per project, in the order given, each over the `.ng.mx` files under that project's directory; before, `mx-tsc -b a b` only ever checked the templates of the last project.

- **The tarball ships only `dist/` and the README** (pkg-types-g10): `files` is now `["dist", "README.md"]`, so `src/`, the test fixtures and `moon.yml` (115 files) no longer ship. `types` is dropped: it pointed at `src/index.ts`, and `bun build` emits no declarations. Nothing imports `@mxlang/tsc` as a TypeScript module; the package is used through its `mx-tsc` bin. `scripts/pack-probe.ts` installs the packed tarball and runs `mx-tsc --version`.

- **Changed (release-changelog-in-package):** `CHANGELOG.md` is now part of every published tarball (`files` lists it in all packed packages); `bun pm pack` honours `files` only, so the alpha.11 tarballs carried just `README.md` and `dist`.

- **Fixed (ambient-types-followups):** A host's `ambientTypes` is now asked through each root file's own lookup (the nearest `package.json` above the file, as every other host operation resolves it), then the tsconfig directory's, and its package files resolve first from the directory of the first root file whose policy selects it (so the root order never picks which install answers), so a package below a monorepo's root tsconfig, or one whose host is installed only beside its files, gets its ambient types. A host whose `ambientTypes` returns no iterable of files (a number, `undefined`, an object without an iterator, a string), an entry that is not a file path (`[undefined]` from `resolve` of a missing file, `[42]`), or a generator that throws while read, is one `TS80004` error naming the package instead of a crash, in `mx-tsc` and the editor. `mx-tsc -w` reports a throwing host on every build while it throws, counted in that build's summary (the first build's summary no longer says "Found 0 errors" above it), and resets the exit code once a rebuild is clean.

- **Fixed (ambient-types-throw-guard):** A host whose `ambientTypes` throws no longer crashes the type check. `mx-tsc` prints one `error TS80004: host <package>: ambientTypes threw: <message>` diagnostic, exits 1, and still checks the project without that host's ambient files. The TypeScript plugin reports the same message as a project-level diagnostic in the editor. Other hosts' ambient types still resolve.

- **Changed (tree-ir-entry):** The tree target is replaced by core's IR entry point (decision 204). A program that reads a `.mx` file as a tree (a dialect such as Mesh's resource definitions) now calls `@mxlang/core`'s `lowerSource` and walks core's own IR; there is no second projection of it. - Removed: the `@mxlang/data` package, with `parseData`, `parseDataFile`, `serializeDataDocument`, `dataDeclarations`, `dataTaglib`, `neutralizations`, `DATA_TAGLIB_ID`, `RESERVED_NAMES`, `ParseDataOptions`, `ParseDataResult`, `DataDiagnostic` and the `Data*` tree types (`DataDocument`, `DataNode`, `DataTag`, `DataAttr`, `DataAttrTag`, `DataExpr`, `DataImport`, `DataStatement`, …). `@mxlang/targets` no longer registers the `tree` descriptor, and `mx.target: "tree"` in a `package.json` is an error in every tool: ``mx.target "tree" was removed (decision 204); a consumer that reads the tree calls lowerSource from @mxlang/core``. The hint for the reserved name `data` (in `mx.target` and in a descriptor's `builtOn`) ends the same way instead of pointing at `"tree"`. The `mx-tsc` check of a data package goes with it: a project with `mx.target: "tree"` now gets an ordinary `tsc` run plus that error. Dialect files are not checked by the tools until the dialect API lands. `@mxlang/data` is deprecated on the registry at the next publish. - Added (`@unstable`): `lowerSource(source, filename, options?)` and `lowerFile(path, options?)` return `{ ir, diagnostics }`: a `SpannedIr`, or `undefined` when any error was reported (never a partial IR), and every independent diagnostic as an `IrDiagnostic` (`severity`, `message`, `line`, `column`, `offset`, `file?`, `code?`). No source input makes either throw. Options: `customTags`, `syntax`, `tagRules`, `defaultTag`, `structural`, `imports`, `unknownTags`, `warnings`; all but `tagRules` have `parseData`'s meanings. With `tagRules: "none"`, every diagnostic `parseData` reported is reported at the same text and position, including the messages that still say "data tree"; under the default `html` rules a file `parseData` accepted can fail (`<input><child/></input>` is ``The closing "input" tag was not expected``). - Added (`@unstable`): tag rules presets, `tagRulesPreset(name, nativeTags?)` with `TagRules` and `TagRulesPreset`. An absent `tagRules` is `html`, the full HTML rules (decision 212 item 8); a dialect whose tags are not HTML passes `none` (Mesh does). `none` has no native elements, so Marko's 19 HTML parse rules (void, raw text, preserved whitespace) are off and `source`, `input` or `title` is an ordinary tag; it declares the module statements and an open-tag-only `<const>`/`<return>`. `markup` adds the web elements and core's statement tags; `html` is the html target's whole table. `tagRules` is a `lowerSource` option only, never a project or host setting (ruling 209). - Added (`@unstable`): `IR_VERSION` (today `1`), the version of the IR's shape, which goes up by one with every change a reader of the IR can observe. - New exports of `@mxlang/core`, all `@unstable`: the functions `lowerSource`, `lowerFile` and `tagRulesPreset`; the values `IR_VERSION` and `TAG_RULES_PRESETS` (`["html", "markup", "none"]`); the types `LowerSourceOptions`, `LowerSourceResult`, `IrDiagnostic`, `Spanned`, `SpannedIr`, `ImportName`, `TagRules` and `TagRulesPreset`. - Changed: spans are guaranteed where a consumer needs them. `Attr.span` is set on every attribute kind (name through value, arguments with their parentheses included, a spread from `...`, a name sugar's token, a default attribute from its `=`; a synthesized attribute, such as a shorthand with a placeholder or a shorthand class merged into `class`, has none, and `lowerSource` reports those forms as positioned errors, as `parseData` did), and `AttributeTagIf`/`AttributeTagFor` carry the span of the whole `<if>` chain or `<for>`. `Import` gains `from`, `names` (`ImportName`: `imported`, `local`, `kind`, `span`, `localSpan?`, `typeOnly?`) and `typeOnly`, read from the parsed declaration. `SpannedIr` makes every `span` required in its type, and with it a static attribute's `valueSpan` and an `Import`'s `from` and `names`, and the IR `lowerSource` returns is a fresh copy whose `DelegatedTag`/`AttributeTag` spans end at the tag (the trailing line terminator of a concise tag is trimmed) and whose `DelegatedTag.args` is always present (`[]` with none). - Migration from `parseData`: pass `tagRules: "none"` to keep `parseData`'s parse rules (the default is `html`). A tag is `ir.body[i].tag` (a `DelegatedTag`; attribute tags are `attributeTags`/`attributeTagTree`); attribute kind `string` is `static` and `expression` is `dynamic`, and a whole-value atom or member is a `static` attribute carrying `atom`/`member`; a wildcard-matched child's `tag.name` is the canonical contract name, with the authored spelling in `tag.alias.authored`; `statements`/`imports` are `ir.imports` and `ir.hoisted`.

- **Added (dialect-1c):** The tools check a dialect's files. `mx-tsc`, the language server and the TypeScript plugin route a file to the dialect that claims its extension (`mx.extensions` can route more, and `.probe.mx`-style extensions count), run `lowerSource` on it under the dialect's own syntax and tag rules, and report its diagnostics. A diagnostic's `source` is the dialect's `name` (`mxlang` when a project hands the extension to dialects but routing cannot settle which, say two dialects claim it) and its `code` is the dialect's own code; `mx-tsc` prints that code where `tsc` prints `TS<number>`, as in `page.probe(1,4): error PROBE_BAD: bad probe`. No JavaScript is generated for these files, and a file that is not a dialect's is checked exactly as before. The Vite plugin refuses to import a dialect's file: building a file calls its dialect's emit, and the error is positioned at the import, `<dialect name> files cannot be imported: the dialect registers no emit`, with the same text whether or not the file checks clean. For an entry or a hand-built id, it is positioned at the head of the dialect file. A dialect's file is checked against the project's contracts (`mx.contracts`) and local `tags/` like an MX file, so a contract violation shows in every tool. A dialect declared in a package below the project's root (a workspace package, or a `-b` reference of `mx-tsc`) counts for the files in that package, and a sibling package that declares no dialect keeps its own files. A dialect's file gets no `mx.target` problems from the language server: it has no target. `mx.target: "tree"` is now the ordinary unknown-target error in every tool, listing the valid targets. The `mx-tsc` data-package check and the registry's data-target mask are gone with the target they served.

- **Removed (core-drops-name-sugars):** **Breaking:** core has no name sugars. Every form reads as stock Marko reads it, with Marko's errors; a dialect that wants a name sugar claims it through its syntax table. The tag-adjacent shorthand (`<div#a.b>`, `<#a>`, `<.b>`) is unchanged. Readings that change, all visible to a dialect such as Mesh: a `:` in a tag head is part of the name (`<input:email>`, `<uuid:id>`, `<:x>` and concise `entity:Todo` are one tag name each, so on web an unknown custom tag; Angular's `<svg:rect>` passes through as written), and part of a shorthand part (`<div.c:b>` is the class `c:b`, `<div#d:b>` the id `d:b`); an attribute named `:x` is Marko's `value:x` and a bare `:` is `value:`, `:x(…)` is Marko's "Unsupported arguments on the `value:x` attribute."; a spaced `#x` or `.x` in attribute position is `Invalid attribute name` (a host with `acceptsForeignAttrNames`, Angular, keeps `#ref`); a spaced ` :x` or ` .x` after any value, a default value or a single atom included, continues the value as in stock, so `<div x=a :b/>` and `<if=:a :b>` are Marko's "Expected a single expression, but found `:` after it." and `x=a .b` is member access. Removed exports: `sugarTagName` (`@mxlang/core`), `HostDeclarations.claimsAttributeHash` (Angular no longer sets it), and the `":"` value of `MxShorthand.sigil` (`@mxlang/babel`). Removed codes: `MX_SUGAR_ARGUMENTS`, `MX_SUGAR_BOUND`, `MX_SUGAR_DYNAMIC`, `MX_SUGAR_NAME_INVALID`, `MX_SUGAR_NAME_MISSING`, `MX_SUGAR_ON_STATEMENT`, `MX_SECOND_NAME`, `MX_COLON_BEFORE_DYNAMIC` and `MX_SHORTHAND_INVALID`; the "`:x` right after a default value is not supported" error is gone with them. The `Attr.sugar` and `Attr.sugarValueOf` IR fields stay, set by the tag-adjacent shorthand and by a dialect's triggers.

- **Removed (core-drops-atom-lexing):** **Breaking:** core has no atom syntax. `:x` in a `.mx` file is plain JavaScript, as in Marko: `<a b=:x/>`, `<a b=(f(:x))/>`, `${:x}` and the concise `a b=:x` are Marko's "Unexpected token" at the `:`, and `<a b=x::y/>` is "Expected a single expression, but found `:` after it.". `::` is no longer reserved: inside a name it is part of the name, as Marko reads it (`<a::b/>` is the tag `a::b`, `<a x::y=1/>` the attribute `x:` with the modifier `y`). A dialect builds atoms through its triggers: an `expressionTriggers` or `valueTriggers` row whose hook returns a `StringLiteral` marked `extra.mxAtom = { span }`; core records it, splices its string into `Expr.code`, and lowers a whole-value atom to a `static` attribute with `atom`, as before. Removed: the template parser's `onAtom` handler option and its `Atom` event, and the `MxAtom` node type (`@mxlang/babel`); the "`:a` is an atom" misuse errors, the "`::a` is reserved" error and the two hints about the `:` TypeScript owns. Kept: the `Atom` IR kind, `Expr.atoms`, `MxAtomMark`, `extra.mxAtom` and the `type: "atom"` contract shape check.

- **Fixed (dialect-tag-extensions-watch):** A dialect's `tagExtensions` entry that no claimed extension ends (`.concept` beside a dialect that claims `.probe`) is now a dialect file the tools list: `dialectExtensions` and `dialectExtensionsUnder` include `tagExtensions`. The language server watches such a tag file, so a change to it re-checks the dialect files that call it; the TypeScript plugin hosts it; and `mx-tsc` checks it and prints its errors, as it already did for a tag file named `.thing.probe`.

- **Changed (unknown-tag-wording):** `MX_UNKNOWN_TAG` no longer claims the contract was missing from `customTags`, which was false for a dialect file whose tags come from the dialect's `contracts`, its tag directories or the project's scan. A file of a dialect now names the dialect by its id: `` `<widget>` is not a known tag: it has no contract in `customTags` `` is now `` `<widget>` is not a known tag in the `mesh` dialect ``. Any other file now reads `` `<widget>` is not a known tag: no contract for it was given ``, because a lowering is handed its contracts and cannot tell where the caller found them. The `; did you mean `<x>`?` hint and the `(inside the unknown tag `<parent>`; may resolve once it is declared)` and `; inside `<parent>`: …` suffixes are unchanged, and so are the code and the position. Consumers that match on the code `MX_UNKNOWN_TAG` are unaffected; a golden file or a test that pins the old text needs to be regenerated. A dialect's `tagFile` hook whose contract carries a key no contract has now gets the wording every other contract source gives. `` `bogus` is not a contract key: a tag file's contract holds attributes, attributeTags, children, parents, defaultTag, or a key the dialect claims (`contractFields.tag`) `` is now `` Unknown key "bogus" in the declaration of tag "money"; allowed: attributes, attributeTags, children, parents, defaultTag `` (plus any key the dialect claims through `contractFields`), with the same code (`MX_TAG_FILE_ERROR`) and position. A `declares` key in that contract now reads `` `declares` is not allowed: no syntax module claims it (`contractFields`) ``.

- **Added (ir-diagnostic-codes):** Every error `lowerSource` and the template compilers report now carries a stable code, and so does every core warning: `IrDiagnostic.code` on the IR entry, `TranslateError.diagnosticCode` on a template compile, `MxWarning.code` on a warning. Match on the code; the wording may change, the code does not. Messages, severities and where a diagnostic starts are unchanged. Codes come from one catalogue, by family: - **Lowering**, the language's own rules: `MX_INVALID_IF`, `MX_INVALID_FOR`, `MX_UNKNOWN_ATTRIBUTE_TAG` and the rest. - **Contract**, a call checked against its tag's contract: `MX_UNKNOWN_TAG`, `MX_TAG_NOT_ALLOWED`, `MX_TEXT_NOT_ALLOWED`, `MX_MISSING_ATTRIBUTE`, `MX_UNKNOWN_ATTRIBUTE`, `MX_RESERVED_TAG`, `MX_INVALID_DEFAULT_TAG` and the rest. - **Data file**, what a static data tree cannot hold: `MX_STRUCTURAL_CONSTRUCT`, `MX_NOT_IN_DATA_FILE`. - **Registration**: contracts, configuration, dialects and tag files (`MX_INVALID_CONTRACT`, `MX_TAG_FILE_ERROR`, `MX_TAG_FILE_CYCLE`, `MX_INVALID_DIALECT_CONTRACT`). - **Hook defaults**: `MX_DIALECT_ERROR` and `MX_TAG_ERROR` for a hook's error that gave no code, `MX_DIALECT_WARNING` for its warning, `MX_DIALECT_HOOK_ERROR` and `MX_TAG_HOOK_ERROR` for a hook that broke its contract or threw. - **Warnings**: every core warning, among them `MX_DUPLICATE_ATTRIBUTE`, `MX_IGNORED_CONFIG` and `MX_SHADOWED_CONTRACT`. - **Parse**: the front end's own errors reach `code` too, `MX_PARSE_EXPRESSION` for a Babel error in an expression, `MX_EXPECTED_SINGLE_EXPRESSION` for a second expression where one is expected, the front end's own rules (`MX_TAG_NAME_MISSING`, `MX_ATTRIBUTE_TAG_AT_ROOT`, ...) and one `MX_PARSE_*` code per template-parser error (`MX_PARSE_MISSING_END_TAG`, `MX_PARSE_MALFORMED_OPEN_TAG`, ...). - **Internal**: `MX_INTERNAL_ERROR` for an error that reaches the entry without a code, which is a bug in MX. The specification lists every code (§13.7.5 Diagnostic codes). The tools that already showed a dialect's code now show core's too: on a dialect file `mx-tsc` prints `error MX_PARSE_MISSING_END_TAG:` where it printed `error TS80001:`, the TypeScript plugin gives the code in place of `80001`, the language server sets `code`, and a `@mxlang/vite-plugin` scan warning reads `MX_IGNORED_CONFIG: …`. The codes a dialect that restricts its tags relies on (`MX_UNKNOWN_TAG`, `MX_TAG_NOT_ALLOWED`, `MX_TEXT_NOT_ALLOWED`, `MX_EXPECTED_SINGLE_EXPRESSION`, `MX_DUPLICATE_ATTRIBUTE`) and `MX_TAG_FILE_ERROR` keep their meanings and their sites. Hooks may pass `at` as a span (`{ sourceStart, sourceEnd }`) as well as a position: `unit.fail(message, { at })` in `afterLower` and a contract hook's `ctx.fail(message, { at })` keep the span. `unit.warn(message, { at, code })` places and codes a dialect's warning. The `MX_` prefix is reserved for MX's own codes. A hook that passes a code starting with `MX_` gets `MX_DIALECT_HOOK_ERROR` (`MX_TAG_HOOK_ERROR` from a contract hook) in place of its diagnostic; a `tagFile` hook may still forward the diagnostics `ctx.lower()` gave it, codes included. Give your dialect's codes your own prefix. More diagnostics now say where they end (`end`, exclusive): a contract error ends at the end of `<name` when it is about the whole tag, after the value of the attribute it names, or at the end of the text it refuses; a `ctx.fail` given a span ends at the span's end; a contract key a dialect module or `mx.contracts` module writes ends at the end of the key; core's lowering warnings (`MX_DUPLICATE_ATTRIBUTE`, `MX_NOT_A_DOM_EVENT`, `MX_DEFINE_EXTRA_PARAMS`, `MX_BODY_DROPPED`, ...) end with the attribute or tag name they blame; a statement that does not parse is a point. Changed: the IR entry's `invalid-default-tag` code is now `MX_INVALID_DEFAULT_TAG`. The target-policy diagnostic keeps `invalid-default-tag`. No other code is renamed. An `afterLower` that throws is now `MX_DIALECT_HOOK_ERROR` (`the dialect's \`afterLower\` threw: …`), where it was reported as an internal error.

- **Changed (ir-diagnostic-tools):** Errors and warnings in `.mx` files now show MX's own code where they showed `TS80001` (for a `.solid.mx` region error or an `.astro.mx` lowering error, which carry no code, `TS80001` remains): `mx-tsc` prints `page.mx(1,6): error MX_PARSE_MISMATCHED_CLOSING_TAG: …` where it printed `page.mx(1,6): error TS80001: …`, the TypeScript plugin gives the code in place of `80001`, and the language server sets `code`. `TS80001` and `TS80002` remain for an error or warning that has no code. If a script matches `error TS80001` in `mx-tsc` output, match `error MX_` as well. The tools also paint the range a diagnostic covers, not one character. The editor (the language server and the TypeScript plugin) underlines the whole `<name` of a tag, the whole attribute, or the whole expression a diagnostic blames, in `.mx` and dialect files alike (except the region errors named above, which still underline one character). A diagnostic without a range, and a parse error at a single point, still underline one character. The Vite plugin's error overlay and build log draw a run of carets under that range in the code frame, to the end of the line when the range runs on.

- **Fixed (hosts-colon-astro-rethrow):** An undeclared colon tag in an `.astro.mx` file (`<ns:tag/>`, `<Ns:Tag/>`) is now a compile error at the tag, as in the JSX hosts: Astro used to emit it silently as a namespace element. The fix the error names is now true for every name. It suggests an `mx.tags` `prefix` only when some prefix can produce the name (the name ends in a file stem: `<a:-x/>` takes `prefix: "a:-"`), and for a name no tag file can end (`<uuid:/>`, `<a:b$/>`) it says only to write the name without the colon. The error now carries the end of the name, so an editor underlines all of it. A lowering error inside a region of a `.solid.mx`, `.preact.mx`, `.react.mx` or `.hono.mx` file, and in an `.astro.mx` file, now reaches `mx-tsc` and the TypeScript plugin with its `MX_*` code and its whole range, where it showed `TS80001` and one character. The language server shows the same code and underlines the whole range for such an error, where it showed one character.

- **Fixed (block-import-export-crash):** An `import` or an `export` written inside a `static`, `server` or `client` block no longer fails to compile. `static { import x from "./x" }` used to be refused with `'import' and 'export' may only appear at the top level.` (the block's braces reached the statement check), and `server { export default foo }` crashed the compiler with an internal `undefined is not an object` error. The block's statements are now module-level statements, as in Marko: `static { import x from "./x"; export const z = 1 }` hoists both to the module, exactly as `static import x from "./x"` and `static export const z = 1` do, and in a `client` block the names they bind are declared as `var name;`. An `import` or `export` below the block's own statements (inside a nested block, an `if` or a function body, or in a second block) is still refused at the position of the declaration, with a message that says where an `import` or `export` may go (it used to be Babel's "'import' and 'export' may only appear at the top level."), and a real syntax error, decorator or JSX beside an import in a block is reported at its own position instead of as the import's placement error. Blocks without an `import` or `export` compile as before.

- **Fixed (parse-error-cascade-after-expression-error):** An expression error in an open tag is now listed before the tag-level error it causes. `<for of=[1]|x|>` reads `|>` as the pipeline operator, which swallows the tag's `>`: the file has a missing end tag, and the cause is the expression error at the `|>`. `lowerSource` listed the "missing end tag" error first because it sorted by position; it now lists the expression error first, as Marko does (`compileSource` and `parseFragment` already did). Only an expression error (or a second expression, "Expected a single expression") inside the open tag of the tag reported as never closed moves; every other order is by position. Two parse errors that used to be zero-width now cover what they point at, so an editor underlines it and a build error frame marks it: an expression error spans the offending token (`|>` both characters, an identifier or string whole), and a trigger line that ends after its text ("ends after its text") spans the stray text, trailing whitespace left out. An expression that stops at its delimiter (the `}` of `${1+}`, the `>` of `<div x=a.>`) spans that character; only an error at the very end of the file has nothing to cover and stays a point.

- **Fixed (tag-var-error-position-siblings):** Two more `MX_INVALID_TAG_VAR` errors now point at the tag variable with its end, as the "declares no `<return>`" error beside them already does: a `/var` on a tag with no template (an L2 sidecar: "it has no template, so it has no `<return>` to bind") and a `/var` on an imported `.mx` unit that cannot be read ("`/n` on `<B>` can't bind: … does not exist / does not compile"). `<box/x/>` underlines `x`, where both used to point at the start of the tag and carry no end, so an editor or `mx-tsc` showed the squiggle on the tag name instead of on the variable to remove. A multi-line destructuring pattern is covered whole, and a region of a `.preact.mx` file reports the same file-absolute position.

- **Fixed (block-export-default-refused):** A default export in a `static`, `server` or `client` statement (`export default <value>`, `export default function`, `export default class`, `export { x as default }`, `export { default } from "…"`, `export { a as default } from "…"`, `export * as default from "…"`, in a block or without one) is a compile error at the export, `MX_INVALID_STATEMENT`, with a message that says a template is already its own default export and to use a named export instead. It used to compile to a module with two default exports that does not load, and `mx-tsc` reported TS2528 at 1:1. A type-only default (`export default interface I {}`) is erased and still compiles. Also, an `export { q }` or `export { q as other }` in its own `static`, `server` or `client` statement may name a binding an earlier statement or import declares (`static const q = 1;` then `static export { q };`, or a plain top-level `export { q }` after an `import`); it was refused with "Export 'q' is not defined." and printed a Babel warning, and stock Marko compiles it.

- **Added (fix-it-carriers-tsserver-tsc):** A diagnostic's quick fixes now reach tsserver and `tsc`. The TypeScript plugin answers `getCodeFixesAtPosition` for an MX diagnostic's range with one code fix per fix, whose edits apply to the `.mx` file (the `<effect>` error's "Rename to `<script>`" renames the open and the close tag, and a dialect's diagnostic can carry its own fixes); requests for TypeScript's own error codes, and for files with no such diagnostic, go to TypeScript unchanged. `mx-tsc` prints each fix on a `fix:` line under the diagnostic, e.g. ``fix: Rename to `<script>`: replace 2:4-2:10 with "script"; replace 2:17-2:23 with "script"`` (1-based `line:column`, end exclusive, new text quoted), the same with and without `--pretty`. The plugin also exports `applicableFixes` and `mxCodeFixes`.

- **Changed (script-body-syntax-check):** A `<script>` body that does not parse is now a compile error, `MX_INVALID_STATEMENT`, positioned at the syntax error, as in Marko. Before, the html target emitted none of the body and so accepted any text (`<script>@d class C {}</script>` and `<script>const = 1;</script>` compiled), and the check for a stale `<const>` read in a `<script>` body was switched off for such a body without a word. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (tsc-server-statement-positions):** On the html target, `mx-tsc` and the editor now report a type error inside a `server` or `client` statement at the token you wrote, where `server` errors were reported at 1:1 as "an MX bug" and `client` statements were not type-checked at all. A `client` statement's own code is now part of the type-check projection, so a `client let`, `client function` or `client const` read in the template has its declared type (no more TS7005/TS7034 under `strict`; a `client var q;` with no initializer is `any` in TypeScript too and is reported at `q`). The compiled page is unchanged: a `client` statement still leaves only `var <names>;`.

- **Fixed (tsc-watch-host-policy-once):** `mx-tsc --watch` now reports host-policy diagnostics (`TS80003`, such as an `mx.target` that belongs to another host) on every build, the first one included, before tsc's summary line. A policy error is counted in the summary and keeps the exit code at 1 until a build no longer has it; a policy warning is printed and not counted. They used to print once, after the first build's summary and outside its count, and never on a rebuild, so a watcher standing on a bad `package.json` could read as clean.

- **Fixed (tsc-watch-misses-mx-errors):** `mx-tsc --watch` reports MX compile errors on every rebuild. It used to print them once, after the first build (and under the first build's "Found 0 errors"), so an MX error introduced while the watcher ran, such as `<effect>` or an unclosed tag, produced "Found 0 errors" and no MX line at all. Each rebuild now prints the MX errors that hold after it, with their fix lines, before tsc's summary, and the summary's count includes them; a fixed error is gone from the next rebuild. A one-shot run with an MX error ends with `mx-tsc: Found N MX error(s) (tsc's own error count does not include MX errors).` when tsc printed its own count line, since tsc counts only its own diagnostics. The language server's quick-fix code actions skip a malformed fix (a `null` entry, a `null` edit, a missing `edits` array) instead of throwing on it.

- **Fixed (tsc-client-server-dual-projection):** The type-check of a `.mx` file now types a `client` name the way the server render sees it: as `undefined`, and not exported. `client let q = 1` with `<div>${q.toFixed(2)}</div>` used to check clean and throw on the server render; it now reports `'q' is possibly 'undefined'` at the read, and a client function or class called in the template is an error too. `import { x } from "./ca.mx"` of a `client export const x` used to pass silently; it now reports TS2614 at the specifier, for a plain, a `static` and a `server` import and for a `.ts` importer, and a `server` or `static` export of the same file stays importable. Inside client code (a handler, a `client` block, a later `client` statement) a client name keeps its declared type, and hover, completions and error positions there are unchanged; a top-level `return` in a `client` block is still reported (TS1108) at the `return`. In the generated TypeScript for tooling, a `client` statement's names are declared `var q: undefined` at module level and its code runs in a function the module calls where the last `client` statement stands, so a use before declaration is still reported; the module that runs is unchanged. Known limits: a `client import` of another module's client export reports TS2614, because the type-check reads that module as the server sees it. A client interface or type alias that names a client value (a class, an enum, a `const` through `typeof`) is checked in the client scope, so a type outside it, such as the page's own `export interface Input`, cannot name that class or enum, and `import type` of such a type from another file does not find it; a client type that names no client value stays at module level and importable. A client `namespace` is declared at module level, where a client value is `undefined`, so a namespace body that reads one reports it. A `client` statement that reads a `static` or `server` name declared after it, but before a later `client` statement, is not reported as used before its declaration. From a template read of a client name, go-to-definition lands on the read, and rename or find-references on the declaration do not include it.

# @mxlang/tsc

`mx-tsc`: real `tsc` with the MX language plugins spliced in through Volar's tsc patches, applied by `runVolarTsc` in this package's `src/index.ts` (Volar's own `runTsc` route does not work under Bun: its native CJS loader bypasses the patched `fs.readFileSync`). Its internals are described in `../typescript-plugin/AGENTS.md`; this file covers only what is specific to this package's tests.

## Tests

From this directory:

```
bunx vitest run --root ../../.. --project @mxlang/tsc
```

Needs `bun install` and `bun run build` first (`dist/` of core, parser, the html target and the plugin). `@mxlang/typescript-plugin`'s `dist` bundles `@mxlang/target-html` (it is not external in its build script), so after editing `packages/targets/html` rebuild the plugin too, or these tests pass on a stale html.

This package's run is slow and sensitive to machine load (TODO `tsc-tests-runtime-2`): the whole project took ~340 s on a busy machine and hit `[vitest-worker]: Timeout calling "onTaskUpdate"`. Run single files with the path filter (`... src/<file>.test.ts`) while iterating.

## The Angular template pass in watch mode (`src/watch-templates.ts`)

`tsc -w` returns from `executeCommandLine` after its first build and rebuilds on its own, so nothing of `index.ts` runs again afterwards: every rebuild needs the template pass of its own. It runs from an interceptor on `process.stdout.write` (`installWatchTemplatePass`), matched on tsc's own watch summary (`Found N errors. Watching for file changes.`): the pass's diagnostics are printed before that line and its errors are counted into it. Only that line is acted on. Under `-b -w` each program's compiles are matched back to a project by root-file overlap (`matchProjects` in `build-templates.ts`), never by path prefix.

The same interception reports the MX compile diagnostics (`compile` in `installWatchTemplatePass`): the plugins' per-file answers, newest generation of plugins that compiled a file deciding (`src/watch-compile.ts`; Volar makes a new plugin set whenever the root files change, and does not re-read an unchanged file, so an older set still holds that file's error). They print before the summary and are counted in it; the first build's go out the same way and are not printed again after it. The host-policy diagnostics (`TS80003`, from `getTargetPolicyDiagnostics`) go the same way (`policy` in `installWatchTemplatePass`, `currentPolicyDiagnostics` in `src/watch-compile.ts`, same newest-generation rule): printed after the MX errors and before the summary on every build, errors counted and exit-code-relevant (`reportWatchPass`), warnings printed and not counted. The after-`runVolarTsc` print is skipped when the interceptor ran. The `package.json` that decides a `.mx` file's host is an input of that file (`src/watch-package-json.ts`, wired in `setup`): the host's `getSourceFile` adds the manifests (the nearest and the next one up, or each directory's up to them, so a nearer one created later counts) to the `packageJsonLocations` of the options object `createProgram` reads back, which TypeScript watches with the watch host's `watchFile` and which starts a rebuild; under `-b -w`, where the solution builder watches only the package-info cache of module resolution, the same manifests are looked up through `getPackageScopeForPath` so they land there. When a manifest's stat stamp changed since a file was handed out, `getSourceFile` returns a new source file object (same text, new `version`), because Volar does not recompile an unchanged object and the builder reuses the semantic diagnostics of an unchanged version; that recompile replaces the file's policy diagnostics (the TS80003 position is recomputed). Under `-w -p` TypeScript's own `canWatchAffectingLocation` refuses a manifest whose path has at most 4 components on POSIX (`/tmp/x/package.json`, `/app/x/package.json`, `/home/me/package.json`; `/workspaces/<name>/package.json` is the exception: 4 components suffice there), so those are not watched; the tests put the project in `<tmp>/<dir>/project` for that reason. `mx.config.*` files also decide a host and are not covered in watch mode. The one-shot `--pretty` line `mx-tsc: Found N MX error(s)` counts TS80003 errors with the compile errors. A one-shot run prints `mx-tsc: Found N MX error(s) (...)` only when tsc printed its own count line (`--pretty`), which cannot include them.

Four test files cover the watch surfaces. Three run their watchers in this process on virtual time (`src/watch-memory.ts`: an in-memory stdout capture, `TSC_WATCHFILE`/`TSC_WATCHDIRECTORY` polling strategies and `vi.useFakeTimers`; no child process, no real fs watcher, no sleeps) — `src/watch-mx-diagnostics.test.ts` (MX compile diagnostics), `src/watch-policy-diagnostics.test.ts` (host policy) and `src/watch-ngmx-rebuild-diagnostics.test.ts` (this pass, plus the localized-summary cases). Where a file's cases share one watcher they run in order, each settling the project for the next; `start()` runs in the describe's `beforeAll`, so `-t` and `.only` on any case work. `src/watch-rebuild-diagnostics.test.ts` (the TypeScript pass) still spawns real watchers: run it one at a time.

## The Angular template cache under `-b` (`src/build-cache.ts`)

A one-shot `-b` run checks the templates of every project of the graph (tsc's up-to-date state knows nothing of templates), which costs one extra program and one Angular checker per project. `checkBuildProjects` in `index.ts` stores each project's answer (`{key, ownedFiles, ngResult}`) in `<tsbuildinfo>.mx-ng.json` and replays it when the key is unchanged. The sidecar sits beside the build info, usually in `outDir`, and holds each `.ng.mx` file's source text (`reports[].source`), so a package that publishes `outDir` excludes `*.mx-ng.json` from its `files`; `-b --clean` does not delete it (the key makes a leftover harmless). The key (`cacheKey`) is SHA-256 over content only, never an mtime: the build info's `fileNames`/`fileInfos` (read-only, after tsc wrote them; tsc hashes a `.ng.mx`'s authored text there, not the lowered text), the tsconfig and its `extends` chain, the `.mx` files' bytes, every manifest and MX config path `packageJsonInputs` and core's `findMxConfig(...).watch` probe (absent ones too), the tag-discovery inputs core's `scanCached` reports per `.mx` file (every candidate tag directory's listing, present or absent, the bytes of each file in it, and the manifests and config files it read, so a nearer tag file created later counts), `resolveCompilerCli`/`resolveTypescript` per package directory, `ts.version`, `toolIdentity()` and the previous project's key, position and claimed files. The chain through the previous key is conservative: `claimed` and `position` carry which earlier project owns an overlapping `.ng.mx`, and the chain makes any change to an earlier cacheable project's inputs a miss for every later project too (an uncacheable project contributes a fixed `uncached:<position>`), so an edit in the first project of a graph re-checks the whole graph once. `toolIdentity()` (computed once per run, only when a project has a build info) hashes this package's bundle (run from source: every non-test `.ts` under `src/`, outside `fixtures*` and dot-directories, where tests write scratch projects, each keyed by its path under `src/`, plus each file a relative import reaches outside `src/`, such as `typescript-plugin/src/tsconfig-paths.ts`, followed through extensionless and `index` specifiers and through those files' own relative imports) and each entry of `TOOL_EXTERNALS`: its entry bytes, its version, its siblings (core's `marko-frontend.cjs`; a missing one hashes as `missing`, so removing it does not turn the cache off), and the installed version and real directory of every package its `dependencies` reach, transitively (Babel and what `@babel/core` brings, the template parser, cosmiconfig: a lockfile bump moves no MX version; one not installed hashes as `missing`); `@angular/compiler` counts by its `package.json` version and realpath. An external that does not resolve makes the run uncacheable. `projectCacheEntry` treats only an unreadable input as uncacheable (an fs errno code, `ENOENT`, `ENOTDIR`, `EISDIR`, `EACCES`, `EPERM`, `ELOOP`, `EMFILE`, `ENFILE`, `ENAMETOOLONG`, `EIO` or `EBUSY`, or `MODULE_NOT_FOUND`; a `SyntaxError` from a malformed JSON input; core's `TranslateError`); any other throw, a Node `ERR_*` error included, is a bug in building the key and is rethrown, so it cannot turn the cache off unseen. A project is uncacheable (`projectCacheEntry` returns `undefined`) without an incremental build info, with a file the key does not cover (only scripts, JSON, `.ng.mx` and plain `.mx`, whose tag discovery is scanned with the Angular target lookup; another host's region file such as `.solid.mx`, an `.astro.mx`, or a dialect's `x.probe.mx` makes the project uncacheable), with an MX config module (`mx.config.ts`/`.js`/...: the modules it imports are not inputs), or with a JSON or YAML MX config whose text contains `$import` (cosmiconfig merges the imported file, which core's `watch` does not list; the text check is conservative), with an `mx.target` or `mx.host` given as a package or path specifier rather than a built-in id (core loads that descriptor module; conservative, a specifier a built-in owns counts too), or with a module the tag scan read (a `.tag.ts` sidecar, an `mx.contracts` module, a dialect module) whose relative import (`from`, `import`, `require`) points outside the hashed tag directories, or whose bare import (a package, a tsconfig path alias) does not resolve from that file or resolves to a real path outside every `node_modules` directory (a linked workspace package, an alias to sources): the imported code is no input. A type-only `import type`/`export type` is erased and ignored; an installed package under `node_modules` falls under the `--force`-after-an-install caveat below. An MX config whose revision failed to load (`findMxConfig(...).error`, an unresolvable `$import` included, where core keeps the previous text or none) is not cacheable either. Nothing is read or stored when tsc's own pass failed or under watch. `mayStore` (pure, unit-tested per clause) refuses a project whose program printed an MX compile or host-policy diagnostic, or when the run has an ambient-types error (the count seen when the project is decided, not per project: an ambient error of this project or an earlier one keeps it from storing; a later project's does not), that had a project-level error, that has `mx.angular.diagnostics: "off"`, or whose compiled set differs from the build info's. `--force` reads nothing and rewrites. A new input of the template answer needs a key field, a `BUILD_CACHE_FORMAT` bump and a row in `src/build-cache.test.ts` (unit rows over temp fixtures, fast lane). The whole-build cases are in `src/build-cache-build.test.ts`, a slow-lane file (`SLOW_LANE_FILES` in `scripts/vitest-lanes.ts`; about a minute of `mx-tsc -b` runs), which prove a hit by a `BuildPassProbe` (in `build-cache.ts`) passed through `runMxTscArgs` to the in-process run (the CLI passes none, so production keeps no counter), not by timing. Its ng-build-refs case is one sequence on one scratch copy with one cold run, each step starting from the state the step before left (shuffle-safe, being one case); it ends with the file's one spawned run, the built `dist/bin.cjs`, which must compute a key and store under it (its tool identity differs from the sources', so it rewrites the sidecar): the bundle reaches `@mxlang/host-angular/descriptor` through CommonJS interop, which wraps its default export (`descriptorOf` unwraps it), and an in-process run cannot see that. That case needs `bun run build` after any edit to `src/`; it fails with that instruction when `dist/bin.cjs` is older than a source file. The cache inherits `tsc -b`'s up-to-date check: when tsc decides by mtime that a project is up to date (after `git checkout`, `cp -p` or a restored CI cache that leaves inputs older than the build info), it rewrites no `fileInfos`, so a stale template answer is replayed exactly as tsc keeps its own stale output for `.ts`. Run `mx-tsc -b --force` after an mtime-preserving restore. Two more inputs are not re-checked on a hit. A hit creates no template program, so an ambient-types error that program would now raise (the host's types package was removed) is not printed. And the key trusts the build info, so a dependency typing change that `tsc -b` does not rebuild for (new `@angular/core` typings under the same compiler-cli) replays the old answer. Run `mx-tsc -b --force` after an install that changes dependencies.

## Dispatch goldens (`src/host-dispatch-golden.test.ts`)

For one fixture directory per row under `src/fixtures/host-dispatch/`, the test records what each tool produces today: language-server diagnostics, the TypeScript plugin's `generated` text, `mappings`, compile and host-policy diagnostics, the Vite transform output, and `mx-tsc`'s output. `mx-tsc` runs once, in process, over `fixtures/host-dispatch/tsconfig.json` (with `--astro`, which is a superset of the extension lists); its output is split per row by path. Goldens are JSON in `src/fixtures/host-dispatch/__golden__/`, paths normalised to `<root>`/`<repo>`, ANSI stripped.

- A refactor of the per-target dispatch must leave the goldens unchanged. A golden that changes is a behaviour change: say so in the PR.
- Regenerate with `-u`: `bunx vitest run --root ../../.. --project @mxlang/tsc src/host-dispatch-golden.test.ts -u`. Without `-u` a missing golden is written on a local run (not under `CI=true`, where it fails) and a differing one fails. Review the diff of every rewritten file.
- Adding a row: create the directory under `fixtures/host-dispatch/`, add its name to `ROWS` in the test, run once. The test also fails when a directory is not in `ROWS`.
- Editing a fixture's `package.json` or sources moves positions in the goldens (policy diagnostics point into `package.json`); regenerate, and run Biome with `--write` on the fixture first so formatting is stable. `bad-package-json` is malformed on purpose and is excluded from Biome in the root `biome.json`.
- Rows the plan changes on purpose, and the known disagreements between tools, are listed in the comment above `ROWS` in the test.
- `bad-package-json` pins that a malformed `package.json` is a `TS80003` warning in every tool and the files beside it compile normally on the default host (no compile diagnostic), the same from the repo root and from this directory. Its policy warning embeds this package's own `package.json` (`mx.host` `html`) as the fallback source: adding or changing an `mx` field there changes that golden.
- `console.warn` output (scan warnings the plugin logs) is not captured in the `mx-tsc` leg; the TypeScript plugin leg records it as `logged`.

## Dialect files (`createDialectLanguagePlugin`)

`mx-tsc` checks a dialect's files, check-only: no JavaScript, no target. `runPatchedTsc` asks `dialectExtensionsOf(argv)` for the extensions the dialects of the `-p`/`-b` projects (every non-flag `-b` argument; the current directory only when none is named) (plus the projects its `references` name, recursively) claim, unioned over the packages below each project root (`dialectExtensionsUnder`; a dialect declared in a workspace package below the tsconfig counts), hands them to `runVolarTsc` as extra supported extensions (so a tsconfig `include` of `**/*.probe` finds them) and puts `@mxlang/typescript-plugin`'s `createDialectLanguagePlugin` **first** in the plugin list (a dialect's `.probe.mx` must not be an MX file). The plugin's virtual code is empty, and its diagnostics come from `@mxlang/targets/dialect-check`'s `checkDialectFile`, which runs `lowerSource`, so the dialect's `tagRules` apply. They print through `reportCompileDiagnostics`: the diagnostic's code in place of `TS80001`/`TS80002`: core's (`a.probe(1,1): error MX_MISSING_ATTRIBUTE: …`) or the dialect's own (`a.probe(1,4): error PROBE_BAD: bad probe`). Every error `lowerSource` reports carries one, so `TS80001` is left for a diagnostic without a code. An `.mx` file prints its code the same way, read from the thrown error's `diagnosticCode` (core's, or the template parser's `MX_PARSE_*`): `page.mx(1,6): error MX_PARSE_MISMATCHED_CLOSING_TAG: …`. `reportCompileDiagnostics` passes the diagnostic's `length` to TypeScript, but `formatDiagnostics` prints no span, so the visible change is the code. `src/diagnostic-code-output.test.ts` pins both the code and the `TS80001` fallback. `src/dialect-files.test.ts` pins the printed lines against the shared probe dialect (`test-fixtures/dialects/probe.ts`).

# @mxlang/preact

## Unreleased

- **Fix, visible emitted-code change (dynamic-tag-return-unit-object-object / dynamic-tag-var-silent-drop, decision 189):** a compiled unit that declares `<return>` now exports the output only; callers that read the pair use `Unit.render(props).value`. No alias. The pair travels through a **render path** — `.render(props)` — decision 155's model with html's `.render` shape adapted to JSX. Before this shape the default export returned the pair itself, so any caller without static knowledge of the unit rendered or mounted the pair object: a dynamic tag (`<${Counter}/>` from the verifier's `tags/counter.mx` with `<return value=input.start + 1/>`, reached directly and through a `.ts` barrel) rendered empty on Preact. A `/var` call site now reads the pair off `.render(props)` (still an ordinary function call, never mounted), and a `/var` on a **dynamic tag** binds through the new `__mxDynamicPair` dispatch (the unit's `.render` when the callee has one, `undefined` and the ordinary render otherwise) — core lets it through via `HostDeclarations.bindsDynamicTagVar`; inside `<for>`/`<if>` it is refused, as for a static returning unit. Same JSX mount semantics for everyone else.
- **Fix (dynamic-tag-var-silent-drop r2):** a dynamic tag that binds `/var` **and** carries tag arguments no longer drops its body: `<${Counter}/n({ start: 1 })>body</>` now renders the body. `__mxDynamicPair` called `render(...payload)` and never passed `content`, so the body thunk landed in the unit's second positional parameter, where nothing read it; it now folds into the call's props object (the key the no-args path reads), and the no-args call keeps its shape. The `/var` statement also no longer stringifies the mapped `payload`/`content` fragments to `[object Object]` — a syntax error in every emitted module that used tag arguments with a `/var`.
- **Fix (dynamic-tag-var-silent-drop, core):** a tag variable a host cannot bind (`/n` on a `.ts` component anywhere) is reported at the `/var` itself, not at the whole tag. Position only; binding and message unchanged.

- **Fix (routed-template-call-namespan):** a discovered tag's call maps its name span, so a type error on it (a missing required prop) lands on the tag name, not at 1:1 marked MX's. A unit that declares `<return>` is called as `name(props)`, which still maps neither the name nor the braces, as for an imported unit. No emitted code changes, only the source map.

- **Fix, behaviour change (unresolved-tags-dir-diagnostic, decision 172):** a tag Marko's lookup resolves to an `.mx` template (a `marko.json` entry) is imported from the path it was found at (`resolveDiscoveredTagModule`), bound as core's `_x` rather than `__mxX`; a `.marko` tag is core's one error, not an import of `./tags/<name>.marko`. The `./tags/<name>.marko` import synthesis in `compile.ts` and `region.ts` is gone.

- **Fix (statement-followup, decision 168):** the error for JSX in a `static`/`export` statement is MX's own message at the `<` (was Babel's "Unterminated regular expression."); a decorated `static class` is accepted again.

- **Fix, behaviour change (statement-tags, decision 168):** statements parse as statements (typed functions, `<T,>`, JSX and atoms in a `static`/`export` line now compile). `server` now fails with a positioned error where it was silently dropped; `client` keeps its error; `class { … }` is a positioned not-supported error. Preact region files behave the same.

- **Fix (jsx-method-shorthand, decision 167):** an attribute method shorthand (`onClick() { … }`) is emitted as the `function` / `async function` expression the compiler printed for it, not an arrow built by a regex over the printed text. That regex split at the last `) {`, so a body holding its own `) {` (`onClick() { if (c) { go() } }`) emitted `() { if (c) => { go(); } }`, which is not JavaScript. A method keeps its own `this` (amends decision 11) and, under `typeCheck`, its type parameters and parameter annotations; a runtime compile erases them as before. The head is unmapped generated text and the body maps token by token to the authored body, as on Solid. Shared emitter: applies to `@mxlang/react` and `@mxlang/hono`. **Behaviour change:** the emitted handler is a function, so `this` is no longer lexical. Render-locked per dialect by `method-attr.test.ts`.

- **Fix (jsx-handler-prop-names, decision 161):** the shared JSX emitter writes a handler prop under the name the host's JSX types declare: Preact `onKeyDown`, `onMouseDown`, `onDblClick`, … (was `onKeydown`, `onMousedown`, `onDblclick`, which the types reject: TS2322 on valid code under `mx-tsc`). New exports `preactEventPropNames`, `honoEventPropNames` from `@mxlang/preact/dialect`, each holding exactly the names its own JSX types declare (checked both ways against the installed `preact` and `hono/jsx` types). A DOM event name outside a dialect's table (`JsxDialect.closedEventPropNames`) is a compile error, never an emitted prop the types reject: `onDoubleClick` on Preact fails (it lowercases to `doubleclick`, which Preact declares no prop for), `on-fullscreenchange` fails on Preact and `on-toggle` on hono. `onGotPointerCapture`/`onLostPointerCapture` are handlers both type sets declare, not capture variants. React is closed the same way (see `@mxlang/react`). The old spelling still bound at run time (Preact lowercases the name), so this changes emitted text, not behaviour; `src/event-names.test.ts` fires keydown/keyup/mousedown/dblclick in jsdom. The type-check-only handler wrapper now ends in `as any`, so the JSX prop no longer reports a second TS2322 beside the mapped TS1360.

- **Fix (native-tag-binding-capture, decision 164 addendum 1):** a registered taglib tag (`tags/row.marko`) that shares its name with an authored import or `<define>` calls the taglib tag through core's binding (`import _row from "./tags/row.marko"`, `<_row …/>`), once, on Preact, React and Hono; it used to alias and call the authored import.

- **Fix (native-tag-binding-capture, decision 164):** a lowercase tag is a native element whatever `import` or `<define>` binding of that name is in scope (no more `__mxDynamic(span, …)` for an imported `span`); also applies to `@mxlang/react` and `@mxlang/hono`. A warning is raised at the tag.

- **Added (preact-region, decision 154):** `.preact.mx`, TSX with MX regions on Preact, is a built-in region file kind (segment `preact`, language id `preactmx`, diagnostic source `preactmx`): `compilePreactRegion` (exported; `targets` defaults to the package's own lookup) is the shared `compileJsxRegion` with Preact's dialect and the new `preactRegionDeclarations`, wired through the descriptor's `fileKinds` with the shared `readJsxCalleeInput` reader. **Behaviour change:** a `*.preact.mx` file stops being a whole-file `.mx`; a region renders what the same markup renders in a whole-file Preact `.mx`. Whole-file output is unchanged.

- **Fix, behaviour change (jsx-define-call-drops-attrs, decision 160):** a `<define>` called with attributes (`<Row n=1/>`) hands the define's first param one object of the attributes, spreads, attribute tags and `content`, as Marko 6.3.51 does (`{}` when the call carries none). It used to emit `Row(undefined)`, which compiled clean and crashed at render. Both `|p|` and `|{ n }|` read it, whole-file and in a `.react.mx` region. A call with tag arguments is unchanged (decision 109); a define with no params still ignores the attributes. **Behaviour change (decision 160 withdraws the per-param name lookup, 4ba13a4ea):** the old call looked each param up by name (`<define/Card|title, head|>` + `<Card title="a"/>` bound `title` to `"a"`); that source now binds `title` to the whole object and `head` is `undefined`, as in Marko, so destructure (`|{ title, head }|`). Core warns at the call tag when a define with 2+ params is called without arguments but with attributes, attribute tags or a body. Render-locked by `define-call-attrs.test.ts`.

- **Changed (jsx-define-call-drops-attrs, decision 160):** the host declares `defineCallPassesAttrs` (whole-file and region), which turns on core's multi-param `<define>` warning. An attribute tag passed to a `<define>` target is emitted untyped: a define's param type depends on inference, so the `Parameters<typeof Row>[0][...]` typing a named component's attribute tags get is not applied.

- **Added (react-region, decision 154):** the shared JSX region engine, `compileJsxRegion` (`@mxlang/preact/region`), which every JSX host wraps for its `.<segment>.mx` file kind, and `readJsxCalleeInput` (`@mxlang/preact/callee-reader`), their one callee reader (new dependency on `@mxlang/parser`). `createJsxDeclarations(name, { region: true })` is the region variant of the reactive-tag errors, naming only the hook in the surrounding component; whole-file messages and output are unchanged.

- **Fix (html-imported-return-tag-object-object):** an imported `.mx` tag that declares `<return>`, called without `/var`, renders its body and drops the value on this host too (the call now carries `returnsValue`, so the shared emitter unwraps `.output`). Render-locked by `imported-return-render.test.ts`.

- **Fix (jsx-textarea-value-content, decision 149):** `<textarea value=x/>` renders the value as escaped content, as Marko 6.3.51 does: `null`/`undefined`/`false`/`true` render nothing, `0` and `""` are kept, a leading newline is doubled for the server, a later `value` beats an earlier spread's, and a spread's `value` yields to a body. An explicit `value` together with body content is the compile error "A textarea cannot have both a value attribute and body content." A runtime-resolved `<${tag} value=…/>` that is a textarea takes `value` as content and rejects `content`. Preact doubles the leading newline only for the server (`typeof document`); see divergences.md. With a spread, an explicit `value` stays in the merged object so the later source wins, as Marko.

- **Fix (jsx-primitive-attr-parity):** primitive attribute values on native elements render as Marko 6.3.51's html output does, on direct, merged and spread paths: `false`/`null`/`undefined` omit (`data-x=false` no longer prints `"false"`), `true` is a bare attribute, `class`/`style` falsy primitives omit, direct `input.checked` is presence-only, and Hono `style=null` no longer throws. Shared normalization in `@mxlang/preact`, reused by react and hono; component props are unchanged.

- **Fix (jsx-text-entities, round 2):** re-emit every decoded C0 control character as a numeric reference so JSX whitespace trimming cannot turn `a&#10;b` into `a b` or drop boundary newlines. Rendered newline/tab regressions are covered; React and Hono share the fix.

- **Fix (marko-parity-trio, `:modifier`):** `<div :foo="y"/>` compiles to the JSX attribute `value:foo={y}`, Marko's own attribute (MX previously rejected it).

- **Fix (jsx-text-entities):** authored `&…` in text is now HTML5-decoded in the emitter and re-emitted as numeric character references, so JSX output equals Marko 6.3.51's browser-decoded text for every input. The decoder is `entities`' spec-exact `decodeHTML` (the tokenizer's "character reference in data" state), covering legacy no-semicolon names (`&copy 2026` → `© 2026`), HTML5-only names (`&check;`), and unterminated numeric references (`&#123`), which the JSX transform's narrower named-entity set used to leave literal. Every JSX-significant or non-ASCII character — including a decoded `&`, carriage returns, and multi-code-point entities, escaped per code point — becomes a `;`-terminated numeric reference the JSX transform always decodes back. `<style>` bodies are exempt: the HTML tokenizer applies no character references in raw-text elements. Adds `entities` 6.0.1 as a dependency. Shared with `@mxlang/react` and `@mxlang/hono`. Pinned by rendered parity tests against Marko + parse5 and by a `@mxlang/typescript-plugin` mapping test.

- **Fix (preact-html-comment-literal-element):** `<html-comment>` is now a positioned compile error — `an HTML comment (<html-comment>) cannot appear in a Preact component: JSX has no comment node…` — instead of silently emitting a literal `<html-comment>` element where Marko renders `<!--…-->`. Shared with `@mxlang/react` and `@mxlang/hono`.

- **Fixed (pr6-s3a-tagtable-fixed):** A custom tag's `ctx.build.element(name)` without a `void` option is now void exactly when an authored `<name>` is: the target's `nativeTags` declares it void, else core's own HTML void elements. It defaulted to `void: false` before, so `ctx.build.element("br")` rendered `<br></br>` on `@mxlang/angular` and `@mxlang/astro` (`@mxlang/html` hid it by re-reading core's void names, which its emitter no longer does). An explicit `void` still wins (review 475 r3, decision 197). A void element built with children, by default or with `{ void: true }`, is now a compile error at the tag ("`<br>` is void and takes no children; pass { void: false } to emit an end tag"): `@mxlang/html` dropped those children silently; `@mxlang/angular` and `@mxlang/astro` emitted `<br>child</br>`; and the JSX hosts (`@mxlang/preact`, `@mxlang/react`, `@mxlang/hono`, `@mxlang/solid`) compiled it to `<br>child</br>` JSX, which React rejects at runtime.

- **Removed (pr6-s3a-tagtable-removed):** A `marko.json` (or `marko-tag.json`) taglib is no longer read (decision 197, PR 6 slice S3a). A tag only a `marko.json` maps (`template`, `renderer`, `tags-dir`) is an unknown tag like any other: `@mxlang/html`'s "Unable to find entry point for custom tag" error, the native element on Preact, React, Hono and Angular. It was imported and called before. With it go `@mxlang/html`'s and `@mxlang/preact`'s `resolveDiscoveredTagModule` implementations; the optional hook stays on `HostDeclarations` for a third-party target. A `tags/x.marko` file is still the decision 172 error, now found by core's own discovery on every host. `parseData` output and the `DataTag`/`DataAttr`/`DataExpr`/`DataImport` types are unchanged (`mesh-syntax.test.ts` passes unchanged).

- **Changed (pr6-s3a-tagtable):** A compile no longer builds `@marko/compiler`'s taglib lookup (decision 197, PR 6 slice S3a): core's own tag table, the target's taglibs over its `nativeTags`, gives the MX front end each tag's shape and tells lowering an element from a tag. It reproduces the lookup's merge for every translator MX builds, pinned against the live lookup (`tag-table.test.ts`). `@mxlang/preact`, `@mxlang/angular`, `@mxlang/solid` and `@mxlang/astro` now depend on `@mxlang/web-elements` and pass its table as their `nativeTags`. A `.<host>.mx` region reads the same table, so `<param>` is a native element in a region as it already was in a whole file. The `typescript-plugin` mapping pass builds core's table instead of Marko's lookup, and so does `@mxlang/core`'s `defaultTag` check (a tag only a `marko.json` maps is not a valid `defaultTag`). A target that declares no `nativeTags` now gets core's own HTML elements as its native layer, in a whole file, a region and the `defaultTag` check alike: the HTML element names and void names core already used, with `pre`'s preserved whitespace and `script`, `style`, `textarea` and `title` read as text. Before, Marko's lookup gave it HTML, SVG and MathML; a third-party target that renders SVG or MathML now passes `@mxlang/web-elements`' `WEB_ELEMENTS`. Lowering reads the same table for which elements are void, so a target's own `nativeTags` decides that in the IR too (it read core's fixed void names before, and dropped the body of an element the target's table did not declare void); `@mxlang/html`'s emitter trusts the IR's `void`. A registered translator-taglib tag with a same-named import or `<define>` in scope calls the module `resolveDiscoveredTagModule` returns for it (decision 164 addendum 1), and that hook's `.marko` answer is the decision 172 error.

- **Removed (pr6-s3b-translator):** Marko's taglib lookup and its cache surface are gone from `@mxlang/core` (decision 197, PR 6 slice S3b). `buildMarkoLookup` and the `Lookup` type are no longer exported: core's own `tagTable(translator, nativeTags)` is the lookup, and its comparison with Marko 5.42.11's lookup is now a frozen fixture (`tag-table.expected.json`) instead of a live call, for the same six translator shapes and every name they hold. `evictTaglibCaches` is removed with the Marko half of the scan cache it cleared. `clearScanCache` and the per-map cache of loaded custom tags are unchanged. `Translator` no longer has a `tagDiscoveryDirs` field, so neither do `createTranslator`'s result or the `translator` objects `@mxlang/target-html` and `@mxlang/host-preact` export. Nothing read the field once `@marko/compiler` stopped running a compile; tags beside a file still reach a compile as `customTags`, found by the integration. `TranslatorOptions.tagDiscoveryDirs` is still accepted, but unread and `@deprecated`. `parseData` output and the `DataTag`/`DataAttr`/`DataExpr`/`DataImport` types are unchanged (`mesh-syntax.test.ts` passes unchanged).

- **Changed (rename-package-families):** Renamed (decision 201, package families): `@mxlang/html` -> `@mxlang/target-html`; `@mxlang/target-registry` -> `@mxlang/targets`, now the umbrella (the registry, the html target's descriptor as `htmlTarget`, and the html target's full entry at `@mxlang/targets/html`); `@mxlang/react` -> `@mxlang/host-react`; `@mxlang/preact` -> `@mxlang/host-preact`; `@mxlang/solid` -> `@mxlang/host-solid`; `@mxlang/hono` -> `@mxlang/host-hono`; `@mxlang/astro` -> `@mxlang/host-astro`; `@mxlang/angular` -> `@mxlang/host-angular`. Imports, emitted runtime imports (`@mxlang/host-solid/...`) and `mx.target` package selection use the new names. The old names are deprecated on the registry at the next publish. `mx-angular build` still treats an output whose header reads `Generated by @mxlang/angular from` as generated, so files built before the rename are rewritten instead of refused. `@mxlang/data` is not renamed: the tree-ir-entry change deletes it (decision 204).

- **Fixed (define-call-trailing-object):** - html, preact, react, hono, solid: a `<define>` called with tag arguments **and** a body or attribute tags now binds the extras the way Marko does: the call appends ONE trailing object (`{ ...attributeTags, content }`) as its next argument, so it lands in the define's first unfilled parameter and every parameter after it reads `undefined` (a rest parameter stays empty). Previously the remaining parameters were filled *by name* from the attribute tags and body, so `<Row(1)><@b>2</@b></Row>` bound `b` to the attribute tag's value and a parameter named `content` received the body renderable; now that parameter receives the whole `{ b: … }` object (destructure it: `|a, { b }|`) and the body arrives under `content` inside the same object. When the tag arguments already fill every parameter, the extras are dropped, as in Marko. The no-argument call is unchanged (one props object into the first parameter). On solid, a rest parameter of a no-argument `<define>` call is no longer padded with `undefined` either.

- **Fixed (lowercase-local-component):** A lowercase tag naming a local binding is now Marko's own error, in core, on every target — same message verbatim, same position (the tag name): `Local variables must be in a [dynamic tag](https://markojs.com/docs/reference/language#dynamic-tags) unless they are PascalCase. Use `<${layout}/>` or rename to `Layout`.` The rule covers every local binding: a default or named `import` (a `.mx` tag module or a `.ts` value alike), a lowercase `<define>`, a `<const>`, a `<for>`/`<define>` tag param, a `static` declaration (`static const layout = 1` then `<layout/>`, plain or destructured), and an `export const`/`function`/`class` declaration. A core taglib name (`<debug>`, `<log>`) keeps its own routing — as in Marko — even when bound: no error and no "native element" warning. A native-element name stays native (silently for a value binding, with the existing warning for a tag binding); a registered custom tag, a taglib tag or a host claim still wins whatever is imported. `_`/`$`-prefixed names follow Marko's message, whose naive capitalization offers "rename to `_row`". Before, the error existed only for a tag binding (a `<define>` or a `.mx` default import) and in core's own wording ("`<layout>` is not a tag here…"), a lowercase **value** import (`import layout from "./layout.ts"` then `<layout/>`) was a silent pass on preact, react, hono, solid and astro (a literal lowercase element was emitted) and only html rejected it, through its own `rejectComponentTag` hook (now removed — core covers it). The `<const>`, `static` and tag-param forms fell to the unknown-tag path at best (html) or passed silently (the JSX hosts); a core taglib name bound by an import drew the local-variable error on the JSX hosts, where Marko compiles the tag. The message and position are measured on the stock parser (`@marko/compiler` 5.42.11 / `marko` 6.4.4): identical for a tag import, a value import, a `static const` local, an `export const` local, a `<const>` and a `<for>` param. The rest of the lowercase-tag rules are unchanged. One boundary, matching the existing import behaviour: a use *before* the `import`/`static`/`export` statement is not covered — bindings register in document order.

- **Changed (dialect-1b):** Dialect routing and MX's config now guard what belongs to MX, to other languages and to the dialect. - A dialect cannot claim, and `mx.extensions` cannot route, `.mx` in any spelling (`.MX`, `.page.Mx`), a host's file kind (`.solid.mx`, `.ng.mx`: the segments the caller's targets declare, which `compileSource` passes in, and `parseFragment` when given its new `targets` option, which every host's region entry passes), or an extension whose last segment is TypeScript's, JavaScript's or Marko's (`.ts`, `.tsx`, `.mts`, `.cts`, `.d.ts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.marko`). Each is an error at `mx.dialect.extensions` or at the `mx.extensions` entry. `.mesh.mx` stays claimable. - MX's config setting `tagRules`, or `tagRules` or `name` under a dialect's id, is an error at its key: those belong to the dialect. A top-level key that is none of MX's keys, no target's or host's settings block and no discovered dialect's id is an `unknown-config-key` error at its key; a `$` key (`$schema`) is JSON metadata and is not checked. - `compileSource` and `parseFragment` parse a dialect's files under the tag rules the dialect states, as `lowerSource` already did; MX's own files keep their target's rules. - An installed dialect whose `mx.dialect.module` is TypeScript is an error saying the module must be JavaScript Node can load, and a `module` written as a package specifier is an error saying it is a file path inside the package. - The reference `syntax/mesh` module states `tagRules: "none"`.

- **Removed (core-drops-name-sugars):** **Breaking:** core has no name sugars. Every form reads as stock Marko reads it, with Marko's errors; a dialect that wants a name sugar claims it through its syntax table. The tag-adjacent shorthand (`<div#a.b>`, `<#a>`, `<.b>`) is unchanged. Readings that change, all visible to a dialect such as Mesh: a `:` in a tag head is part of the name (`<input:email>`, `<uuid:id>`, `<:x>` and concise `entity:Todo` are one tag name each, so on web an unknown custom tag; Angular's `<svg:rect>` passes through as written), and part of a shorthand part (`<div.c:b>` is the class `c:b`, `<div#d:b>` the id `d:b`); an attribute named `:x` is Marko's `value:x` and a bare `:` is `value:`, `:x(…)` is Marko's "Unsupported arguments on the `value:x` attribute."; a spaced `#x` or `.x` in attribute position is `Invalid attribute name` (a host with `acceptsForeignAttrNames`, Angular, keeps `#ref`); a spaced ` :x` or ` .x` after any value, a default value or a single atom included, continues the value as in stock, so `<div x=a :b/>` and `<if=:a :b>` are Marko's "Expected a single expression, but found `:` after it." and `x=a .b` is member access. Removed exports: `sugarTagName` (`@mxlang/core`), `HostDeclarations.claimsAttributeHash` (Angular no longer sets it), and the `":"` value of `MxShorthand.sigil` (`@mxlang/babel`). Removed codes: `MX_SUGAR_ARGUMENTS`, `MX_SUGAR_BOUND`, `MX_SUGAR_DYNAMIC`, `MX_SUGAR_NAME_INVALID`, `MX_SUGAR_NAME_MISSING`, `MX_SUGAR_ON_STATEMENT`, `MX_SECOND_NAME`, `MX_COLON_BEFORE_DYNAMIC` and `MX_SHORTHAND_INVALID`; the "`:x` right after a default value is not supported" error is gone with them. The `Attr.sugar` and `Attr.sugarValueOf` IR fields stay, set by the tag-adjacent shorthand and by a dialect's triggers.

- **Removed (core-drops-atom-lexing):** **Breaking:** core has no atom syntax. `:x` in a `.mx` file is plain JavaScript, as in Marko: `<a b=:x/>`, `<a b=(f(:x))/>`, `${:x}` and the concise `a b=:x` are Marko's "Unexpected token" at the `:`, and `<a b=x::y/>` is "Expected a single expression, but found `:` after it.". `::` is no longer reserved: inside a name it is part of the name, as Marko reads it (`<a::b/>` is the tag `a::b`, `<a x::y=1/>` the attribute `x:` with the modifier `y`). A dialect builds atoms through its triggers: an `expressionTriggers` or `valueTriggers` row whose hook returns a `StringLiteral` marked `extra.mxAtom = { span }`; core records it, splices its string into `Expr.code`, and lowers a whole-value atom to a `static` attribute with `atom`, as before. Removed: the template parser's `onAtom` handler option and its `Atom` event, and the `MxAtom` node type (`@mxlang/babel`); the "`:a` is an atom" misuse errors, the "`::a` is reserved" error and the two hints about the `:` TypeScript owns. Kept: the `Atom` IR kind, `Expr.atoms`, `MxAtomMark`, `extra.mxAtom` and the `type: "atom"` contract shape check.

A top-level `<define>` is unchanged and is visible in every later body. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (html-script-target-support):** `<html-script>` now writes a real `<script>` element on every host, with its attributes and a body that is script text, as stock Marko 6.4.4 does. The html target (`@mxlang/target-html`) dropped every attribute (`<html-script type="module" src="/a.js">` printed a bare `<script>`) and HTML-escaped the body, so `a && b` reached the browser as `a &amp;&amp; b`; it now keeps the attributes (spreads, dynamic values and `nonce=` included, with the shared element rules) and writes the body as Marko does: each `${…}` stringified as in any text, then the joined body escaped for script context (`<script`, `</script` in any case and `<!--` become `\u003C…`), so no value can close the element. Preact, React, Hono and Solid printed a literal `<html-script>` element: they now print `<script>`, with the body through the renderer's raw-HTML prop (`dangerouslySetInnerHTML`, Solid's `innerHTML`) because a JSX renderer HTML-escapes a text child. Astro printed a literal `<html-script>` too: it now prints `<script is:inline … set:html={…}>`, `is:inline` so Astro keeps the element where it is instead of bundling it. Angular's template compiler removes every `<script>` element, so that host now refuses `<html-script>` at the tag with the ways Angular loads a script (`index.html`, the `scripts` array of `angular.json`, the DOM API) instead of emitting an element ngtsc rejects. On Preact, React and Hono a whole-file body is still read as markup: an element, an `<if>` or a comment in it is refused with an error (it would otherwise be silently dropped from the script, so write markup-like text inside a string placeholder), and a body loses its leading and trailing whitespace, because their whole-file compile does not register the raw-text parse option of `<html-script>`; the html target, Solid and Astro keep both, as Marko does.

- **Fixed (jsx-spread-raw-html-prop):** A spread object can no longer inject raw HTML into an element. On Preact, React and Hono, `<div ...input.attrs/>` with `attrs = { dangerouslySetInnerHTML: { __html: "<b>x</b>" } }` (or an `innerHTML` / `outerHTML` string) wrote that markup into the page, and Solid did the same for a spread `innerHTML`; stock Marko 6.4.4 prints these keys as ordinary escaped attributes. The spread helpers now validate those keys like any other attribute and write them as lowercase attributes (`dangerouslysetinnerhtml`, `innerhtml`, `outerhtml`), which no renderer reads as a raw-HTML prop, so the output is the escaped attribute Marko prints and an HTML parser reads the same attribute name. An object value of one of these keys (`{ __html }`) now throws "cannot be a plain object", like every other attribute (Marko prints `[object Object]`). A literal `dangerouslySetInnerHTML=` on a native element or `<html-script>` is now refused at compile time with Marko's message ("`dangerouslySetInnerHTML` is not a valid attribute, did you mean `$!{html}`?"), at the attribute; a component target still receives it as a prop, and `$!{…}` is unchanged. On Solid, a literal `innerHTML=` on a native element or `<html-script>` is refused the same way ("`innerHTML` is not a valid attribute, did you mean `$!{html}`?"), because it is Solid's raw-HTML prop and so wrote raw markup where Marko prints an escaped attribute; a sole `$!{html}` child is the way to write raw HTML, and the "wrap it" hints in the Solid errors for `$!{…}` in a body with tag params now suggest `<div>$!{item}</div>` instead of `<div innerHTML=item/>`. A component target keeps `innerHTML` as an ordinary prop. On Preact, React and Hono a literal `innerHTML=` or `outerHTML=` on a native or custom element is now the same escaped lowercase attribute (`innerhtml`, `outerhtml`) instead of a property write, which wrote markup on a Preact client render. On Solid the spread view also closes the other routes to markup: a spread `outerHTML`, `textContent` and `innerText` are escaped lowercase attributes, `prop:innerHTML` and `prop:outerHTML` are dropped, an object `children` is dropped (the server renderer read `{ t: "<b>" }` as an already-rendered node), and on `<script>` and `<style>` (also a dynamic tag that resolves to one, in any letter case) `children` and the `prop:` text props are dropped too; a literal `prop:innerHTML=` or `prop:outerHTML=` on a native element is a compile error like `innerHTML=`, a literal `textContent=`, `innerText=`, `children=` or `prop:` text prop on `<html-script>` or `<style>` is a compile error, a literal `children=` on any other native element goes through the same view (an object is dropped), and a literal markup prop on a dynamic string tag goes through the view too. The error for an object value of a raw-HTML key now ends with "To write raw HTML, make `$!{html}` the element's only child."

- **Fixed (jsx-dynamic-tag-data-object-element):** A dynamic tag whose value is data no longer hands that data to the renderer as a node. `<${input.x}/>`, `<${input.x}(args)/>` and a template that is only `${input.x}`, with `input.x` set to a plain object from outside the template (JSON from a request, say) now render nothing, as in Marko 6.4.4; `<${input.x}>body</>` still renders `body`, as Marko does. On Hono the browser used to read `{ tag: "img", props: { onerror: "…" } }` as a real `<img onerror>`; on Preact's server renderer an object with a null prototype was read as a vnode the same way; on React a plain object threw. A copy of such data whose prototype was set from a `__proto__` key (`Object.assign({}, JSON.parse(…))`) is data too. A string still gives an element, a component is still called, and what the renderer built (a `hono/jsx` or `hono/jsx/dom` element, a portal, a Preact vnode, a React element) and arrays of them pass through. The check is chosen per host by a new optional `nodeShape` field on the shared emitter's dialect. Preact and Hono tell their own nodes apart by an own `constructor: undefined` and an own `key`/`ref`, which JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not be used as a dynamic tag. Solid's server renderer still writes a `{ t: "<b>x</b>" }` object as markup; that waits on the runtime. The same copy, which used to pass Hono's text-placeholder guard as a class instance and render as an element in the browser, now prints as `[object Object]` there too.

- **Fixed (object-child-text-guard):** On Hono, `${expr}` holding a plain object from outside the template (JSON from a request, say) is now printed as text, `[object Object]` like Marko 6.4.4, instead of being read as an element by `hono/jsx/dom`: a `{ tag: "img", props: { onerror: "…" } }` object used to render a real `<img>` with its event handler and `dangerouslySetInnerHTML` in the browser. This covers a placeholder in a body and also one that is alone in an `<if>`/`<else>` branch, a `<for>` body, a component or render-prop body, `<@catch>` or `<@placeholder>`. An own `toString()` or `valueOf()` is honoured and the result is escaped. What Hono built is left alone: `hono/jsx` elements, nodes from the `hono/jsx/dom` runtime (`jsx`, `createElement`, `cloneElement`, `Fragment`), portals, strings, numbers and arrays of them, and a state update still re-renders the text. The dom runtime's plain node objects are told apart by an own `key` and `ref` that JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not reach a text placeholder. The shared JSX emitter in `@mxlang/host-preact` gained an internal `textObjectGuard` dialect flag that only Hono sets, so Preact, React and Solid output is unchanged. Preact still renders nothing for a plain object in a text placeholder and React still throws, neither reading it as markup; the Preact, React and Hono host pages say so. On Solid's server renderer, a `{ t: "<b>x</b>" }` object in a text placeholder is still written as markup, the same as in hand-written Solid, because the runtime's rendered nodes are unmarked objects of that shape; the Solid host page tells authors to pass only strings, numbers or nodes, and the fix is waiting on the runtime.

- **Fixed (preact-ssr-text-null-proto-vnode):** On Preact, a `${expr}` placeholder whose value is data from outside the template can no longer be read as markup by the server renderer. `<p>${input.x}</p>` with `input.x` set to a null-prototype object that has the fields of a vnode (`type`, `props`, `key`, `ref`; a decoder such as `qs` with `plainObjects` builds these) used to render `<p><img src="x" onerror="alert(1)"></p>` on the server, while the browser rendered `<p></p>`, so hydration disagreed with the server HTML; the same went for an array holding one, and for a placeholder that is the only child of an `<if>`, a `<for>` row or a body. Such data now renders nothing on the server, as it already did in the browser, and a plain object still renders nothing, as before. Strings, numbers, vnodes (`h()`, the jsx runtime, `Fragment`, `cloneElement`, a component's return value), class instances and arrays of them are unchanged. Each non-literal placeholder is now passed through the `__mxRenderable` check the dynamic tag already uses, so the generated code gains that call and one hoisted helper. A vnode is told apart by its own `constructor: undefined`, which JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not reach a text placeholder. The shared emitter gained an internal `textDataGuard` dialect flag that only Preact sets, so apart from the two data guards below, only generated helper text differs. An object whose prototype is an array (JSON can build one through a `__proto__` key and `Object.assign`) no longer passes the class-instance check of the shared `__mxRenderable` and `__mxTextValue` helpers: on a React, Preact or Hono dynamic tag it used to reach the renderer as a node (Preact hydration crashed), and in a Hono text placeholder it used to reach `hono/jsx/dom` as a node and render an element in the browser; it is now dropped, or printed as Marko prints it.

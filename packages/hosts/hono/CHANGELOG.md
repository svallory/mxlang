# @mxlang/hono

## Unreleased

- **Fix, visible emitted-code change (dynamic-tag-return-unit-object-object / dynamic-tag-var-silent-drop):** same as Preact (shared emitter and compiler): a compiled unit that declares `<return>` now exports the output only; callers that read the pair use `Unit.render(props).value`. No alias. The pair moved to a `.render(props)` render path, so a dynamic tag (`<${Counter}/>`, directly or through a `.ts` barrel) renders the body where Hono's string resolver failed on the pair object; `/var` reads the pair off `.render`, and a `/var` on a dynamic tag binds through `__mxDynamicPair` (core's `bindsDynamicTagVar` opt-in), refused inside `<for>`/`<if>`. Also Preact's r2 fix: a dynamic `/var` call with tag arguments renders its body, and the `/var` statement no longer emits `[object Object]`.
- **Fix (dynamic-tag-var-silent-drop, core):** a tag variable a host cannot bind (`/n` on a `.ts` component anywhere) is reported at the `/var` itself, not at the whole tag. Position only; binding and message unchanged.

- **Fix (routed-template-call-namespan):** a discovered tag's call maps its name span, so a type error on it (a missing required prop) lands on the tag name, not at 1:1 marked MX's. Same as Preact (shared emitter). No emitted code changes, only the source map.

- **Fix, behaviour change (unresolved-tags-dir-diagnostic):** a tag Marko's lookup resolves to an `.mx` template (a `marko.json` entry) is imported from the path it was found at (`resolveDiscoveredTagModule`), bound as core's `_x` rather than `__mxX`; a `.marko` tag is core's one error, not an import of `./tags/<name>.marko`.

- **Fix (statement-followup):** the error for JSX in a `static`/`export` statement is MX's own message at the `<` (was Babel's "Unterminated regular expression."); a decorated `static class` is accepted again.

- **Fix, behaviour change (statement-tags):** statements parse as statements (typed functions, `<T,>`, JSX and atoms in a `static`/`export` line now compile). `server` now fails with a positioned error where it was silently dropped; `client` keeps its error; `class { … }` is a positioned not-supported error. Hono region files behave the same.

- **Fix (jsx-method-shorthand):** an attribute method shorthand is emitted as a `function` / `async function` expression, and a body holding `) {` is valid JavaScript again (shared emitter, see `@mxlang/preact`). **Behaviour change:** `this` inside the method is the function's own, not lexical. Render-locked by `method-attr.test.ts`.

- **Fix (jsx-handler-prop-names):** handler props are emitted under hono's declared names: `onKeyDown`, `onMouseDown`, `onDoubleClick` (was `onKeydown`, `onMousedown`, `onDblclick`; the types reject those). `hono/jsx/dom` binds them to the same DOM events (`event-runtime.test.ts`). The table holds only hono's declared names: the authored `onDoubleClick` emits `onDoubleClick` (declared), and a DOM event hono's types declare no handler for (`on-toggle`, `on-search`) is a compile error.

- **Fix (native-tag-binding-capture):** a lowercase tag is a native element whatever `import` or `<define>` binding of that name is in scope (shared emitter, see `@mxlang/preact`). A warning is raised at the tag.

- **Changed (preact-region):** the Bun loader declines `.preact.mx` (Preact's region file kind), as `@mxlang/html`'s does.

- **Added (hono-region):** `.hono.mx` region files: TSX with MX regions, as `.solid.mx` is for Solid. The `hono-jsx` descriptor gains the `hono` file kind (`compileRegion`, `readCalleeInput`, language id `honomx`), and `compileHonoRegion` is exported. A region renders what the same markup renders in a whole-file `.mx`; hooks live in the surrounding component. In a region, `<const>` and module-level MX (`import`, `static`, `export`, `Input`, `<return>`) are errors at the statement, and `<let>`/`<effect>`/`<id>`/`<lifecycle>` name only the hook in the surrounding component (`honoRegionDeclarations`).

- **Changed (hono-region):** **behaviour change:** a `*.hono.mx` file is no longer a whole-file `.mx`; it is a region file, and the Bun loader declines it.

- **Fix, behaviour change (jsx-define-call-drops-attrs):** a `<define>` called with attributes (`<Row n=1/>`) hands the define's first param one object of the attributes, spreads, attribute tags and `content`, as Marko 6.3.51 does (`{}` when the call carries none). It used to emit `Row(undefined)`, which compiled clean and crashed at render. Both `|p|` and `|{ n }|` read it, whole-file and in a `.react.mx` region. A call with tag arguments is unchanged; a define with no params still ignores the attributes. **Behaviour change (the per-param name lookup is withdrawn, 4ba13a4ea):** the old call looked each param up by name (`<define/Card|title, head|>` + `<Card title="a"/>` bound `title` to `"a"`); that source now binds `title` to the whole object and `head` is `undefined`, as in Marko, so destructure (`|{ title, head }|`). Core warns at the call tag when a define with 2+ params is called without arguments but with attributes, attribute tags or a body. Render-locked by `define-call-attrs.test.ts`.

- **Changed (jsx-define-call-drops-attrs):** the host declares `defineCallPassesAttrs` (whole-file and region), which turns on core's multi-param `<define>` warning. An attribute tag passed to a `<define>` target is emitted untyped: a define's param type depends on inference, so the `Parameters<typeof Row>[0][...]` typing a named component's attribute tags get is not applied.

- **Changed (react-region):** the Bun loader declines `.react.mx` (React's region file kind), as `@mxlang/html`'s does.

- **Changed (bridge-host):** the Bun loader's filter is built from its lookup (`mxFilter`), as `@mxlang/html`'s; unchanged with the package's own lookup.

- **Fix (html-imported-return-tag-object-object):** an imported `.mx` tag that declares `<return>`, called without `/var`, renders its body and drops the value on this host too (the call now carries `returnsValue`, so the shared emitter unwraps `.output`). Render-locked by `imported-return-render.test.ts`.

- **Fix (jsx-textarea-value-content):** `<textarea value=x/>` renders the value as escaped content, as Marko 6.3.51 does: `null`/`undefined`/`false`/`true` render nothing, `0` and `""` are kept, a leading newline is doubled for the server, a later `value` beats an earlier spread's, and a spread's `value` yields to a body. An explicit `value` together with body content is the compile error "A textarea cannot have both a value attribute and body content." A runtime-resolved `<${tag} value=…/>` that is a textarea takes `value` as content and rejects `content`. Hono doubles the leading newline only where no `document` exists (`hono/jsx/dom`'s `render` accepts the emitted nodes and must not double); see divergences.md.

- **Fix (jsx-primitive-attr-parity):** primitive attribute values on native elements render as Marko 6.3.51's html output does, on direct, merged and spread paths: `false`/`null`/`undefined` omit (`data-x=false` no longer prints `"false"`), `true` is a bare attribute, `class`/`style` falsy primitives omit, direct `input.checked` is presence-only, and Hono `style=null` no longer throws. Shared normalization in `@mxlang/preact`, reused by react and hono; component props are unchanged.

- **Fix (jsx-text-entities, round 2):** shared JSX emission preserves decoded control references, including newline references at the start/end of text, instead of JSX-trimming or collapsing them. Pinned by real Hono rendering.

- **Fix (marko-parity-trio, `:modifier`):** `<div :foo="y"/>` compiles to the JSX attribute `value:foo={y}`, Marko's own attribute (MX previously rejected it).

- **Fix (jsx-text-entities):** authored entities in text render as Marko 6.3.51's browser-decoded text (`&copy 2026` → `© 2026`, `&check;`, `&lt`, `&#123`), through the shared emitter's HTML5 decode-and-re-emit; see `@mxlang/preact`.

- **Fix (preact-html-comment-literal-element):** `<html-comment>` is now a positioned compile error (JSX has no comment node) instead of silently emitting a literal `<html-comment>` element. See `@mxlang/preact`.

- **Fixed (pr6-s3a-tagtable-fixed):** A custom tag's `ctx.build.element(name)` without a `void` option is now void exactly when an authored `<name>` is: the target's `nativeTags` declares it void, else core's own HTML void elements. It defaulted to `void: false` before, so `ctx.build.element("br")` rendered `<br></br>` on `@mxlang/angular` and `@mxlang/astro` (`@mxlang/html` hid it by re-reading core's void names, which its emitter no longer does). An explicit `void` still wins (review 475 r3). A void element built with children, by default or with `{ void: true }`, is now a compile error at the tag ("`<br>` is void and takes no children; pass { void: false } to emit an end tag"): `@mxlang/html` dropped those children silently; `@mxlang/angular` and `@mxlang/astro` emitted `<br>child</br>`; and the JSX hosts (`@mxlang/preact`, `@mxlang/react`, `@mxlang/hono`, `@mxlang/solid`) compiled it to `<br>child</br>` JSX, which React rejects at runtime.

- **Removed (pr6-s3a-tagtable-removed):** A `marko.json` (or `marko-tag.json`) taglib is no longer read (PR 6 slice S3a). A tag only a `marko.json` maps (`template`, `renderer`, `tags-dir`) is an unknown tag like any other: `@mxlang/html`'s "Unable to find entry point for custom tag" error, the native element on Preact, React, Hono and Angular. It was imported and called before. With it go `@mxlang/html`'s and `@mxlang/preact`'s `resolveDiscoveredTagModule` implementations; the optional hook stays on `HostDeclarations` for a third-party target. A `tags/x.marko` file is still the same error, now found by core's own discovery on every host. `parseData` output and the `DataTag`/`DataAttr`/`DataExpr`/`DataImport` types are unchanged (`mesh-syntax.test.ts` passes unchanged).

- **Changed (rename-package-families):** Renamed (package families): `@mxlang/html` -> `@mxlang/target-html`; `@mxlang/target-registry` -> `@mxlang/targets`, now the umbrella (the registry, the html target's descriptor as `htmlTarget`, and the html target's full entry at `@mxlang/targets/html`); `@mxlang/react` -> `@mxlang/host-react`; `@mxlang/preact` -> `@mxlang/host-preact`; `@mxlang/solid` -> `@mxlang/host-solid`; `@mxlang/hono` -> `@mxlang/host-hono`; `@mxlang/astro` -> `@mxlang/host-astro`; `@mxlang/angular` -> `@mxlang/host-angular`. Imports, emitted runtime imports (`@mxlang/host-solid/...`) and `mx.target` package selection use the new names. The old names are deprecated on the registry at the next publish. `mx-angular build` still treats an output whose header reads `Generated by @mxlang/angular from` as generated, so files built before the rename are rewritten instead of refused. `@mxlang/data` is not renamed: the tree-ir-entry change deletes it.

- **Fixed (define-call-trailing-object):** - html, preact, react, hono, solid: a `<define>` called with tag arguments **and** a body or attribute tags now binds the extras the way Marko does: the call appends ONE trailing object (`{ ...attributeTags, content }`) as its next argument, so it lands in the define's first unfilled parameter and every parameter after it reads `undefined` (a rest parameter stays empty). Previously the remaining parameters were filled *by name* from the attribute tags and body, so `<Row(1)><@b>2</@b></Row>` bound `b` to the attribute tag's value and a parameter named `content` received the body renderable; now that parameter receives the whole `{ b: … }` object (destructure it: `|a, { b }|`) and the body arrives under `content` inside the same object. When the tag arguments already fill every parameter, the extras are dropped, as in Marko. The no-argument call is unchanged (one props object into the first parameter). On solid, a rest parameter of a no-argument `<define>` call is no longer padded with `undefined` either.

- **Fixed (lowercase-local-component):** A lowercase tag naming a local binding is now Marko's own error, in core, on every target — same message verbatim, same position (the tag name): `Local variables must be in a [dynamic tag](https://markojs.com/docs/reference/language#dynamic-tags) unless they are PascalCase. Use `<${layout}/>` or rename to `Layout`.` The rule covers every local binding: a default or named `import` (a `.mx` tag module or a `.ts` value alike), a lowercase `<define>`, a `<const>`, a `<for>`/`<define>` tag param, a `static` declaration (`static const layout = 1` then `<layout/>`, plain or destructured), and an `export const`/`function`/`class` declaration. A core taglib name (`<debug>`, `<log>`) keeps its own routing — as in Marko — even when bound: no error and no "native element" warning. A native-element name stays native (silently for a value binding, with the existing warning for a tag binding); a registered custom tag, a taglib tag or a host claim still wins whatever is imported. `_`/`$`-prefixed names follow Marko's message, whose naive capitalization offers "rename to `_row`". Before, the error existed only for a tag binding (a `<define>` or a `.mx` default import) and in core's own wording ("`<layout>` is not a tag here…"), a lowercase **value** import (`import layout from "./layout.ts"` then `<layout/>`) was a silent pass on preact, react, hono, solid and astro (a literal lowercase element was emitted) and only html rejected it, through its own `rejectComponentTag` hook (now removed — core covers it). The `<const>`, `static` and tag-param forms fell to the unknown-tag path at best (html) or passed silently (the JSX hosts); a core taglib name bound by an import drew the local-variable error on the JSX hosts, where Marko compiles the tag. The message and position are measured on the stock parser (`@marko/compiler` 5.42.11 / `marko` 6.4.4): identical for a tag import, a value import, a `static const` local, an `export const` local, a `<const>` and a `<for>` param. The rest of the lowercase-tag rules are unchanged. One boundary, matching the existing import behaviour: a use *before* the `import`/`static`/`export` statement is not covered — bindings register in document order.

- **Removed (core-drops-name-sugars):** **Breaking:** core has no name sugars. Every form reads as stock Marko reads it, with Marko's errors; a dialect that wants a name sugar claims it through its syntax table. The tag-adjacent shorthand (`<div#a.b>`, `<#a>`, `<.b>`) is unchanged. Readings that change, all visible to a dialect such as Mesh: a `:` in a tag head is part of the name (`<input:email>`, `<uuid:id>`, `<:x>` and concise `entity:Todo` are one tag name each, so on web an unknown custom tag; Angular's `<svg:rect>` passes through as written), and part of a shorthand part (`<div.c:b>` is the class `c:b`, `<div#d:b>` the id `d:b`); an attribute named `:x` is Marko's `value:x` and a bare `:` is `value:`, `:x(…)` is Marko's "Unsupported arguments on the `value:x` attribute."; a spaced `#x` or `.x` in attribute position is `Invalid attribute name` (a host with `acceptsForeignAttrNames`, Angular, keeps `#ref`); a spaced ` :x` or ` .x` after any value, a default value or a single atom included, continues the value as in stock, so `<div x=a :b/>` and `<if=:a :b>` are Marko's "Expected a single expression, but found `:` after it." and `x=a .b` is member access. Removed exports: `sugarTagName` (`@mxlang/core`), `HostDeclarations.claimsAttributeHash` (Angular no longer sets it), and the `":"` value of `MxShorthand.sigil` (`@mxlang/babel`). Removed codes: `MX_SUGAR_ARGUMENTS`, `MX_SUGAR_BOUND`, `MX_SUGAR_DYNAMIC`, `MX_SUGAR_NAME_INVALID`, `MX_SUGAR_NAME_MISSING`, `MX_SUGAR_ON_STATEMENT`, `MX_SECOND_NAME`, `MX_COLON_BEFORE_DYNAMIC` and `MX_SHORTHAND_INVALID`; the "`:x` right after a default value is not supported" error is gone with them. The `Attr.sugar` and `Attr.sugarValueOf` IR fields stay, set by the tag-adjacent shorthand and by a dialect's triggers.

- **Removed (core-drops-atom-lexing):** **Breaking:** core has no atom syntax. `:x` in a `.mx` file is plain JavaScript, as in Marko: `<a b=:x/>`, `<a b=(f(:x))/>`, `${:x}` and the concise `a b=:x` are Marko's "Unexpected token" at the `:`, and `<a b=x::y/>` is "Expected a single expression, but found `:` after it.". `::` is no longer reserved: inside a name it is part of the name, as Marko reads it (`<a::b/>` is the tag `a::b`, `<a x::y=1/>` the attribute `x:` with the modifier `y`). A dialect builds atoms through its triggers: an `expressionTriggers` or `valueTriggers` row whose hook returns a `StringLiteral` marked `extra.mxAtom = { span }`; core records it, splices its string into `Expr.code`, and lowers a whole-value atom to a `static` attribute with `atom`, as before. Removed: the template parser's `onAtom` handler option and its `Atom` event, and the `MxAtom` node type (`@mxlang/babel`); the "`:a` is an atom" misuse errors, the "`::a` is reserved" error and the two hints about the `:` TypeScript owns. Kept: the `Atom` IR kind, `Expr.atoms`, `MxAtomMark`, `extra.mxAtom` and the `type: "atom"` contract shape check.

- **Fixed (jsx-hosts-colon-tag-error):** An undeclared colon tag name such as `<uuid:id/>` is now a compile error on the React, Preact, Hono and Solid hosts, at the tag, instead of an emitted JSX namespace element. A colon is part of the tag name, so the name is one custom tag; with nothing declaring it, the message is `` Unable to find entry point for custom tag `<uuid:id>`. - **Fixed (hosts-colon-astro-rethrow):** An undeclared colon tag in an `.astro.mx` file (`<ns:tag/>`, `<Ns:Tag/>`) is now a compile error at the tag, as in the JSX hosts: Astro used to emit it silently as a namespace element. The fix the error names is now true for every name. It suggests an `mx.tags` `prefix` only when some prefix can produce the name (the name ends in a file stem: `<a:-x/>` takes `prefix: "a:-"`), and for a name no tag file can end (`<uuid:/>`, `<a:b$/>`) it says only to write the name without the colon. The error now carries the end of the name, so an editor underlines all of it. A lowering error inside a region of a `.solid.mx`, `.preact.mx`, `.react.mx` or `.hono.mx` file, and in an `.astro.mx` file, now reaches `mx-tsc` and the TypeScript plugin with its `MX_*` code and its whole range, where it showed `TS80001` and one character. - **Fixed (define-call-rest-trailing-object):** A `<define>` with a rest parameter called with tag arguments and a body or attribute tags now receives the trailing `{ ...attributeTags, content }` object in the rest array, as in Marko, when the arguments already fill every fixed parameter. `|a, ...rest|` called as `<D(1, 2)>x</D>` now reads `rest = [2, { content }]` (and `<D(1, 2, 3)>x</D>` reads `[2, 3, { content }]`), where the object used to be dropped and `rest` was `[2]`. The same holds for a define whose only parameter is `...rest`. A call with no body and no attribute tags still appends nothing, and a rest parameter is still never padded with `undefined`. Defines without a rest parameter are unchanged: when the arguments fill every parameter the extras are dropped.

- **Changed (hosts-unsupported-tag-message):** A tag a host does not support in embedded MX now gets one message on every host: "`<X>` is not supported in embedded MX on <Host>." Before, each host worded the refusal its own way ("`<let>` is Marko reactive state; …", "`<script>` is a Marko client-runtime tag; …", "`<let>` is reactive state and requires a runtime; …" in Astro, and Angular's `<return>` text). The host's existing advice follows as a second sentence when there is one, for example "`<let>` is not supported in embedded MX on Preact. Use Preact's `useState` via `<const/x=useState(0)/>` or in the surrounding module." `<effect>` gets the first sentence alone on every host, with no `<script>` pointer. The code stays `MX_UNSUPPORTED_CONSTRUCT` and the position stays at the tag. Angular's and Astro's `<return>` refusals and Angular's `<try>` fallback in the emitter had no code before; they now carry `MX_UNSUPPORTED_CONSTRUCT`, and `<return>` is positioned at the returned value. This covers every tag the Preact, React, Hono, Solid, Angular and Astro hosts refuse, in whole files and in region files, plus Angular's and Astro's `<return>`; `client` and `server` blocks, `<else>` and `<else-if>` without an `<if>`, and refusals that are not about a tag (dynamic tag names, tag params, type arguments, tag variables) keep their texts. Core adds a third tag disposition, `{ kind: "unsupported", hint? }`, which core words with the new host declaration `hostName` (the display name), and the exported `unsupportedTagMessage(ctx, tag, hint?)` for a refusal a host raises itself after lowering (both `@unstable`). A disposition of kind `error` keeps working with its own `reason`. Tooling that matched the old texts (goldens, expected-error files) needs the new text.

- **Changed (marko-6.4-module-scope-render-names):** Module level code that names something that exists only while the template renders is now a compile error, as in Marko 6.4: a `static`, `server` or `client` block (including the statements of a `static { … }` block) or an `export` statement that references a tag variable (`<let>`, `<const>`, `<define>`, declared anywhere in the file), `input`, `$global` or `$signal`. The error is `MX_RENDER_ONLY_IN_MODULE`, positioned at the name with its end: "`count` exists only while the template renders, so module level code (`static`, `server`, `client` and `export` statements), which runs once as the template loads, cannot reference it. Reference it in the template instead, passing it to module level functions as an argument." It is raised by core, so every host and `lowerSource` report it the same way, where these references used to compile to code that read an unbound name. A module level declaration with the spelling of a tag variable in the template's top level (`static count = 1` beside `<let/count=0/>`) is refused at the declaration, and so is a module level declaration spelled `input` (`static const input = 1`), as in Marko; `$global` and `$signal` may still be declared. A parameter or local of a module function that shadows the name, a property name, a name in a type position, a tag param (`<for|item|>`) and a module binding that shares the spelling of a tag variable only a nested tag declares are not errors. A host that refuses `server` or `client` still reports that refusal first, and the `none` tag rules leave a dialect's statements alone. Move the value into the template and pass it to a module level function as an argument.

- **Changed (static-block-unwrap):** A `static { ... }` block now hoists its statements to module scope with the braces removed, as in Marko: `static { let q = 1 }` declares `q` for the whole module, so the template can read `${q}`, where the braces used to make `q` block-scoped and the read undeclared. Only a body that is exactly one block unwraps (`static { a } { b }` and `static { a };` keep their blocks, one level only: `static {{ a }}` hoists `{ a }`), an empty block (or one holding only comments) hoists nothing but is still a module statement, so a host or region with no module scope refuses it like any other `static`, and a comment after the closing brace is dropped with it. The statements inside keep their text, comments and positions, so an error inside the block still points at its line and column. `server { ... }` hoists the same way on the html target. The render-only name check reads the same block, so a template read of a block binding is fine, and `static { const count = 1 }` beside `<let/count>` is still refused at the declaration. The non-block `static x = 1` form is unchanged. `@mxlang/core` also exports `unwrapStatementBlock`, the one reading of the block form, for hosts that hoist a statement of their own.

- **Fixed (block-import-export-crash):** An `import` or an `export` written inside a `static`, `server` or `client` block no longer fails to compile. `static { import x from "./x" }` used to be refused with `'import' and 'export' may only appear at the top level.` (the block's braces reached the statement check), and `server { export default foo }` crashed the compiler with an internal `undefined is not an object` error. The block's statements are now module-level statements, as in Marko: `static { import x from "./x"; export const z = 1 }` hoists both to the module, exactly as `static import x from "./x"` and `static export const z = 1` do, and in a `client` block the names they bind are declared as `var name;`. An `import` or `export` below the block's own statements (inside a nested block, an `if` or a function body, or in a second block) is still refused at the position of the declaration, with a message that says where an `import` or `export` may go (it used to be Babel's "'import' and 'export' may only appear at the top level."), and a real syntax error, decorator or JSX beside an import in a block is reported at its own position instead of as the import's placement error. Blocks without an `import` or `export` compile as before.

- **Fixed (define-attributes-silently-dropped):** A `<define>` tag's own attributes are no longer dropped. `<define/D a=1 b="s"/>` compiled, and `${D.a}` read `undefined`; Marko makes the attributes properties of the define's value, and MX now does too. On html, preact, react and hono they are own properties of the function a call runs (a spread keeps its place, a repeated name is last-wins, and attributes named `name`, `length`, `caller` or `arguments` work), evaluated where the `<define>` is written and outside its params. A `<let>` written in one (`<define/D a=(count++)/>`) is now refused like in any attribute. A `content` attribute next to a body is dropped, as in Marko (the body is `content`), with the warning `MX_DEFINE_CONTENT_DROPPED` at the attribute; with no body it is an ordinary property. Solid and Angular cannot expose a property on their define (a hoisted function, a template reference) and now refuse a `<define>` with attributes with a positioned error instead of dropping them (a divergence from Marko, listed in `divergences.md`); Astro already refuses `<define>`. A `Define` IR node now carries its `attrs`, so `IR_VERSION` goes from 3 to 4.

- **Fixed (define-in-if-shadows-import):** A `<define>` is now scoped to the body that declares it, as in Marko. A `<define/Foo>` inside an `<if>`, `<else>`, `<for>`, `<try>`, component body or native element used to stay callable for the rest of the file, so a later `<Foo/>` outside it called the define even when `Foo` was also an import (html called the define, Solid hoisted the define and called it), and with no import it compiled instead of reporting an unresolved tag. The `<Foo/>` outside the body now renders the import, or reports "Unable to find entry point for custom tag" when there is none; inside the body the define still wins. A top-level `<define>` is unchanged and is visible in every later body. Solid also keeps a top-level define reachable after a same-name define inside a `<try>` or attribute-tag body (the outer call used to land on the inner function).

- **Fixed (hono-fragment-drops-sole-zero):** A lone placeholder whose value is `0` or `NaN` no longer renders nothing on Hono. Hono's `Fragment` drops a sole falsy child, so `<if=input.a>${input.x}</if>` with `x` = 0 rendered an empty string where the html target renders `0`, `<for|i| of=[0,1]>${i}</for>` rendered `1` instead of `01`, and a define call or dynamic tag body `${0}` rendered empty. The emitter now writes a `{null}` child after a fragment's only value child, in the component's own return, a `<for>` row, the body of a define call or dynamic tag, a `<define>`, the body of a `<try>` (also under `<@placeholder>`), a lone-placeholder `<@catch>` body, and the fragment around a `.<host>.mx` region. A null child renders nothing on every JSX host, so the Preact and React output is unchanged apart from that extra child, the way an attribute-tag body was already written.

- **Fixed (jsx-define-call-in-if-invalid-tsx):** A `<define>` call that is the only child of an `<if>`, `<else-if>` or `<else>` branch no longer emits invalid TSX. `<define/Foo><p>inner</p></define><if=input.a><Foo/></if>` compiled to `input.a ? {Foo()} : null`, which Bun and Babel refuse to parse (`ts.createSourceFile` reports nothing, so a parse-only check missed it); it now compiles to `input.a ? Foo() : null`. The same braces broke a dynamic tag (`<${X}/>`), a nested `<if>` and a `<for>` that is the only child of a branch, the `<@placeholder>` fallback, and an `<@item>` attribute-tag body that is a define call or dynamic tag (`item={{Foo()}}`, `Box({ "item": {Foo()} })`). A define call that is the only child of a `<@catch|e|>`, a `<@item|x|>` attribute-tag body or a `<Tag|item|>` render-prop body compiled to `(e) => {Foo()}`, a block body that returns nothing, so the fallback or row rendered empty; it now returns the call.

- **Fixed (jsx-sole-placeholder-body-renders-source):** A body whose only child is a `${expr}` placeholder no longer renders the expression's source text, and an empty body no longer renders the word "null". `<for|i| of=input.l>${i}</for>` compiled to `<__mxFragment key={i}>i</__mxFragment>` and rendered `ii` for a two-item list where the html target renders `12`; the same happened for `<for in>`, `<for from to>`, the body of a `<define>` call (`<Box>${input.y}</Box>` rendered `<b>input.y</b>`, and `<Box|n|>${n}</Box>` rendered `n`) and the body of a dynamic tag (`<${X}>${input.y}</>`). An empty `<for>` body (or one holding only a comment) rendered `null` once per row. A lone placeholder in these positions is now a JSX expression child (`{i}`), and an empty body is empty. A placeholder in an expression position (a ternary arm, a render-prop arrow body) is unchanged.

- **Changed (render-write-other-bindings):** Writing a binding the template does not write is now a compile error, as it is in Marko, with three new codes. Each message gives the rule and the fix and sits on the assignment or update with its end (a `for...of` or `for...in` on the loop's left side). `MX_READONLY_BINDING_WRITE`: a `<const>` and a `<for>` parameter (value, index and key) are never written, whether the write is while the template renders, in an event handler or callback, or in a `<script>` body; a `<define>` parameter bound as a plain name (`|a|`) is refused the same way; a name bound through an object pattern (`<const/{ a }=…/>`, `<for|{ a }|…>`, `<define/D|{ a }|>`) is written through its object, so it is refused only while the template renders. `MX_LET_WRITE_BEFORE_DECLARATION`: a `<let>` is written only below its declaration, in a placeholder, a handler or a `<script>` body alike, counting a `<let>` later in the same block or after it in an enclosing one. `MX_LET_LOOP_ASSIGNMENT`: a `for...of` or `for...in` cannot assign to a `<let>`, also inside a handler. A parameter or local of the same spelling still shadows the binding. The `<const>`, `<for>`, `<define>` and `<let>`-position rules apply on every target, so a template that wrote one of these now fails on Preact, React, Hono, Solid, Angular and Astro too (for example `<const/x=1/>` with `<button onClick() { x = 2 }/>` compiled to `onClick={function () { x = 2; }}` on Preact, React and Hono before). A target that refuses `<let>` itself still reports a `<let>` written above its declaration first, as `MX_LET_WRITE_BEFORE_DECLARATION`. The render write of a `<let>` (`MX_LET_WRITE_IN_RENDER`) is unchanged and stays on the html default policy. Solid now reports a write to a `<for>` parameter with the core message, so its "computed from its bounds" wording for a stepped range is no longer shown for a render write; its own refusals remain for what core does not reach. Not covered: a `<let>` or `<const>` written from a sibling block or above its declaration (for `<const>`), a name bound through an array pattern, the parameters of other tags, and a `<script>` body that does not parse. Before, all of these compiled without a message.

- **Changed (static-decorator-refused):** A decorator in a module statement is now a positioned compile error, as in Marko, whose parser has no decorators plugin. `static @d() class C {}`, `server @d() class C {}`, `client @d() class C {}` and a decorated class member (`static class C { @d m() {} }`, a property, an accessor or a parameter) compiled before and are refused now with `MX_INVALID_STATEMENT`, on every target. The error sits on the first `@` and its span covers that decorator; the same holds for `static { @d class C {} }`, `export @d class C {}` and a class expression. The message says what to do: move the decorated class to a `.ts` module and import it, or apply the decorator as a plain function call. A class with no decorator is unchanged.

- **Fixed (block-export-default-refused):** A default export in a `static`, `server` or `client` statement (`export default <value>`, `export default function`, `export default class`, `export { x as default }`, `export { default } from "…"`, `export { a as default } from "…"`, `export * as default from "…"`, in a block or without one) is a compile error at the export, `MX_INVALID_STATEMENT`, with a message that says a template is already its own default export and to use a named export instead. It used to compile to a module with two default exports that does not load, and `mx-tsc` reported TS2528 at 1:1. A type-only default (`export default interface I {}`) is erased and still compiles. Also, an `export { q }` or `export { q as other }` in its own `static`, `server` or `client` statement may name a binding an earlier statement or import declares (`static const q = 1;` then `static export { q };`, or a plain top-level `export { q }` after an `import`); it was refused with "Export 'q' is not defined." and printed a Babel warning, and stock Marko compiles it.

- **Fixed (host-component-body-as-jsx):** The body of a tag that resolves to a host component now reaches the component exactly as hand-written JSX would pass it. `import { Fragment } from "hono/jsx"` then `<Fragment>${input.count}</Fragment>` used to wrap the body in a fragment of MX's own with a `{null}` sibling, so a component received a fragment element instead of its children, and on Hono a `Fragment` rendered `0` where `<Fragment>{0}</Fragment>`, written by hand, renders nothing. The `content` function the emitter writes for such a call now returns what `<Tag>…</Tag>` would pass as `children`: the bare value for a lone placeholder, the string for text, the element for an element and the array of children for several, and the render prop of a call with tag params returns its body the way `(n) => n` does. A binding imported from a module that is not an MX or Marko template, or a local whose value cannot be proven, is a host component; MX's own fragments (an `<if>` branch, a `<for>` row, a define call, a dynamic tag written as `<${expr}>`, a positional call and an attribute-tag body) keep their `{null}` sibling. A dynamic tag whose binding is absent at run time still renders its body on its own, now through a closed fragment, so a lone `0` still renders on Hono.

- **Changed (script-body-syntax-check):** A `<script>` body that does not parse is now a compile error, `MX_INVALID_STATEMENT`, positioned at the syntax error, as in Marko. Before, the html target emitted none of the body and so accepted any text (`<script>@d class C {}</script>` and `<script>const = 1;</script>` compiled), and the check for a stale `<const>` read in a `<script>` body was switched off for such a body without a word. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (html-script-target-support):** `<html-script>` now writes a real `<script>` element on every host, with its attributes and a body that is script text, as stock Marko 6.4.4 does. The html target (`@mxlang/target-html`) dropped every attribute (`<html-script type="module" src="/a.js">` printed a bare `<script>`) and HTML-escaped the body, so `a && b` reached the browser as `a &amp;&amp; b`; it now keeps the attributes (spreads, dynamic values and `nonce=` included, with the shared element rules) and writes the body as Marko does: each `${…}` stringified as in any text, then the joined body escaped for script context (`<script`, `</script` in any case and `<!--` become `\u003C…`), so no value can close the element. Preact, React, Hono and Solid printed a literal `<html-script>` element: they now print `<script>`, with the body through the renderer's raw-HTML prop (`dangerouslySetInnerHTML`, Solid's `innerHTML`) because a JSX renderer HTML-escapes a text child. Astro printed a literal `<html-script>` too: it now prints `<script is:inline … set:html={…}>`, `is:inline` so Astro keeps the element where it is instead of bundling it. Angular's template compiler removes every `<script>` element, so that host now refuses `<html-script>` at the tag with the ways Angular loads a script (`index.html`, the `scripts` array of `angular.json`, the DOM API) instead of emitting an element ngtsc rejects. No host invents a `nonce`: Marko reads one from `$global.cspNonce`, which an MX render does not have, so the author's own `nonce=` is the only source. On Preact, React and Hono a whole-file body is still read as markup: an element, an `<if>` or a comment in it is refused with an error (it would otherwise be silently dropped from the script, so write markup-like text inside a string placeholder), and a body loses its leading and trailing whitespace, because their whole-file compile does not register the raw-text parse option of `<html-script>`; the html target, Solid and Astro keep both, as Marko does.

- **Fixed (jsx-spread-raw-html-prop):** A spread object can no longer inject raw HTML into an element. On Preact, React and Hono, `<div ...input.attrs/>` with `attrs = { dangerouslySetInnerHTML: { __html: "<b>x</b>" } }` (or an `innerHTML` / `outerHTML` string) wrote that markup into the page, and Solid did the same for a spread `innerHTML`; stock Marko 6.4.4 prints these keys as ordinary escaped attributes. The spread helpers now validate those keys like any other attribute and write them as lowercase attributes (`dangerouslysetinnerhtml`, `innerhtml`, `outerhtml`), which no renderer reads as a raw-HTML prop, so the output is the escaped attribute Marko prints and an HTML parser reads the same attribute name. An object value of one of these keys (`{ __html }`) now throws "cannot be a plain object", like every other attribute (Marko prints `[object Object]`). A literal `dangerouslySetInnerHTML=` on a native element or `<html-script>` is now refused at compile time with Marko's message ("`dangerouslySetInnerHTML` is not a valid attribute, did you mean `$!{html}`?"), at the attribute; a component target still receives it as a prop, and `$!{…}` is unchanged. On Solid, a literal `innerHTML=` on a native element or `<html-script>` is refused the same way ("`innerHTML` is not a valid attribute, did you mean `$!{html}`?"), because it is Solid's raw-HTML prop and so wrote raw markup where Marko prints an escaped attribute; a sole `$!{html}` child is the way to write raw HTML, and the "wrap it" hints in the Solid errors for `$!{…}` in a body with tag params now suggest `<div>$!{item}</div>` instead of `<div innerHTML=item/>`. A component target keeps `innerHTML` as an ordinary prop. On Preact, React and Hono a literal `innerHTML=` or `outerHTML=` on a native or custom element is now the same escaped lowercase attribute (`innerhtml`, `outerhtml`) instead of a property write, which wrote markup on a Preact client render. On Solid the spread view also closes the other routes to markup: a spread `outerHTML`, `textContent` and `innerText` are escaped lowercase attributes, `prop:innerHTML` and `prop:outerHTML` are dropped, an object `children` is dropped (the server renderer read `{ t: "<b>" }` as an already-rendered node), and on `<script>` and `<style>` (also a dynamic tag that resolves to one, in any letter case) `children` and the `prop:` text props are dropped too; a literal `prop:innerHTML=` or `prop:outerHTML=` on a native element is a compile error like `innerHTML=`, a literal `textContent=`, `innerText=`, `children=` or `prop:` text prop on `<html-script>` or `<style>` is a compile error, a literal `children=` on any other native element goes through the same view (an object is dropped), and a literal markup prop on a dynamic string tag goes through the view too. The error for an object value of a raw-HTML key now ends with "To write raw HTML, make `$!{html}` the element's only child."

- **Fixed (jsx-dynamic-tag-data-object-element):** A dynamic tag whose value is data no longer hands that data to the renderer as a node. `<${input.x}/>`, `<${input.x}(args)/>` and a template that is only `${input.x}`, with `input.x` set to a plain object from outside the template (JSON from a request, say) now render nothing, as in Marko 6.4.4; `<${input.x}>body</>` still renders `body`, as Marko does. On Hono the browser used to read `{ tag: "img", props: { onerror: "…" } }` as a real `<img onerror>`; on Preact's server renderer an object with a null prototype was read as a vnode the same way; on React a plain object threw. A copy of such data whose prototype was set from a `__proto__` key (`Object.assign({}, JSON.parse(…))`) is data too. A string still gives an element, a component is still called, and what the renderer built (a `hono/jsx` or `hono/jsx/dom` element, a portal, a Preact vnode, a React element) and arrays of them pass through. The check is chosen per host by a new optional `nodeShape` field on the shared emitter's dialect. Preact and Hono tell their own nodes apart by an own `constructor: undefined` and an own `key`/`ref`, which JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not be used as a dynamic tag. Solid's server renderer still writes a `{ t: "<b>x</b>" }` object as markup; that waits on the runtime. The same copy, which used to pass Hono's text-placeholder guard as a class instance and render as an element in the browser, now prints as `[object Object]` there too.

- **Fixed (object-child-text-guard):** On Hono, `${expr}` holding a plain object from outside the template (JSON from a request, say) is now printed as text, `[object Object]` like Marko 6.4.4, instead of being read as an element by `hono/jsx/dom`: a `{ tag: "img", props: { onerror: "…" } }` object used to render a real `<img>` with its event handler and `dangerouslySetInnerHTML` in the browser. This covers a placeholder in a body and also one that is alone in an `<if>`/`<else>` branch, a `<for>` body, a component or render-prop body, `<@catch>` or `<@placeholder>`. An own `toString()` or `valueOf()` is honoured and the result is escaped. What Hono built is left alone: `hono/jsx` elements, nodes from the `hono/jsx/dom` runtime (`jsx`, `createElement`, `cloneElement`, `Fragment`), portals, strings, numbers and arrays of them, and a state update still re-renders the text. The dom runtime's plain node objects are told apart by an own `key` and `ref` that JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not reach a text placeholder. The shared JSX emitter in `@mxlang/host-preact` gained an internal `textObjectGuard` dialect flag that only Hono sets, so Preact, React and Solid output is unchanged. Preact still renders nothing for a plain object in a text placeholder and React still throws, neither reading it as markup; the Preact, React and Hono host pages say so. On Solid's server renderer, a `{ t: "<b>x</b>" }` object in a text placeholder is still written as markup, the same as in hand-written Solid, because the runtime's rendered nodes are unmarked objects of that shape; the Solid host page tells authors to pass only strings, numbers or nodes, and the fix is waiting on the runtime.

- **Fixed (preact-ssr-text-null-proto-vnode):** On Preact, a `${expr}` placeholder whose value is data from outside the template can no longer be read as markup by the server renderer. `<p>${input.x}</p>` with `input.x` set to a null-prototype object that has the fields of a vnode (`type`, `props`, `key`, `ref`; a decoder such as `qs` with `plainObjects` builds these) used to render `<p><img src="x" onerror="alert(1)"></p>` on the server, while the browser rendered `<p></p>`, so hydration disagreed with the server HTML; the same went for an array holding one, and for a placeholder that is the only child of an `<if>`, a `<for>` row or a body. Such data now renders nothing on the server, as it already did in the browser, and a plain object still renders nothing, as before. Strings, numbers, vnodes (`h()`, the jsx runtime, `Fragment`, `cloneElement`, a component's return value), class instances and arrays of them are unchanged. Each non-literal placeholder is now passed through the `__mxRenderable` check the dynamic tag already uses, so the generated code gains that call and one hoisted helper. A vnode is told apart by its own `constructor: undefined`, which JSON cannot carry; data decoded by a library that keeps `undefined` (`devalue`, `superjson`, `structuredClone`) can imitate one and must not reach a text placeholder. The shared emitter gained an internal `textDataGuard` dialect flag that only Preact sets, so apart from the two data guards below, only generated helper text differs. An object whose prototype is an array (JSON can build one through a `__proto__` key and `Object.assign`) no longer passes the class-instance check of the shared `__mxRenderable` and `__mxTextValue` helpers: on a React, Preact or Hono dynamic tag it used to reach the renderer as a node (Preact hydration crashed), and in a Hono text placeholder it used to reach `hono/jsx/dom` as a node and render an element in the browser; it is now dropped, or printed as Marko prints it.

Component, class/style, controlled and framework-only props keep their existing contracts. Nested event/style prefix hints are corrected through the shared JSX emitter.

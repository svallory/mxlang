# Changelog

## 0.1.0-alpha.36 — 2026-10-19

- **Fixed (attribute-args-refusal):** React, Preact, Hono, Solid and Angular reject attribute argument lists such as `onClick(v)=fn` at the attribute where Marko refuses them, instead of silently dropping the arguments. `<define>` and `<const>` retain Marko's acceptance and dropped arguments; builtin, host-tag and region module-statement errors keep their existing precedence. Write `onClick=fn` instead; method shorthand remains subject to the host's existing callable-value policy. Hosts opt in through the generic `attributeArgs: "refuse"` declaration; core's default IR lowering still retains attribute arguments, including dialect expressions.

## 0.1.0-alpha.35 — 2026-10-19

- **Fixed (define-dynamic-tag-read-solid-angular):** `<${D}/>` of a `<define>` now renders the define on Solid and Angular, as Marko 6.4.4 does, where it emitted a name nothing declares (Solid: `D` at module scope, while the define is hoisted under a generated name) or a template reference bound to `ngComponentOutlet` (Angular). Solid points the dynamic tag at the hoisted function, including inside a conditional target (`<${c ? D : "span"}/>`); a loop param or another declaration named like the define still shadows it. Angular renders a bare define through `ngTemplateOutlet` and lowers `c ? D : Other`, `c || D`, `c && D` and `c ?? D` to `@if`/`@else`, each operand by what it names; attributes on the tag reach only the component operands, as `<D n=3/>` drops them. A define read any other way in the tag name (`f(D)`) and a define with params are a positioned error that names the fix. A define declared after its read is unchanged on both hosts (Marko refuses it too).

- **Fix (dynamic-tag-var-silent-drop, core):** a tag variable a host cannot bind (`/n` on a dynamic tag — Solid does not set `bindsDynamicTagVar`) is reported at the `/var` itself, not at the whole tag: `<div>\n  <${C}/n/>\n</div>` fails at line 2, column 8 (the `/n`), where the refusal used to sit at the tag. Message and outcome unchanged (the refusal stands); position only.

- **Fix (routed-template-call-namespan):** a discovered tag's call maps its name span, so a type error on it (a missing required prop) lands on the tag name, not at 1:1 marked MX's. No emitted code changes, only the source map.

- **Fix (solid-method-shorthand):** an attribute method is emitted as written: a method shorthand (`onClick() { … }`) as the `function` expression the compiler printed for it (`function (e) { … }`, `async function () { … }`, `function <T>(e: T) { … }`), and an authored `function` expression or arrow unchanged. The method used to be turned into an arrow by a regex that split at the last `) {`, so `onClick() { if (c) { go() } }` compiled to `() { if (c) => { go(); } }`, which is not JavaScript. A named function lost its binding as an arrow, and a generic method was invalid TSX. The method's body is now mapped token by token against the authored body (`Expr.bodySpan`/`bodySource`), so a TypeScript error inside it, async, generic or nested, reports at its authored column; its printed head stays unmapped. A `<for in>` comma-expression source is parenthesized, so it stays one argument to `Object.entries`. The oracle's `counter` twin (dom) records the function-vs-arrow form as a divergence.

- **Fix (native-tag-binding-capture):** a module-scope import named like a native element no longer turns that element into `<Dynamic>`; it stays native. A warning is raised at the tag (without the binding's position).
- **Added (bridge-host):** `appendSolidBuiltinImport` (moved from `@mxlang/typescript-plugin`) is Solid's `completeTypecheckModule` on the `.solid.mx` file kind, behind the descriptor's lazy `require`; also exported. Output unchanged.

- **Changed (solid-rename):** the Solid file kind's `languageIds` are now `["solidmx", "solid"]` (was `["solidmx", "SolidMX"]`): Zed derives its LSP language id from the lowercased language name, and its language is now `Solid`. The `solidmx` id, `compileSolidMx` and the `.solid.mx` suffix are unchanged.

- **Fix (jsx-textarea-value-content):** `<textarea value=x/>` renders the value as escaped content, as Marko 6.3.51 does: `null`/`undefined`/`false`/`true` render nothing, `0` and `""` are kept, a leading newline is doubled for the server, a later `value` beats an earlier spread's, and a spread's `value` yields to a body. An explicit `value` together with body content is the compile error "A textarea cannot have both a value attribute and body content." A runtime-resolved `<${tag} value=…/>` that is a textarea takes `value` as content and rejects `content`. Solid doubles under `isServer`, for a runtime-resolved `<${tag} value=…/>` (a `value` attribute, a spread or the args object) too, through `__mxTextareaDynValue`/`__mxTextareaDynSpread`, which leave every non-textarea target and the client render untouched. A runtime-resolved `<${tag} value=…>body</>` whose tag is `textarea` throws Marko's dynamic-textarea content error.

- **Fix (solid-astro-angular-primitive-attr-parity):** a dynamic native `class` and the `class`/`style` keys of a native spread now render as Marko does (falsy primitive omitted, `true` printed as `"true"`) instead of Solid's always-present `class=""`: `class=expr` lowers to a `__mxClassProp(...)` prop spread and `__mxAttrSpread` filters falsy `class`/`style` keys. `<input checked=expr>` without a spread is presence only (`0`, `"x"` set it). Component props, static attributes and object/array `class` are unchanged. A direct `style=expr` non-object stays a compile error.

- **Fix (solid-stepped-range-not-reactive):** a stepped `<for from= to=|until= step=>` now follows its reactive bounds like an unstepped range. The row value was a `const` inside the `<Repeat>` callback, which Solid never re-runs, so `from=base() to=base()+4 step=2` kept rendering `10, 12, 14` after `setBase(20)`. `from` and `step` are evaluated once per (re)render of the loop (Marko 6.3.51 evaluates its `_for_to(to, from, step, …)` head once), bound to constants in an IIFE around the `<Repeat>` unless both are literals; reads of the row param expand to `(__mxFrom) + __mxIndex * (__mxStep)`, so every read in one row agrees even for an impure bound, and `to`/`until` still follow signals through the count prop. A change to a non-literal `from` or `step` recreates the stepped rows (aligned with the unstepped range, which also rebuilds when `from` changes), while a change to `to`/`until` grows or shrinks them in place. A write to a stepped row value now fails with a stepped-specific message. Executed jsdom regressions for each bound; SSR output and unstepped ranges are unchanged.

- **Test (html-imported-return-tag-object-object):** `imported-return-render.test.ts` renders an imported `.mx` tag that declares `<return>`, called without `/var`, through Solid SSR. No emitter change: Solid hands the value back through a callback prop, so the markup already rendered.

- **Fix (solid-object-attr-value-silent):** a plain-object (or null-prototype, function, symbol) value on a dynamic native attribute now throws Marko's `The `data-x` attribute cannot be a plain object (it would render as `[object Object]`).` at render, on SSR and DOM output. Unknown-typed dynamic attributes compile to `__mxAttrValue(...)` and native-element spreads to a lazy validating Proxy (`__mxAttrSpread`); string-valued, class/style/ref/children, `on:`/`use:`/`prop:`/`attr:`/`bool:` and component attributes compile as before. `innerHTML`, `textContent`, `classList`, `:foo` and string-target dynamic tags are validated too. Oracle rows `attrs` and `todos` are recorded divergences.

- **Fix (jsx-text-entities, round 2; supersedes the earlier parity claim below):** browser-only decoding is correct for intrinsic-element templates, **not** for component/control-flow text. Such bodies now HTML5-decode with `entities@6.0.1` (including surrogate references → U+FFFD) and use a lazy build-conditioned escape: escaped HTML in SSR, decoded text nodes in the DOM build. `<if>`/`<else>`, `<for>`, fragments, component children and `<try>` no longer turn authored `&lt;b&gt;` into live markup or double-decode `&amp;copy;`. Real `renderToString` and jsdom DOM tests check text and element structure against live Marko/parse5 evidence. Intrinsic templates and attributes retain their existing behavior.

- **Fix (marko-parity-trio, `:modifier`):** `<div :foo="y"/>` compiles to `value:foo={y}`, which both Solid 2 backends lower to `setAttribute(el, "value:foo", …)`; MX previously rejected the form as a malformed namespaced attribute.

- **Fix (jsx-text-entities):** verified at parity, no decode change. Solid's pipeline already applies Marko's own model to authored `&…`: `@solidjs/babel-plugin` passes JSX text through unaltered, and the SSR string (or the DOM template, which the browser parses with full HTML5 rules) carries the authored spelling to the browser, so legacy no-semicolon names (`&copy 2026`), HTML5-only names (`&check;`), unterminated numeric references (`&#123`), and surrogate references all render exactly as Marko 6.3.51's browser parse — unlike the Preact/React/Hono JSX transforms, which decode only `;`-terminated numeric references and the HTML4 named set and now compensate in the emitter. Probed case-by-case against Marko + parse5; the emitter comment now documents the deliberate passthrough (the stale TODO is removed).

- **Fix (preact-html-comment-literal-element):** `<html-comment>` is now a positioned compile error — `an HTML comment (<html-comment>) cannot appear in a Solid component: JSX has no comment node…` — instead of silently emitting a literal `<html-comment>` element where Marko renders `<!--…-->`.

- **Fixed (jsx-host-script-refusal-first):** On a host that does not support `<script>` (Preact, React, Hono, Solid, Angular, Astro), the host refusal is now the only error for the tag. A `<script>` body that does not parse, a head the tag has no use for or a `${...}` placeholder in the body was reported first, so the fix led to the refusal next. Hosts that support `<script>` report the same errors as before.

Text children now escape `<`, `>`, `{`, and `}` as numeric character references, which JSX decodes back to the original characters, so rendered text equals Marko 6.3.51's; authored entities decode the same as in a browser only for `;`-terminated numeric references and the HTML4 named set — HTML5-only names and unterminated legacy forms stay literal (known divergence, tracked separately). ### Test: a real client (DOM) render harness for live `<for>` updates (solid-client-render-harness)

New `src/client-render.test.ts`: every prior render test in this package (`ssr-render.test.ts`) proves the emitted `<For>`/`<Repeat>` binding renders the right shape once, server-side, through Solid's SSR codegen — none of them mount a component and mutate a live signal. This file compiles the same MX `<for>` fragments through Solid's *client* (DOM) codegen instead, mounts them into a real `jsdom` document (a Bun subprocess, `--conditions=browser` forced — `@solidjs/web`'s package exports branch on a `worker`/`browser`/`deno`/`node` condition key and Bun's default `node` condition otherwise silently resolves the SSR build), writes a same-key row replacement to the backing signal, and asserts the live DOM re-renders — including that a surviving row keeps its own DOM node identity (a stamped `data-mx-node-id`, since a real DOM node cannot cross the subprocess boundary) and reacts live to a further value-only change on that same row — across all four `<for>` keying modes (`by="id"`, `by=(fn)`, unkeyed `of=`, and `in=`). New devDependency: `jsdom@30.1.1` (exact-pinned; bumps the transitive `vitest` peer's own optional `jsdom` from 28.1.0 to 30.1.1, otherwise unaffected). `happy-dom` was tried first and rejected: it throws inside `@solidjs/web`'s own `insertExpression` on the very first client render of a template with a reactive text child (a real incompatibility with Solid 2's DOM codegen, not a config gap) — measured directly, not assumed. Confirmed regression-detecting by locally reverting `@mxlang/core`'s `rewriteAccessorReads` (rebuilding core's `dist/` to pick up the change — a stale `dist/` fails this silently, see this package's own CLAUDE.md) and observing three of the four tests crash inside `@solidjs/signals`, then restoring it.

### Fix: a whole-file unit's `/var` declares `let n: any;`, not a bare `let n;` (tag-var-type-from-return)

Firstmate's ruling (2026-09-28), filed from PR #159 round 2, option C: the value bound from a `<return>` unit's `$mxReturn={...}` callback prop cannot be typed as the `<return>` expression's real type without changing the emitted runtime JS — TypeScript's `typeof` only accepts an identifier, never an arbitrary expression, and the expression can depend on the unit's own body locals, so no type-only declaration beside the component can name it either. `compileSolidUnit` now declares the binding `let n: any;` explicitly instead of a bare `let n;`, which additionally reported `noImplicitAny`'s own TS7005 at every read — unrelated noise, now silenced. The bound value's type is still `any`, a known Solid-only limitation (documented in the spec's `/var` section and this package's AGENTS.md), unlike html/preact/react/hono, which already infer the real type through a `const n = temp.value;` binding. Pinned by a regression test naming the limitation, so a future fix (MX 2's per-callback-scope statement position) flips the assertion.

### Feat: `compileSolidUnit` types a whole-file component's props (solid-whole-file-prop-typing)

`compileSolidUnit` now emits the author's `export interface Input` and annotates the component parameter (`export default function Card(input: Input)`), the same shape as `@mxlang/html` and `@mxlang/preact`, so a caller's `<Card title=1/>` against `title: string` is TS2322 through the TypeScript plugin, `mx-tsc` and the editor. A unit with no `Input` gets `export interface Input {}`; a unit declaring `<return>` widens the parameter with the `$mxReturn` callback prop; an `AttrTag` in `Input` gets `import type { AttrTag } from "@mxlang/solid"`. **The output is now TSX carrying types, so it needs a TypeScript-aware step**: the vite path already has one (`@mxlang/vite-plugin` gives whole-file units a `.tsx` id, `@solidjs/compiler` parses TypeScript and passes the types through, vite strips them). The old "Solid's compiler has no TypeScript frontend" premise was wrong. The custom-tags oracle harness now loads compiled Solid units as `.tsx`.

  into the surrounding module. After hoisting, the `<define>`
  call shapes (no arguments, arguments, attribute tags, arguments plus
  content and attribute tags) apply on Solid too, through a plain
  function-call expression at the call site (`{$mx_DefineRowN(...)}`)
  rather than a JSX tag — JSX has no positional-call syntax, so this
  differs from every other `Component` target on this host, which prints
  an ordinary `<Tag .../>` element.

  Two constructs a hoisted `<define>` cannot express, both reported as a
  positioned error rather than silently wrong code:

  - **Nested inside `<if>`/`<for>`/an attribute tag/another `<define>`.**
    Only a direct top-level child of the region hoists; module scope has no
    per-row or per-branch scope for a nested one to close over.
  - **Closing over a value local to the region** — a binding from the
    surrounding TypeScript function the region lives in (a signal from
    `createSignal`, a prop). A hoisted `<define>` becomes a real
    module-scope function and can only reference its own params, another
    top-level `<define>`'s name, and the module's own imports.

  See `packages/hosts/solid/AGENTS.md` and
  `apps/docs/docs/specification.md` §5.4 for the full contract, and the new
  `fixtures/define-hoist` oracle fixture (recorded as a documented
  `divergences.md` entry: MX's gensym'd function names can never byte-match
  a hand-written twin's natural names, verified semantically identical
  otherwise).

- An unresolved capitalized tag is now a compile error, matching Marko.
  `isComponent` (`emitter.ts`) was a bare `/^[A-Z]/` test
  with no resolvability check — any unresolvable capitalized tag
  (`<TotallyUndefined/>`, or a self-recursive `<define>` before its own
  name is registered) silently lowered as an ordinary component call and
  printed a bare JSX reference to a binding nothing declares, a runtime
  `ReferenceError` rather than a positioned MX error. It now returns `true`
  only when the name genuinely resolves: through the surrounding
  TypeScript module's own top-level value bindings (an import or a
  top-level `const`/`function`/`class`, type-only bindings excluded), or
  one of Solid's own JSX built-ins (`Show`, `For`, `Switch`, `Match`,
  `Repeat`, `Errored`, `Loading`, `Dynamic`). Everything else reaches
  Marko's own positioned error (`` Unable to find entry point for custom
  tag `<Name>`. ``, verified against `@marko/compiler` 5.42.5 /
  `marko@6.3.51`) through a new `rejectUnknownTag` declaration.

  **Behavior change**: a `.solid.mx` template (or whole-file `.mx`
  resolved to the Solid host) that previously compiled to a dangling JSX
  reference for an unresolvable capitalized tag now fails to compile
  instead, naming the tag. A whole-file `.mx` compiled to Solid still
  cannot use an authored `import` for such a name (a separate,
  pre-existing limitation — `compileSolidMx` rejects any module-level
  statement outside a real `.solid.mx` region); a registered custom tag is
  the resolution route available there.

### Breaking

- Attribute tags now follow the callee-declared `AttrTag` cardinality and
  shape. Solid renderables are reusable accessors: `() => JSX`, or
  `(...params) => () => JSX` for parameterized tags. Data-shaped tags carry
  that accessor under `content`; arrays, control flow, attributes and nested
  tags are preserved.

- **Fixed (block-import-export-crash):** An `import` or an `export` written inside a `static`, `server` or `client` block no longer fails to compile. `static { import x from "./x" }` used to be refused with `'import' and 'export' may only appear at the top level.` (the block's braces reached the statement check), and `server { export default foo }` crashed the compiler with an internal `undefined is not an object` error. The block's statements are now module-level statements, as in Marko: `static { import x from "./x"; export const z = 1 }` hoists both to the module, exactly as `static import x from "./x"` and `static export const z = 1` do, and in a `client` block the names they bind are declared as `var name;`. An `import` or `export` below the block's own statements (inside a nested block, an `if` or a function body, or in a second block) is still refused at the position of the declaration, with a message that says where an `import` or `export` may go (it used to be Babel's "'import' and 'export' may only appear at the top level."), and a real syntax error, decorator or JSX beside an import in a block is reported at its own position instead of as the import's placement error. Blocks without an `import` or `export` compile as before.

- **Fixed (define-attributes-silently-dropped):** A `<define>` tag's own attributes are no longer dropped. `<define/D a=1 b="s"/>` compiled, and `${D.a}` read `undefined`; Marko makes the attributes properties of the define's value, and MX now does too. On html, preact, react and hono they are own properties of the function a call runs (a spread keeps its place, a repeated name is last-wins, and attributes named `name`, `length`, `caller` or `arguments` work), evaluated where the `<define>` is written and outside its params. A `<let>` written in one (`<define/D a=(count++)/>`) is now refused like in any attribute. A `content` attribute next to a body is dropped, as in Marko (the body is `content`), with the warning `MX_DEFINE_CONTENT_DROPPED` at the attribute; with no body it is an ordinary property. Solid and Angular cannot expose a property on their define (a hoisted function, a template reference) and now refuse a `<define>` with attributes with a positioned error instead of dropping them (a divergence from Marko, listed in `divergences.md`); Astro already refuses `<define>`. A `Define` IR node now carries its `attrs`, so `IR_VERSION` goes from 3 to 4.

- **Fixed (define-in-if-shadows-import):** A `<define>` is now scoped to the body that declares it, as in Marko. A `<define/Foo>` inside an `<if>`, `<else>`, `<for>`, `<try>`, component body or native element used to stay callable for the rest of the file, so a later `<Foo/>` outside it called the define even when `Foo` was also an import (html called the define, Solid hoisted the define and called it), and with no import it compiled instead of reporting an unresolved tag. The `<Foo/>` outside the body now renders the import, or reports "Unable to find entry point for custom tag" when there is none; inside the body the define still wins. A top-level `<define>` is unchanged and is visible in every later body. Solid also keeps a top-level define reachable after a same-name define inside a `<try>` or attribute-tag body (the outer call used to land on the inner function).

- **Changed (render-write-other-bindings):** Writing a binding the template does not write is now a compile error, as it is in Marko, with three new codes. Each message gives the rule and the fix and sits on the assignment or update with its end (a `for...of` or `for...in` on the loop's left side). `MX_READONLY_BINDING_WRITE`: a `<const>` and a `<for>` parameter (value, index and key) are never written, whether the write is while the template renders, in an event handler or callback, or in a `<script>` body; a `<define>` parameter bound as a plain name (`|a|`) is refused the same way; a name bound through an object pattern (`<const/{ a }=…/>`, `<for|{ a }|…>`, `<define/D|{ a }|>`) is written through its object, so it is refused only while the template renders. `MX_LET_WRITE_BEFORE_DECLARATION`: a `<let>` is written only below its declaration, in a placeholder, a handler or a `<script>` body alike, counting a `<let>` later in the same block or after it in an enclosing one. `MX_LET_LOOP_ASSIGNMENT`: a `for...of` or `for...in` cannot assign to a `<let>`, also inside a handler. A parameter or local of the same spelling still shadows the binding. The `<const>`, `<for>`, `<define>` and `<let>`-position rules apply on every target, so a template that wrote one of these now fails on Preact, React, Hono, Solid, Angular and Astro too (for example `<const/x=1/>` with `<button onClick() { x = 2 }/>` compiled to `onClick={function () { x = 2; }}` on Preact, React and Hono before). A target that refuses `<let>` itself still reports a `<let>` written above its declaration first, as `MX_LET_WRITE_BEFORE_DECLARATION`. The render write of a `<let>` (`MX_LET_WRITE_IN_RENDER`) is unchanged and stays on the html default policy. Solid now reports a write to a `<for>` parameter with the core message, so its "computed from its bounds" wording for a stepped range is no longer shown for a render write; its own refusals remain for what core does not reach. Not covered: a `<let>` or `<const>` written from a sibling block or above its declaration (for `<const>`), a name bound through an array pattern, the parameters of other tags, and a `<script>` body that does not parse. Before, all of these compiled without a message.

- **Changed (static-decorator-refused):** A decorator in a module statement is now a positioned compile error, as in Marko, whose parser has no decorators plugin. `static @d() class C {}`, `server @d() class C {}`, `client @d() class C {}` and a decorated class member (`static class C { @d m() {} }`, a property, an accessor or a parameter) compiled before and are refused now with `MX_INVALID_STATEMENT`, on every target. The error sits on the first `@` and its span covers that decorator; the same holds for `static { @d class C {} }`, `export @d class C {}` and a class expression. The message says what to do: move the decorated class to a `.ts` module and import it, or apply the decorator as a plain function call. A class with no decorator is unchanged.

- **Fixed (typescript-plugin-hoisted-code-offset):** In a whole-file `.mx` page, a diagnostic on a `static` statement is reported after the keyword. The statement's code was located by searching from the start of the statement, so `static a` mapped `a` onto the `a` inside `static` itself (and `static s`, `static t`, `static i`, `static c` onto the matching letter of the keyword), putting the diagnostic and hover two to five characters into the keyword. The search now starts after `static` and the whitespace that follows it, so the block form `static { let a = 1 }` also maps to its statements. The same fix applies to a Solid page, whose statement mappings `@mxlang/host-solid` records itself. For a target that both returns a source map and records its own mappings, a recorded mapping now wins wherever the two overlap in the generated text.

- **Fixed (block-export-default-refused):** A default export in a `static`, `server` or `client` statement (`export default <value>`, `export default function`, `export default class`, `export { x as default }`, `export { default } from "…"`, `export { a as default } from "…"`, `export * as default from "…"`, in a block or without one) is a compile error at the export, `MX_INVALID_STATEMENT`, with a message that says a template is already its own default export and to use a named export instead. It used to compile to a module with two default exports that does not load, and `mx-tsc` reported TS2528 at 1:1. A type-only default (`export default interface I {}`) is erased and still compiles. Also, an `export { q }` or `export { q as other }` in its own `static`, `server` or `client` statement may name a binding an earlier statement or import declares (`static const q = 1;` then `static export { q };`, or a plain top-level `export { q }` after an `import`); it was refused with "Export 'q' is not defined." and printed a Babel warning, and stock Marko compiles it.

- **Fixed (conformance-shorthand-id-placeholder):** `lowerSource` lowers a shorthand `id` or `class` with a placeholder (`<div#a${x}/>`, `<div#${x}-a/>`, `<div.a${x}.b/>`, concise `div.a${x}`) instead of refusing it with "a shorthand id with a placeholder is not supported in a data file". The value is the template literal (or, for several class words, the array) core builds over the word, and its `span` is the authored word run after the sigil, so `code` is not the source sliced by `span` (a static `.a.b` already works this way). A shorthand class beside a `class` attribute (`<div.a${x} class="b"/>`) is still refused. Solid now compiles a shorthand class array that mixes a static word and a placeholder (`<div.b.a${y}/>`, `<div.a.${y}/>`); it used to refuse them with "`.class` shorthand combined with a non-string `class` value".

- **Changed (script-body-syntax-check):** A `<script>` body that does not parse is now a compile error, `MX_INVALID_STATEMENT`, positioned at the syntax error, as in Marko. Before, the html target emitted none of the body and so accepted any text (`<script>@d class C {}</script>` and `<script>const = 1;</script>` compiled), and the check for a stale `<const>` read in a `<script>` body was switched off for such a body without a word. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (html-script-target-support):** `<html-script>` now writes a real `<script>` element on every host, with its attributes and a body that is script text, as stock Marko 6.4.4 does. The html target (`@mxlang/target-html`) dropped every attribute (`<html-script type="module" src="/a.js">` printed a bare `<script>`) and HTML-escaped the body, so `a && b` reached the browser as `a &amp;&amp; b`; it now keeps the attributes (spreads, dynamic values and `nonce=` included, with the shared element rules) and writes the body as Marko does: each `${…}` stringified as in any text, then the joined body escaped for script context (`<script`, `</script` in any case and `<!--` become `\u003C…`), so no value can close the element. Preact, React, Hono and Solid printed a literal `<html-script>` element: they now print `<script>`, with the body through the renderer's raw-HTML prop (`dangerouslySetInnerHTML`, Solid's `innerHTML`) because a JSX renderer HTML-escapes a text child. Astro printed a literal `<html-script>` too: it now prints `<script is:inline … set:html={…}>`, `is:inline` so Astro keeps the element where it is instead of bundling it. Angular's template compiler removes every `<script>` element, so that host now refuses `<html-script>` at the tag with the ways Angular loads a script (`index.html`, the `scripts` array of `angular.json`, the DOM API) instead of emitting an element ngtsc rejects. No host invents a `nonce`: Marko reads one from `$global.cspNonce`, which an MX render does not have, so the author's own `nonce=` is the only source. On Preact, React and Hono a whole-file body is still read as markup: an element, an `<if>` or a comment in it is refused with an error (it would otherwise be silently dropped from the script, so write markup-like text inside a string placeholder), and a body loses its leading and trailing whitespace, because their whole-file compile does not register the raw-text parse option of `<html-script>`; the html target, Solid and Astro keep both, as Marko does.

- **Fixed (jsx-spread-raw-html-prop):** A spread object can no longer inject raw HTML into an element. On Preact, React and Hono, `<div ...input.attrs/>` with `attrs = { dangerouslySetInnerHTML: { __html: "<b>x</b>" } }` (or an `innerHTML` / `outerHTML` string) wrote that markup into the page, and Solid did the same for a spread `innerHTML`; stock Marko 6.4.4 prints these keys as ordinary escaped attributes. The spread helpers now validate those keys like any other attribute and write them as lowercase attributes (`dangerouslysetinnerhtml`, `innerhtml`, `outerhtml`), which no renderer reads as a raw-HTML prop, so the output is the escaped attribute Marko prints and an HTML parser reads the same attribute name. An object value of one of these keys (`{ __html }`) now throws "cannot be a plain object", like every other attribute (Marko prints `[object Object]`). A literal `dangerouslySetInnerHTML=` on a native element or `<html-script>` is now refused at compile time with Marko's message ("`dangerouslySetInnerHTML` is not a valid attribute, did you mean `$!{html}`?"), at the attribute; a component target still receives it as a prop, and `$!{…}` is unchanged. On Solid, a literal `innerHTML=` on a native element or `<html-script>` is refused the same way ("`innerHTML` is not a valid attribute, did you mean `$!{html}`?"), because it is Solid's raw-HTML prop and so wrote raw markup where Marko prints an escaped attribute; a sole `$!{html}` child is the way to write raw HTML, and the "wrap it" hints in the Solid errors for `$!{…}` in a body with tag params now suggest `<div>$!{item}</div>` instead of `<div innerHTML=item/>`. A component target keeps `innerHTML` as an ordinary prop. On Preact, React and Hono a literal `innerHTML=` or `outerHTML=` on a native or custom element is now the same escaped lowercase attribute (`innerhtml`, `outerhtml`) instead of a property write, which wrote markup on a Preact client render. On Solid the spread view also closes the other routes to markup: a spread `outerHTML`, `textContent` and `innerText` are escaped lowercase attributes, `prop:innerHTML` and `prop:outerHTML` are dropped, an object `children` is dropped (the server renderer read `{ t: "<b>" }` as an already-rendered node), and on `<script>` and `<style>` (also a dynamic tag that resolves to one, in any letter case) `children` and the `prop:` text props are dropped too; a literal `prop:innerHTML=` or `prop:outerHTML=` on a native element is a compile error like `innerHTML=`, a literal `textContent=`, `innerText=`, `children=` or `prop:` text prop on `<html-script>` or `<style>` is a compile error, a literal `children=` on any other native element goes through the same view (an object is dropped), and a literal markup prop on a dynamic string tag goes through the view too. The error for an object value of a raw-HTML key now ends with "To write raw HTML, make `$!{html}` the element's only child."

- **Fixed (solid-shorthand-class-with-class-attr):** A shorthand class that has a placeholder after a static word (`<div.a.${y} class="c"/>`, `<div.b.a${y} class="c"/>`) now merges with a string or object-literal `class=` on Solid instead of being refused with the "combine shorthand with a string class" error. It renders the same class string as the other hosts and stock Marko: the shorthand parts first, then `class=`, one space apart. A shorthand with a static word still refuses any other `class=`: an identifier, a call, a ternary, a template literal, or an array.

- **Fixed (define-attributes-lowering-solid-angular):** A `<define>` with attributes (`<define/D a=1/>`, `${D.a}`) compiles on Solid and Angular and renders what Marko 6.4.4 does, where both used to refuse it. Static, dynamic and boolean attributes and a spread become properties of `D`, evaluated once where the define is written, with any number of defines, a define with params, a define that reads its own attributes in its body (Angular), and a define inside a `<for>` or an `<if>` (Angular). On Solid the siblings after the define read the attributes through a memoized `<Show>` (literal attributes read as `D.<attribute>` are inlined; a whole-value read of `D` takes the `<Show>` path so `D` keeps one identity), so they stay reactive and are evaluated once; on Angular the attributes are a `@let` beside the template reference. A define that has attributes and a body can only be read as `D.<attribute>` on both: `D.content` and any other whole-value use of `D` (`D`, `(D).content`, `D[key]`, `<${D}/>`) is a positioned error at the read, as is a bound attribute (`a:=x`). On Solid a define inside a `<for>`/`<if>` body, and a define whose body reads another define's dynamic attribute or its own attribute, stay refused (every define is hoisted there).

- **Fixed (solid-shorthand-class-any-class-attr):** A tag-shorthand class now merges with any `class=` value on Solid, as it does in Marko and on the other hosts. `<div.a class=y/>`, `<div.a.${x} class=y/>` and concise `div.a class=y` used to stop with "combine shorthand with a string class or use class={...}" unless `y` was a string or an object literal; they now compile to `class={["a", y]}` and render the shorthand first, then the value, joined by a single space. Objects, arrays (nested ones included), numbers, `true`, calls and ternaries all work, and `null`, `undefined`, `false` and `0` add nothing, so `<div.a class=null/>` renders `class="a"`. On a native element an array `class` (merged with a shorthand or written as `class=["a", y]`) is now joined into one string the way Marko joins it, where Solid used to flatten it: `0` printed, `true` was dropped, a repeated word collapsed, a number sorted ahead of the shorthand and a later `{k: false}` removed an earlier `"k"`. A component still receives the array. The error is gone.

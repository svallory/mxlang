# Changelog

- **Fix (dynamic-tag-var-silent-drop, core):** a tag variable a host cannot bind (`/n` on a call whose `/var` core refuses) is reported at the `/var` itself, not at the whole tag — on `.astro.mx`, a refusal at the line's start moved from column 0 to the `/var`'s column (e.g. `4:0` → `4:9`). Message and outcome unchanged (the refusal stands); position only.

- **Fix (routed-template-call-namespan):** a discovered tag's call maps its name span, so a type error on it (a missing required prop) lands on the tag name, not at 1:1 marked MX's. No emitted code changes, only the source map.

- **Fix (astro-isolated-install-ts-resolution):** under an isolated install (bun workspaces, pnpm) a project that lists only `@mxlang/astro` could not resolve the bare `@mxlang/html` that a compiled `.mx` module imports in `mx-tsc --astro` and the TypeScript plugin (the language server does not type-check); the TS2307 sat on unmapped generated text and was dropped, so `escape`, `createOut` and `Out` silently became `any` (a non-`Out` sink passed to `Unit.render(input, sink)` was accepted). The type-check projection now imports them from `@mxlang/astro/typecheck`, a declarations-only subpath (`export * from "@mxlang/html"`, so it cannot drift from what the emitter imports) that resolves from the project (`html`'s `compile` takes `runtimeFrom`; the astro descriptor sets it only for `typeCheck` compiles). Runtime and build output are unchanged: compiled modules still import `@mxlang/html`, resolved by `mxHtmlResolve`. No tsconfig `paths` needed.

- **Fix (native-tag-binding-capture, decision 164):** a frontmatter-imported lowercase name no longer rejects a same-named native element (`<span>` with `import { span }`): it stays a native element, with a warning at the tag.
- **Fix (astro-mx-custom-tag-tsx):** a discovered custom tag called from `.astro.mx` was shipped as a literal `<$mx_Badge1 />` element with no diagnostic: Astro treats a tag whose name is not upper-case-led as an HTML element, and core's binding is `$`-led. The host now binds it as `Mx_Badge1` (checked against core's bindings and the author's own identifiers), and the type-check projection parses without a stand-in. The `/var` hint now names the tag file's own path. Core and other hosts are unchanged.

- **Fix (render-consumers, `@mxlang/html` resolution):** the integration resolves `@mxlang/html` (and subpaths such as `@mxlang/html/runtime`) for the `.mx` modules it compiles, from its own dependency (`mxHtmlResolve`, `src/html-resolve.ts`). Under an isolated install, a project that lists only `@mxlang/astro` (as the install line says) failed `astro build` with "Rolldown failed to resolve import @mxlang/html" from every page. `examples/astro-static` no longer needs the package listed. Bundler only; the type-check side is the entry above.
- **Added (render-consumers):** `@mxlang/astro/runtime` exports `createOut` and the `Out` type (a re-export of `@mxlang/html/runtime`), so a fence calling `Unit.render(input, createOut())` needs no second package. The `/var`-in-`.astro.mx` hint and the README example import it from there. A subpath and not the main entry: the main entry is the integration, build-time code that does not load inside the SSR bundle.
- **Tests (render-consumers):** the `--astro` type surface is pinned behaviourally: a mistyped `Counter.render(...)` in an `.astro` fence and a mistyped dynamic-tag `/var` are reported under `mx-tsc --astro`, not only in golden text.

- **Fix (render-consumers, decision 155):** the renderer calls the unit's default export unchanged (`(input) => string`); the dead `{ output }` unwrap is gone and the `Symbol.for("mx.component")` brand check stays. The Astro type surface keeps `render` visible on the default export, so `Unit.render(...)` and `/var` type under `mx-tsc --astro` instead of falling to an unmapped, silently dropped TS2339. The `/var`-in-`.astro.mx` error hint now shows `X.render({ ... }, createOut())`; it still showed the pre-decision-155 `const { value } = X(...)`. The page-wrapper tail match accepts the typed default export.

- **Fix (render-sink, decision 155):** the page wrapper (`wrapAsPage`) moves the compiled module's `NAME.render = __mxRender;` line along with the rename to `__mxRenderPage`. Without that, an `@mxlang/html` module from decision 155 would reference a removed binding when it loaded.

- **Fix (solid-astro-angular-primitive-attr-parity, decision 149):** dynamic native attributes and spread keys in `.astro.mx` go through `__mxAttrOut`, so primitives render as Marko does: `false` omitted and `true` bare on data/aria/title/value, falsy `class`/`style` omitted and `true` printed as `"true"`, and Astro's boolean-attribute names present for everything but null/undefined/false (presence only, see divergences.md). Static attributes are unchanged.

- **Fix (astro-html-comment-literal-element):** `<html-comment>` lowers to a real `<!--…-->` instead of a literal `<html-comment>` element (with `${x}` left as `{input.x}`). It matches Marko 6.3.51: only `>` is escaped, falsy values render nothing except `0`, an all-placeholder comment that renders empty is `<!-- -->`, and a value that renders as `[object Object]` throws, as Marko's debug build does (optimized Marko prints it). A nested `<!-- -->` is kept as text with its `>` escaped. `<textarea ...x set:html=…/>` is refused like every other element.

- **Fix (astro-textarea-value-content):** `<textarea value=x/>` renders the value as escaped content, as Marko does, instead of a `value` attribute on an empty textarea. A spread's `value` is split out at render time, a spread's `value` yields to a body, `value` with a body is a build error, and a textarea body is raw text (a literal `<` no longer crashes the Astro compiler). Dynamic tags stay unsupported on this host.

- **Test (html-imported-return-tag-object-object):** `imported-return-render.test.ts` renders an `.astro.mx` page that imports a `.mx` tag declaring `<return>` and calls it without `/var`, through Astro's compiler, container and the MX renderer: markup rendered, value dropped. `server.test.ts` pins the renderer's own unwrap. No code change.

- **Fix (marko-parity-trio, `:modifier`):** `<div :foo="y"/>` in a template body emits `value:foo={y}`, which the real Astro compiler renders as `value:foo="y"`; MX previously rejected the form.

### Docs: `/var` on a returning tag from `.amx` explains why, and shows the workaround (amx-tag-var)

The `/var` refusal on a returning tag called from an `.amx` template previously read as an unshipped feature ("is not supported in `.amx` yet"). Ruled 2026-09-28: it is a structural host limit, not a missing one — Astro runs the `---` fence to completion before the template's tags are ever lowered or called, so there is no statement position left, in the fence or the template, to bind a value into. The message now says why and points at the route that already works: calling the unit directly from the fence's own TypeScript, an ordinary function call since a `.mx` unit compiled for this host still exports the plain `{ value, output }` shape. Documented in the language spec's `/var` section, this package's README and AGENTS.md, and a new pinned test alongside the existing `astro-template.test.ts:689-720` cases. No behavior change — the refusal itself is unchanged, only its wording.

### Fixed

- **`source-bindings-silent-parse-failure` (filed from the PR #156 review):**
  a syntax error in the `---` fence used to be silently swallowed by
  `sourceBindings`, treating the fence as binding nothing — so every
  capitalized tag in that file, including a genuinely imported one,
  misreported "Unable to find entry point for custom tag" instead of the
  real syntax error. `lowerAstroMx` now surfaces the fence's own parse
  error (`AstroTemplateError`, positioned at the actual broken line/column
  in the file) when `sourceBindings` reports one, instead of silently
  falling through to component resolution with no bindings. No downstream
  layer had reported it yet at that point — `lowerAstroMx` never runs
  Astro's own compiler itself, so there is no risk of a duplicate
  diagnostic for the same error.
- `rejectUnknownTag`'s Marko-wording message now comes from `@mxlang/core`'s
  `unresolvedCustomTagMessage` instead of a hand-copied literal. No
  behavior change.

### Changed

- **Behavior change (local extension of decision 116, firstmate's ruling):**
  a `---` fence binding used as a tag now classifies the same way `.solid.mx`
  does — `@mxlang/parser`'s new `unknownSourceBindings` marks a non-import
  `const`/`function`/`class` whose value isn't statically a function/arrow/
  class as "unknown". A function-like fence binding (the common case) is
  entirely unaffected. Astro has no dynamic-tag construct at all (unlike
  every other host, `component()`'s own pre-existing guard rejects any
  non-`"name"` target unconditionally), so an unknown binding now fails at
  MX compile time with its own named error — `` `<Tag>` is bound in the
  frontmatter to a value MX can't prove is a component, and @mxlang/astro
  can't render a tag name decided at runtime. `` — instead of the
  pre-existing silent misroute (a literal `<Tag>` JSX reference that failed
  only at Astro's own render time with an opaque `NoMatchingRenderer`-class
  error).

- Named slots now expose both the callable renderable view and the default
  data view's `.content` thunk to `.mx` components. Arrays, attributes,
  params, and nested attribute tags remain positioned host errors because an
  Astro slot is keyed only by name. Nested conditionals and empty branches now
  emit valid Astro expressions, and bodiless tags are rejected because they
  have no markup to project.
- **Behavior change (decision 114 parity, `unresolved-tag-jsx-astro-angular`):**
  `<TotallyUndefined/>` — a capitalized tag with no `---` fence import,
  binding, or taglib entry — now fails to compile with Marko's own error
  ("Unable to find entry point for custom tag `<TotallyUndefined>`."),
  matching `@mxlang/html` and `@mxlang/solid`. `isComponent` used to be a
  bare `/^[A-Z]/` casing test, so every capitalized `.amx` tag resolved as a
  component whether or not the fence actually imported it. `lowerAstroMx`
  now parses the fence's own top-level value bindings
  (`@mxlang/parser`'s `sourceBindings`, new dependency) into `ctx.imports`
  before lowering — the same operator-ruling extension decision 114 already
  gave `.solid.mx`'s surrounding module — so a fence `import Card from
  "./Card.astro"` still resolves `<Card/>` exactly as before; only a
  genuinely undeclared capitalized tag now errors instead of silently
  compiling. A type-only fence import does not resolve a tag either
  (decision 114/115). `<Fragment>` — the one Astro built-in the real
  compiler auto-imports (`@astrojs/compiler-rs`, astro@7.3.2; measured, the
  only such name) — resolves with no fence import needed.

- **Fixed (pr6-s3a-tagtable-fixed):** A custom tag's `ctx.build.element(name)` without a `void` option is now void exactly when an authored `<name>` is: the target's `nativeTags` declares it void, else core's own HTML void elements. It defaulted to `void: false` before, so `ctx.build.element("br")` rendered `<br></br>` on `@mxlang/angular` and `@mxlang/astro` (`@mxlang/html` hid it by re-reading core's void names, which its emitter no longer does). An explicit `void` still wins (review 475 r3, decision 197). A void element built with children, by default or with `{ void: true }`, is now a compile error at the tag ("`<br>` is void and takes no children; pass { void: false } to emit an end tag"): `@mxlang/html` dropped those children silently; `@mxlang/angular` and `@mxlang/astro` emitted `<br>child</br>`; and the JSX hosts (`@mxlang/preact`, `@mxlang/react`, `@mxlang/hono`, `@mxlang/solid`) compiled it to `<br>child</br>` JSX, which React rejects at runtime.

- **Changed (pr6-s3a-tagtable):** A compile no longer builds `@marko/compiler`'s taglib lookup (decision 197, PR 6 slice S3a): core's own tag table, the target's taglibs over its `nativeTags`, gives the MX front end each tag's shape and tells lowering an element from a tag. It reproduces the lookup's merge for every translator MX builds, pinned against the live lookup (`tag-table.test.ts`). `@mxlang/preact`, `@mxlang/angular`, `@mxlang/solid` and `@mxlang/astro` now depend on `@mxlang/web-elements` and pass its table as their `nativeTags`. A `.<host>.mx` region reads the same table, so `<param>` is a native element in a region as it already was in a whole file. The `typescript-plugin` mapping pass builds core's table instead of Marko's lookup, and so does `@mxlang/core`'s `defaultTag` check (a tag only a `marko.json` maps is not a valid `defaultTag`). A target that declares no `nativeTags` now gets core's own HTML elements as its native layer, in a whole file, a region and the `defaultTag` check alike: the HTML element names and void names core already used, with `pre`'s preserved whitespace and `script`, `style`, `textarea` and `title` read as text. Before, Marko's lookup gave it HTML, SVG and MathML; a third-party target that renders SVG or MathML now passes `@mxlang/web-elements`' `WEB_ELEMENTS`. Lowering reads the same table for which elements are void, so a target's own `nativeTags` decides that in the IR too (it read core's fixed void names before, and dropped the body of an element the target's table did not declare void); `@mxlang/html`'s emitter trusts the IR's `void`. A registered translator-taglib tag with a same-named import or `<define>` in scope calls the module `resolveDiscoveredTagModule` returns for it (decision 164 addendum 1), and that hook's `.marko` answer is the decision 172 error.

- **Changed (rename-package-families):** Renamed (decision 201, package families): `@mxlang/html` -> `@mxlang/target-html`; `@mxlang/target-registry` -> `@mxlang/targets`, now the umbrella (the registry, the html target's descriptor as `htmlTarget`, and the html target's full entry at `@mxlang/targets/html`); `@mxlang/react` -> `@mxlang/host-react`; `@mxlang/preact` -> `@mxlang/host-preact`; `@mxlang/solid` -> `@mxlang/host-solid`; `@mxlang/hono` -> `@mxlang/host-hono`; `@mxlang/astro` -> `@mxlang/host-astro`; `@mxlang/angular` -> `@mxlang/host-angular`. Imports, emitted runtime imports (`@mxlang/host-solid/...`) and `mx.target` package selection use the new names. The old names are deprecated on the registry at the next publish. `mx-angular build` still treats an output whose header reads `Generated by @mxlang/angular from` as generated, so files built before the rename are rewritten instead of refused. `@mxlang/data` is not renamed: the tree-ir-entry change deletes it (decision 204).

- **Fixed (lowercase-local-component):** A lowercase tag naming a local binding is now Marko's own error, in core, on every target — same message verbatim, same position (the tag name): `Local variables must be in a [dynamic tag](https://markojs.com/docs/reference/language#dynamic-tags) unless they are PascalCase. Use `<${layout}/>` or rename to `Layout`.` The rule covers every local binding: a default or named `import` (a `.mx` tag module or a `.ts` value alike), a lowercase `<define>`, a `<const>`, a `<for>`/`<define>` tag param, a `static` declaration (`static const layout = 1` then `<layout/>`, plain or destructured), and an `export const`/`function`/`class` declaration. A core taglib name (`<debug>`, `<log>`) keeps its own routing — as in Marko — even when bound: no error and no "native element" warning. A native-element name stays native (silently for a value binding, with the existing warning for a tag binding); a registered custom tag, a taglib tag or a host claim still wins whatever is imported. `_`/`$`-prefixed names follow Marko's message, whose naive capitalization offers "rename to `_row`". Before, the error existed only for a tag binding (a `<define>` or a `.mx` default import) and in core's own wording ("`<layout>` is not a tag here…"), a lowercase **value** import (`import layout from "./layout.ts"` then `<layout/>`) was a silent pass on preact, react, hono, solid and astro (a literal lowercase element was emitted) and only html rejected it, through its own `rejectComponentTag` hook (now removed — core covers it). The `<const>`, `static` and tag-param forms fell to the unknown-tag path at best (html) or passed silently (the JSX hosts); a core taglib name bound by an import drew the local-variable error on the JSX hosts, where Marko compiles the tag. The message and position are measured on the stock parser (`@marko/compiler` 5.42.11 / `marko` 6.4.4): identical for a tag import, a value import, a `static const` local, an `export const` local, a `<const>` and a `<for>` param. The rest of the lowercase-tag rules are unchanged. One boundary, matching the existing import behaviour: a use *before* the `import`/`static`/`export` statement is not covered — bindings register in document order.

- **Changed (dialect-1b):** Dialect routing and MX's config now guard what belongs to MX, to other languages and to the dialect. - A dialect cannot claim, and `mx.extensions` cannot route, `.mx` in any spelling (`.MX`, `.page.Mx`), a host's file kind (`.solid.mx`, `.ng.mx`: the segments the caller's targets declare, which `compileSource` passes in, and `parseFragment` when given its new `targets` option, which every host's region entry passes), or an extension whose last segment is TypeScript's, JavaScript's or Marko's (`.ts`, `.tsx`, `.mts`, `.cts`, `.d.ts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.marko`). Each is an error at `mx.dialect.extensions` or at the `mx.extensions` entry. `.mesh.mx` stays claimable. - MX's config setting `tagRules`, or `tagRules` or `name` under a dialect's id, is an error at its key: those belong to the dialect. A top-level key that is none of MX's keys, no target's or host's settings block and no discovered dialect's id is an `unknown-config-key` error at its key; a `$` key (`$schema`) is JSON metadata and is not checked. - `compileSource` and `parseFragment` parse a dialect's files under the tag rules the dialect states, as `lowerSource` already did; MX's own files keep their target's rules. - An installed dialect whose `mx.dialect.module` is TypeScript is an error saying the module must be JavaScript Node can load, and a `module` written as a package specifier is an error saying it is a file path inside the package. - The reference `syntax/mesh` module states `tagRules: "none"`.

- **Removed (core-drops-name-sugars):** **Breaking:** core has no name sugars. Every form reads as stock Marko reads it, with Marko's errors; a dialect that wants a name sugar claims it through its syntax table. The tag-adjacent shorthand (`<div#a.b>`, `<#a>`, `<.b>`) is unchanged. Readings that change, all visible to a dialect such as Mesh: a `:` in a tag head is part of the name (`<input:email>`, `<uuid:id>`, `<:x>` and concise `entity:Todo` are one tag name each, so on web an unknown custom tag; Angular's `<svg:rect>` passes through as written), and part of a shorthand part (`<div.c:b>` is the class `c:b`, `<div#d:b>` the id `d:b`); an attribute named `:x` is Marko's `value:x` and a bare `:` is `value:`, `:x(…)` is Marko's "Unsupported arguments on the `value:x` attribute."; a spaced `#x` or `.x` in attribute position is `Invalid attribute name` (a host with `acceptsForeignAttrNames`, Angular, keeps `#ref`); a spaced ` :x` or ` .x` after any value, a default value or a single atom included, continues the value as in stock, so `<div x=a :b/>` and `<if=:a :b>` are Marko's "Expected a single expression, but found `:` after it." and `x=a .b` is member access. Removed exports: `sugarTagName` (`@mxlang/core`), `HostDeclarations.claimsAttributeHash` (Angular no longer sets it), and the `":"` value of `MxShorthand.sigil` (`@mxlang/babel`). Removed codes: `MX_SUGAR_ARGUMENTS`, `MX_SUGAR_BOUND`, `MX_SUGAR_DYNAMIC`, `MX_SUGAR_NAME_INVALID`, `MX_SUGAR_NAME_MISSING`, `MX_SUGAR_ON_STATEMENT`, `MX_SECOND_NAME`, `MX_COLON_BEFORE_DYNAMIC` and `MX_SHORTHAND_INVALID`; the "`:x` right after a default value is not supported" error is gone with them. The `Attr.sugar` and `Attr.sugarValueOf` IR fields stay, set by the tag-adjacent shorthand and by a dialect's triggers.

- **Removed (core-drops-atom-lexing):** **Breaking:** core has no atom syntax. `:x` in a `.mx` file is plain JavaScript, as in Marko: `<a b=:x/>`, `<a b=(f(:x))/>`, `${:x}` and the concise `a b=:x` are Marko's "Unexpected token" at the `:`, and `<a b=x::y/>` is "Expected a single expression, but found `:` after it.". `::` is no longer reserved: inside a name it is part of the name, as Marko reads it (`<a::b/>` is the tag `a::b`, `<a x::y=1/>` the attribute `x:` with the modifier `y`). A dialect builds atoms through its triggers: an `expressionTriggers` or `valueTriggers` row whose hook returns a `StringLiteral` marked `extra.mxAtom = { span }`; core records it, splices its string into `Expr.code`, and lowers a whole-value atom to a `static` attribute with `atom`, as before. Removed: the template parser's `onAtom` handler option and its `Atom` event, and the `MxAtom` node type (`@mxlang/babel`); the "`:a` is an atom" misuse errors, the "`::a` is reserved" error and the two hints about the `:` TypeScript owns. Kept: the `Atom` IR kind, `Expr.atoms`, `MxAtomMark`, `extra.mxAtom` and the `type: "atom"` contract shape check.

- **Fixed (hosts-colon-astro-rethrow):** An undeclared colon tag in an `.astro.mx` file (`<ns:tag/>`, `<Ns:Tag/>`) is now a compile error at the tag, as in the JSX hosts: Astro used to emit it silently as a namespace element. The fix the error names is now true for every name. It suggests an `mx.tags` `prefix` only when some prefix can produce the name (the name ends in a file stem: `<a:-x/>` takes `prefix: "a:-"`), and for a name no tag file can end (`<uuid:/>`, `<a:b$/>`) it says only to write the name without the colon. The error now carries the end of the name, so an editor underlines all of it. A lowering error inside a region of a `.solid.mx`, `.preact.mx`, `.react.mx` or `.hono.mx` file, and in an `.astro.mx` file, now reaches `mx-tsc` and the TypeScript plugin with its `MX_*` code and its whole range, where it showed `TS80001` and one character. The language server shows the same code and underlines the whole range for such an error, where it showed one character.

- **Changed (html-strict-scriptlet-fix-clause):** In strict mode (always on for Astro `.mx` files), a `$ let` or `$ var` scriptlet now says what to write instead. The error used to stop at "scriptlets (`$ statement`) are not supported in MX"; it now adds "declare a value with `<const/x=…/>` (this strict policy rejects `<let>`, which is reactive state)", naming the declared variable, and a `$ let x = ;` that fails to parse gets the same clause. Strict mode rejects `<let>`, so `<const>` is the form that compiles. The error code, line, column and end are unchanged, and so is the default policy's text.

- **Added (diagnostic-fix-its):** A diagnostic can now say how to fix itself. `IrDiagnostic.fixes` (`@unstable`) is a list of fixes, each `{ title, edits }` where an edit is `{ offset, end, newText }`: UTF-16 offsets into the same text the diagnostic's `offset` indexes (the file named by `file` when the diagnostic is positioned in another file), `end` exclusive, edits within one fix never overlapping, so applying all the edits of one fix to the original source gives the fixed source. The types are exported as `IrDiagnosticFix` and `IrDiagnosticEdit`, and a compile error carries the same list as `TranslateError.fixes`. The `<effect>` error (`MX_RESERVED_EFFECT_TAG`) now offers one fix, "Rename to `<script>`", that renames the open tag and, when there is one, the close tag; a self-closing tag, a concise tag and a `</>` close have only the open name. A host's "not supported" error for `<effect>` and the strict html policy's own row offer no fix. `fixes` travels wherever a diagnostic's `code` and `end` already do: the tag-file and tag-template errors, a JSX-region error re-raised by `@mxlang/tsx-bridge` (a non-enumerable `fixes`, offsets in the whole file), `AstroTemplateError`, `DialectDiagnostic` from `@mxlang/targets/dialect-check`, and the TypeScript plugin's `MxCompileDiagnostic`. The language server puts a diagnostic's fixes in its `data.fixes` and offers each one as a quick fix (code action) that edits the document, only while the text is the one the diagnostic was computed from. A fix for a diagnostic raised inside another file (a tag template) is not offered across files. The TypeScript plugin's tsserver diagnostics and `mx-tsc` do not show fixes.

- **Changed (hosts-unsupported-tag-message):** A tag a host does not support in embedded MX now gets one message on every host: "`<X>` is not supported in embedded MX on <Host>." Before, each host worded the refusal its own way ("`<let>` is Marko reactive state; …", "`<script>` is a Marko client-runtime tag; …", "`<let>` is reactive state and requires a runtime; …" in Astro, and Angular's `<return>` text). The host's existing advice follows as a second sentence when there is one, for example "`<let>` is not supported in embedded MX on Preact. Use Preact's `useState` via `<const/x=useState(0)/>` or in the surrounding module." `<effect>` gets the first sentence alone on every host, with no `<script>` pointer. The code stays `MX_UNSUPPORTED_CONSTRUCT` and the position stays at the tag. Angular's and Astro's `<return>` refusals and Angular's `<try>` fallback in the emitter had no code before; they now carry `MX_UNSUPPORTED_CONSTRUCT`, and `<return>` is positioned at the returned value. This covers every tag the Preact, React, Hono, Solid, Angular and Astro hosts refuse, in whole files and in region files, plus Angular's and Astro's `<return>`; `client` and `server` blocks, `<else>` and `<else-if>` without an `<if>`, and refusals that are not about a tag (dynamic tag names, tag params, type arguments, tag variables) keep their texts. Core adds a third tag disposition, `{ kind: "unsupported", hint? }`, which core words with the new host declaration `hostName` (the display name), and the exported `unsupportedTagMessage(ctx, tag, hint?)` for a refusal a host raises itself after lowering (both `@unstable`). A disposition of kind `error` keeps working with its own `reason`. Tooling that matched the old texts (goldens, expected-error files) needs the new text.

- **Changed (marko-6.4-module-scope-render-names):** Module level code that names something that exists only while the template renders is now a compile error, as in Marko 6.4: a `static`, `server` or `client` block (including the statements of a `static { … }` block) or an `export` statement that references a tag variable (`<let>`, `<const>`, `<define>`, declared anywhere in the file), `input`, `$global` or `$signal`. The error is `MX_RENDER_ONLY_IN_MODULE`, positioned at the name with its end: "`count` exists only while the template renders, so module level code (`static`, `server`, `client` and `export` statements), which runs once as the template loads, cannot reference it. Reference it in the template instead, passing it to module level functions as an argument." It is raised by core, so every host and `lowerSource` report it the same way, where these references used to compile to code that read an unbound name. A module level declaration with the spelling of a tag variable in the template's top level (`static count = 1` beside `<let/count=0/>`) is refused at the declaration, and so is a module level declaration spelled `input` (`static const input = 1`), as in Marko; `$global` and `$signal` may still be declared. A parameter or local of a module function that shadows the name, a property name, a name in a type position, a tag param (`<for|item|>`) and a module binding that shares the spelling of a tag variable only a nested tag declares are not errors. A host that refuses `server` or `client` still reports that refusal first, and the `none` tag rules leave a dialect's statements alone. Move the value into the template and pass it to a module level function as an argument.

- **Changed (static-block-unwrap):** A `static { ... }` block now hoists its statements to module scope with the braces removed, as in Marko: `static { let q = 1 }` declares `q` for the whole module, so the template can read `${q}`, where the braces used to make `q` block-scoped and the read undeclared. Only a body that is exactly one block unwraps (`static { a } { b }` and `static { a };` keep their blocks, one level only: `static {{ a }}` hoists `{ a }`), an empty block (or one holding only comments) hoists nothing but is still a module statement, so a host or region with no module scope refuses it like any other `static`, and a comment after the closing brace is dropped with it. The statements inside keep their text, comments and positions, so an error inside the block still points at its line and column. `server { ... }` hoists the same way on the html target. The render-only name check reads the same block, so a template read of a block binding is fine, and `static { const count = 1 }` beside `<let/count>` is still refused at the declaration. The non-block `static x = 1` form is unchanged. `@mxlang/core` also exports `unwrapStatementBlock`, the one reading of the block form, for hosts that hoist a statement of their own.

- **Changed (render-write-other-bindings):** Writing a binding the template does not write is now a compile error, as it is in Marko, with three new codes. Each message gives the rule and the fix and sits on the assignment or update with its end (a `for...of` or `for...in` on the loop's left side). `MX_READONLY_BINDING_WRITE`: a `<const>` and a `<for>` parameter (value, index and key) are never written, whether the write is while the template renders, in an event handler or callback, or in a `<script>` body; a `<define>` parameter bound as a plain name (`|a|`) is refused the same way; a name bound through an object pattern (`<const/{ a }=…/>`, `<for|{ a }|…>`, `<define/D|{ a }|>`) is written through its object, so it is refused only while the template renders. `MX_LET_WRITE_BEFORE_DECLARATION`: a `<let>` is written only below its declaration, in a placeholder, a handler or a `<script>` body alike, counting a `<let>` later in the same block or after it in an enclosing one. `MX_LET_LOOP_ASSIGNMENT`: a `for...of` or `for...in` cannot assign to a `<let>`, also inside a handler. A parameter or local of the same spelling still shadows the binding. The `<const>`, `<for>`, `<define>` and `<let>`-position rules apply on every target, so a template that wrote one of these now fails on Preact, React, Hono, Solid, Angular and Astro too (for example `<const/x=1/>` with `<button onClick() { x = 2 }/>` compiled to `onClick={function () { x = 2; }}` on Preact, React and Hono before). A target that refuses `<let>` itself still reports a `<let>` written above its declaration first, as `MX_LET_WRITE_BEFORE_DECLARATION`. The render write of a `<let>` (`MX_LET_WRITE_IN_RENDER`) is unchanged and stays on the html default policy. Solid now reports a write to a `<for>` parameter with the core message, so its "computed from its bounds" wording for a stepped range is no longer shown for a render write; its own refusals remain for what core does not reach. Not covered: a `<let>` or `<const>` written from a sibling block or above its declaration (for `<const>`), a name bound through an array pattern, the parameters of other tags, and a `<script>` body that does not parse. Before, all of these compiled without a message.

- **Changed (static-decorator-refused):** A decorator in a module statement is now a positioned compile error, as in Marko, whose parser has no decorators plugin. `static @d() class C {}`, `server @d() class C {}`, `client @d() class C {}` and a decorated class member (`static class C { @d m() {} }`, a property, an accessor or a parameter) compiled before and are refused now with `MX_INVALID_STATEMENT`, on every target. The error sits on the first `@` and its span covers that decorator; the same holds for `static { @d class C {} }`, `export @d class C {}` and a class expression. The message says what to do: move the decorated class to a `.ts` module and import it, or apply the decorator as a plain function call. A class with no decorator is unchanged.

- **Fixed (block-export-default-refused):** A default export in a `static`, `server` or `client` statement (`export default <value>`, `export default function`, `export default class`, `export { x as default }`, `export { default } from "…"`, `export { a as default } from "…"`, `export * as default from "…"`, in a block or without one) is a compile error at the export, `MX_INVALID_STATEMENT`, with a message that says a template is already its own default export and to use a named export instead. It used to compile to a module with two default exports that does not load, and `mx-tsc` reported TS2528 at 1:1. A type-only default (`export default interface I {}`) is erased and still compiles. Also, an `export { q }` or `export { q as other }` in its own `static`, `server` or `client` statement may name a binding an earlier statement or import declares (`static const q = 1;` then `static export { q };`, or a plain top-level `export { q }` after an `import`); it was refused with "Export 'q' is not defined." and printed a Babel warning, and stock Marko compiles it.

- **Changed (script-body-syntax-check):** A `<script>` body that does not parse is now a compile error, `MX_INVALID_STATEMENT`, positioned at the syntax error, as in Marko. Before, the html target emitted none of the body and so accepted any text (`<script>@d class C {}</script>` and `<script>const = 1;</script>` compiled), and the check for a stale `<const>` read in a `<script>` body was switched off for such a body without a word. A decorator, JSX, a proposal syntax, an `assert { … }` import attribute (write `with`) or a CommonJS `import x = require(…)` / `export = value` in a `<script>` body is refused with a message that says what to write instead (a `.ts` module for a decorated class, a tag for markup); a concise-mode body of several lines is read as one body, at positions in the file; any other error carries Babel's message at Babel's position. A body that parses compiles as before: an `import`, an `export`, a top-level `return` or `await`, type annotations, `enum`, `satisfies`, `namespace` and `declare` are accepted, and a body that holds a `${…}` placeholder is still not read. On a host that refuses `<script>` (Preact, React, Hono, Solid, Angular, Astro), a body that does not parse is now reported at its syntax error before the host's "`<script>` is not supported" message.

- **Fixed (html-script-target-support):** `<html-script>` now writes a real `<script>` element on every host, with its attributes and a body that is script text, as stock Marko 6.4.4 does. The html target (`@mxlang/target-html`) dropped every attribute (`<html-script type="module" src="/a.js">` printed a bare `<script>`) and HTML-escaped the body, so `a && b` reached the browser as `a &amp;&amp; b`; it now keeps the attributes (spreads, dynamic values and `nonce=` included, with the shared element rules) and writes the body as Marko does: each `${…}` stringified as in any text, then the joined body escaped for script context (`<script`, `</script` in any case and `<!--` become `\u003C…`), so no value can close the element. Preact, React, Hono and Solid printed a literal `<html-script>` element: they now print `<script>`, with the body through the renderer's raw-HTML prop (`dangerouslySetInnerHTML`, Solid's `innerHTML`) because a JSX renderer HTML-escapes a text child. Astro printed a literal `<html-script>` too: it now prints `<script is:inline … set:html={…}>`, `is:inline` so Astro keeps the element where it is instead of bundling it. Angular's template compiler removes every `<script>` element, so that host now refuses `<html-script>` at the tag with the ways Angular loads a script (`index.html`, the `scripts` array of `angular.json`, the DOM API) instead of emitting an element ngtsc rejects. No host invents a `nonce`: Marko reads one from `$global.cspNonce`, which an MX render does not have, so the author's own `nonce=` is the only source. On Preact, React and Hono a whole-file body is still read as markup: an element, an `<if>` or a comment in it is refused with an error (it would otherwise be silently dropped from the script, so write markup-like text inside a string placeholder), and a body loses its leading and trailing whitespace, because their whole-file compile does not register the raw-text parse option of `<html-script>`; the html target, Solid and Astro keep both, as Marko does.

Reading a derived `<const>` in a handler after writing a `<let>` it depends on is now a compile error on the html default policy and in `lowerSource`: "`total` is stale here: it derives from `items`, which this handler wrote on line 5. Compute from `items` directly, or move the check into a `<script>`, which runs after the write settles on every target." Marko, React and Solid 2 return the value from before the write there; Svelte, Vue, Angular and Lit return the new one, so the same source meant different things. Core raises it, with the new code `MX_STALE_DERIVED_READ`, at the read with its end. A handler is a function given to an `on…` attribute of any tag (a custom tag and an attribute tag included; `<lifecycle>` hooks are not handlers); the dependency set is transitive; a write in an earlier branch or block, a read after an `await`, and a read that shares a loop with the write all count. A read before the write, a read in a nested function or callback, a `<script>` body, a `<const>` that does not depend on the written `<let>`, and a parameter or local that shadows either name are not flagged. A handler held in a variable or built by a call, a function declared with `<const>` and called from a handler, a write made inside a nested function, a `for (items of …)` head used as a write, a `<const>` declared below the handler's tag, and a write followed by a read inside one `<lifecycle>` hook are not detected. Hosts and the html `strict` policy refuse `<let>` itself and never reach the check; under the `none` tag-rules preset `let` is an ordinary tag name. Before, such a read compiled without a message.

A message about one of MX's built-in tags now names the tag the way the file's dialect spells it, through `formatTag`, and uses the dialect's word for "attribute". Before, `if`, `else`, `for`, `const`, `define`, `return`, `effect`, `script`, `try`, `await` and the other built-ins were always written as MX's `<name>`, so with a dialect `const x = 1` reported `` `<const>` without a variable name (write `<const/name=value/>`) `` where the dialect's file has no such tag. The same went for the tag in an owner label (`rejectUnsupportedFields`, `checkBinding`), in the write refusals (`` `x` is a `<let>` and cannot be written while the template renders ``), in the `<try>` shape checks, in the data-file refusals of `define`, `return`, `else`, `else-if` and `try`, and in the `$ statement` and `*…` advice. This reverses the documented rule that built-in tags "keep MX's words" in `MessageVocabulary`: the doc comment and `custom-tags/dialects.md` now say the built-ins are spelled by `formatTag` like any other tag. One rule covers the hints that show a fix in MX's tags (`<const/name=value/>`, `<for|item| of=…>`, `<else if>`, `<return value=…/>`): the example is shown only when the file spells that tag as MX does, and a dialect that spells it otherwise gets the tag in its own spelling and the rule without the example. A message in MX's own words, and in a dialect with no `formatTag`, is byte for byte what it was. `formatTag` is still called only when a message is built, and a `formatTag` that throws while a built-in is spelled is `MX_DIALECT_HOOK_ERROR` at the tag. The message-vocabulary guard test now fails on a literal `` `<if>` ``-style built-in in a scanned message unless the allow-list gives the reason.

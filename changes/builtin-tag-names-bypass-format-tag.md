A message about one of MX's built-in tags now names the tag the way the file's dialect spells it, through `formatTag`, and uses the dialect's word for "attribute". Before, `if`, `else`, `for`, `const`, `define`, `return`, `effect`, `script`, `try`, `await` and the other built-ins were always written as MX's `<name>`, so with a dialect `const x = 1` reported `` `<const>` without a variable name (write `<const/name=value/>`) `` where the dialect's file has no such tag. The same went for the tag in "unsupported tag params / variable / arguments" messages, in the refusals to write a `let`, `const` or `for` parameter while the template renders, in the `<try>` shape errors, in the data-file refusals of `define`, `return`, `else`, `else-if` and `try`, and in the advice for a `$ statement` or a `*…` line. This reverses the documented rule that built-in tags "keep MX's words" in `MessageVocabulary`: the doc comment and `custom-tags/dialects.md` now say the built-ins are spelled by `formatTag` like any other tag. One rule covers the hints that show a fix in MX's tags (`<const/name=value/>`, `<for|item| of=…>`, `<else if>`, `<return value=…/>`): the example is shown only when the file spells that tag as MX does, and a dialect that spells it otherwise gets the tag in its own spelling and the rule without the example. A message in MX's own words, and in a dialect with no `formatTag`, is byte for byte what it was. `formatTag` is called only when a message is built, never for a valid file, and a `formatTag` that throws while a built-in is spelled is `MX_DIALECT_HOOK_ERROR` at the tag.

A dialect expression trigger can now be the operand of `delete`. With a `&name` trigger that a dialect lowers to a member (`self.name`), `return delete &name`, `delete (&name)` and `${delete &name}` used to fail with Babel's `Deleting local variable in strict mode.` at the `delete`, although `delete self.name` parses; whether `delete` on that member is allowed is now the dialect's rule, not a parse error about text the user did not write. The same went for a trigger whose stand-in is a number, as the target of an assignment (`#1 = 2`, `#1 += 2`), an update (`#1++`), a `for-in`/`for-of` head or a destructuring pattern (`[#1] = y`, `[...#1] = y`, `(#1) = 2`): Babel's `Invalid left-hand side …` errors no longer fire for a trigger. Errors in code the user wrote are unchanged, with the same message and position, including a real `delete x` or `1 = 2` in the same expression as a trigger (`delete x` of a plain local still reports `Deleting local variable in strict mode.`). `with (&name) {}` and a duplicated parameter still report their own errors. An expression with triggers that fails one of these checks is parsed a second time to tell the two apart; an expression with no triggers, or that fails any other way, is parsed once as before.

The stale derived read error now also covers a `<script>` body and a `<lifecycle>` hook. Writing a `<let>` and then reading a `<const>` that depends on it in the same body is a compile error with the same code, `MX_STALE_DERIVED_READ`, on the html default policy and in `lowerSource`: "`total` is stale here: it derives from `items`, which this `<script>` wrote on line 5. Compute from `items` directly." (for a hook: "which this `<lifecycle>` hook wrote"). Marko compiles the read to the value from before the write in both, as it does in a handler. A body that writes is not the place to move the read to, so the message names only the first fix; the handler message is unchanged. The scope is the handler's: the dependency set is transitive, a write in an earlier branch, a read after an `await` and a read that shares a loop with the write count, a read in a nested callback and a name that shadows either one do not. A hook is any function given to a `<lifecycle>` (`onMount`, `onUpdate`, `onDestroy`). Reading a `<const>` that a handler wrote, and reading before the write, stay fine. A `<script>` body that holds a `${…}` placeholder, and a write in one body with the read in another, are not detected. Hosts and the html `strict` policy refuse `<let>` itself and never reach the check; under the `none` tag-rules preset nothing fires. Before, such a read compiled without a message.

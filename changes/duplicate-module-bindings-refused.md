A module name declared twice across the `import`, `static`, `server`, `client` and `export` statements (in a block or without one) is a compile error, `MX_DUPLICATE_DECLARATION`, at the second declaration's name, in source order, with a message that begins `Duplicate declaration "x"` and says where the first declaration is. The rule is JavaScript's, applied after the TypeScript strip: `var` with `var` and the merges TypeScript accepts (enum with enum, overload signatures, namespace merges, `declare` merges) still compile. Pairs stock Marko compiles but whose module does not load are refused too: a `var` before a `const`, a `function` or an `import`, a `function` beside a `function`, `var`, `const` or `import`, and a namespace holding values beside a `const`, `let`, `var` or `import` in either order or before a `function` or `class` of its name (Bun, esbuild and `tsc` emit `var N` beside `function N`, and a class is read before it is initialised). Only bindings that exist at run time collide: a `declare` function, class, enum or namespace and a function signature without a body bind nothing, so they compile beside a real one, and the conflicts only TypeScript reports (TS2300, TS2384, TS2434, TS2451) are left to `mx-tsc`, while a `declare const`, `let` or `var` beside another declaration follows stock Marko's own, order-dependent answers (`declare const d` then `const d` is refused, `declare var v` then `const v` compiles); before this, `import x` with `static const x` and similar reached the host, which emitted a module that could not load. An export list that names a binding no module statement declares (`static export { q }`) is refused at the name, `MX_UNDECLARED_EXPORT`, and a value that only `declare` introduces counts as undeclared (the TypeScript strip erases it), and so does a function signature without a body, while a `type` or `interface` name is accepted; re-exports and type exports are not checked. Both codes can be renamed through a dialect's `diagnosticCodes`.

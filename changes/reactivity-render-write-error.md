Writing a `<let>` while the template renders is now a compile error on the html default policy (`lowerSource` refuses a `<let>` tag variable outright and reports the write first): "`count` is a `<let>` and cannot be written while the template renders. Write it in an event handler or a `<script>` body, or derive a value with `<const>`." Core raises it, with the new code `MX_LET_WRITE_IN_RENDER`, at the assignment or update with its end. Render position is a placeholder (`${}`, `$!{}`), an attribute, tag-argument, spread or attribute-tag value, the attributes and arguments of `<log>`, `<debug>`, `<id>`, `<lifecycle>` and `<script>`, the attributes of the `<let>` itself, a `<const>` value, the default of a tag param, and an `<if>` or `<for>` header. The body of a function, arrow or object method (an event handler, a callback, a `<let>`'s own `valueChange`) and a `<script>` body are not render position (a class member is, as in Marko), a parameter or local that shadows the `<let>` is not a write to it, and a write inside a function the template calls while it renders is not detected. Hosts and the html `strict` policy refuse `<let>` itself and never reach the check; under the `none` tag-rules preset `let` is an ordinary tag name. Before, the html target compiled such a write without a message.

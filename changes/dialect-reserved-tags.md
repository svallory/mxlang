A definition that names a reserved tag is an `MX_RESERVED_TAG` error and is dropped, on all four sources: a discovered tag file (at the file's `1:0`), an `mx.tags` entry (at that entry in the config, the tag file named in the message), an `mx.contracts` entry (at its key in the module's literal, else the module's `1:0`) and a `customTags` entry passed to `lowerSource` (at each call of the name, else the source's `1:0`). A call then resolves as if the definition were absent, and never also gets `MX_UNKNOWN_TAG`. The reserved names are core's structural names (`RESERVED_NAMES`, now exported from `@mxlang/core`) and the `reservedTags` of the dialect a file routes to; `customTags` passed with an explicit `dialect` are that dialect's own, so only core's names bind them. `MX_RESERVED_TAG` replaces the dialect-only `MX_BUILTIN_TAG_FILE` and the scan's `try` warning. `lowerSource` fix: a `customTags` entry named after `if`, `for`, `const`, `import`, `export`, `static` or any other core name was silently ignored; it is now refused. `lowerSource` change: a `customTags` entry named `try` was a thrown `TranslateError`; it is now an `MX_RESERVED_TAG` diagnostic, and `ir` is `undefined` beside any error. `compileSource` and `parseFragment` keep their throw. A `reservedTags` manifest entry that names a core name is positioned at the entry, not at the `reservedTags` key.
